The insights engine (§10 of the analytics service design), in its first form. A new `insights` feature holds the query types — trends, funnels, retention, the web overview, the events list, and the people behind any of their points — as plain serde values an app or an admin compiles without the service. With the `service` feature, the `run` operation plans each query into SQL for SQLite or Postgres and answers with the series, steps, grid, or page beside the SQL it ran, its bound parameters, and its timing (the Workings drawer's data). Property names travel as bound parameters and session columns come from an allow-list, so a name carrying SQL reads a property of that name instead of running it; every query resolves persons through `person_overrides`, so a merge applies to past events at once. Saved insights and dashboards are app-only CRUD over new `insights` and `dashboards` tables, with the default "Web overview" available as data. Live refresh: the batch writer bumps one live `ingest_ticks` row at most once per `refresh_seconds` (default 10, configurable), so watched insights re-run as events arrive without the events table being live. A minimal `live_events` stream tails the writer's last 10,000 events, filtered server-side and resumable, each item with the matched rate. The service's `routes` now also returns its live socket, which the binary starts. All query operations answer to the app's caller, like the person operations before them.
