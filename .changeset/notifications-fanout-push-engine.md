Make the fanout and push engine finish what it starts. Every batch of a topic, condition, or everyone send is pushed: the push rounds keep going while the walk is still adding deliveries, and a round never takes the key of one that already ran. A round does a bounded share — at most a thousand attempts, started within a minute — and hands the rest on at once, one round of a send at a time; one delivery's failure (an unreadable stored options value, a database error, a row gone mid-attempt) is that delivery's outcome, never the round's. A fanout step claims its batch before writing, keys its successor by the cursor it starts from, and a step that loses its batch to a replay keeps the walk going, so a send can no longer stay `fanning_out` forever. Each step wakes only its own batch's people. Retries wait one minute, doubling, with jitter that differs per delivery, on every platform, so an hour's provider outage loses nothing. Values that would overflow what the service stores are refused at send time on every target and in a dry run (`MAX_SPEC_LEN`, `MAX_TARGET_LEN`, `options::MAX_OPTIONS_LEN`), a full 255-byte idempotency key works everywhere, and a past `visible_at` is stored as now, so its push gets its full window. `cancel` is set-based and cancels a large fanout's rows in batches through the new `cancel_rows` job. Breaking: `send` and `send_test` are now `#[rpc::action]`s, so a dry run walks its audience and a test send waits on providers with no transaction open; the RPC layer keeps no request-ID receipt for them, so a retried `send` answers from its idempotency key and a retried `send_test` pushes again.
