# leptoskit_notifications

Durable notifications for LeptosKit apps: a first-party service, the send format its app's server uses, and the inbox its clients read.

An app's server sends to explicit user ids, and the service stores one durable inbox row per recipient, in a database of its own, with idempotency by send key: the same key with the same intent answers the first run's result across restarts — whenever it is asked, expiry included — and the same key with a different intent is a conflict. Recipients read their own inbox from any device their app signs in on — the web, a native app, or the server while it renders — paginated and bounded, with per-person read, dismissed, and cancelled state shared across devices. Categories and opt-out preferences are enforced at send time and at visibility, and changing one reaches screens that are already open. Scheduled sends become visible when their time comes and can be cancelled until then; expired rows leave every view. Open screens follow all of it live: the service runs wake jobs at each send's turning points, so what time changes, the watching screen re-reads.

When the operator configures a push transport — APNs by `.p8` key, FCM by service account, or Web Push by VAPID pair, each from the service's environment — the same send also reaches the devices its recipients enrolled: one durable delivery per notification and endpoint, attempted by a background job at the notification's visibility, retried on transient failures with the provider's `Retry-After` honored, ended clearly on permanent ones, and reported to the app as sanitized per-endpoint status. Delivery is at-least-once, collapse-tagged by the notification's id, and provider acceptance is as far as the service sees — never a person's receipt. Enrollment is the signed-in person's own act through a typed credential; the credential never appears in a list, a status row, or an error, and only its owner revokes it.

What this crate deliberately does not do yet: **the client half of enrollment**. The native token acquisition (APNs/FCM registration through the platform plugins) and the generated browser service-worker handlers that hand the service its subscription are later work — today an app brings its own platform-issued credential to `register_push_endpoint`. There is no delivery receipt: the service knows what the provider accepted and nothing more. Compose received items with the local-notifications plugin (`leptoskit_plugin_notifications`) where the platform supports it, and see the notifications guide for the platform gaps.

Add the service with `[services.notifications]` in `leptoskit.toml`; see the notifications guide on the site for the whole flow, the transport variables, and what push costs you.

## Worker runtime ownership

When embedding the push service, pass clones of the same `service::push::Push` configuration to `service::routes_with_push` and `service::workers_with_push`. Each database's workers own their transports. Rebuild the runtime on restart; pending jobs use that fresh runtime and persist only send and round IDs. `service::workers` and `service::routes` remain usable without push configured.
