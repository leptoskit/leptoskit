# leptoskit_cloud_runtime

LeptosKit Cloud's runtime crate: the desired state of one environment as data, the boundary a place that runs environments sits behind, and the Kubernetes manifests for one release.

A [`ReleaseSpec`](https://docs.rs/leptoskit_cloud_runtime/latest/leptoskit_cloud_runtime/spec/struct.ReleaseSpec.html) is the whole release the cloud applies: the app and its services, each with an exact image digest, port, health paths, environment variables, secret references, resources, scale, and volumes; the routes that reach them; and the policy they live under — a runtime class, egress rules, a quota, and a database's door. The spec is pure data with no plans or prices in it, and [`validate`](https://docs.rs/leptoskit_cloud_runtime/latest/leptoskit_cloud_runtime/spec/struct.ReleaseSpec.html#method.validate) refuses one no runtime could honor, one typed error per reason: two apps, a route to nowhere, a sleeper whose minimum is not zero, a process with volumes that scales past one replica, a quota the full scale would blow past, a tag where a digest belongs.

Compute the minimum environment quota with `Quota::for_processes(&spec.processes)`: every process needs its maximum replica count plus one surge pod for a rolling update. Processes with volumes use `Recreate`, so they need no surge pod. CPU counts container limits, memory counts requests equal to limits, and storage counts each claim once. Validation uses the same calculation and rejects quotas below it. One `xs` process with a maximum of one replica therefore needs two pods, 1000 millicores, and 256 MiB of memory.

An environment's Kubernetes namespace is never built from the names its owner chose: it is `lk-` plus twenty hex characters hashed from the organisation, project, and environment ids, so a rename moves nothing and no two environments collide. Slugs ride along only as labels.

The [`Runtime`](https://docs.rs/leptoskit_cloud_runtime/latest/leptoskit_cloud_runtime/runtime/trait.Runtime.html) trait is the adapter boundary: `apply` puts a spec into one environment and waits for the rollout, `status` and `logs` answer what is running, and `destroy` takes the environment down. Boxed futures let a control plane hold runtimes behind `dyn Runtime`. The `kube` feature supplies the cluster adapter; the local process adapter is a later slice.

Behind the `kubernetes` feature, [`manifests`](https://docs.rs/leptoskit_cloud_runtime/latest/leptoskit_cloud_runtime/kubernetes/fn.manifests.html) generates a restricted namespace, quota and limit range, network policies, a tokenless account, Secrets, claims, hardened Deployments, Services, scaling resources, disruption budgets and Ingress objects in dependency order. Generation is deterministic and refuses unsupported requests before applying anything. Sleeping processes use the HTTP add-on resources described below; elastic always-on processes use an HPA.

Secret values live in a `SecretValues` map that is deliberately not serializable and prints `[redacted]` in every log and error; a value appears in exactly one place, the `data` of the Secret a process reads whole from.

Behind the `testing` feature, the `Fake` is a `Runtime` that records every call, validates every spec, and lets a test script how a rollout looks afterwards — ready, never ready, or unreachable — and read back exactly what was applied.

The crate compiles without features to `wasm32-unknown-unknown`, so the cloud dashboard's browser build reads the spec types.

The `kube` feature provides `Cluster`, constructed from the worker's in-cluster ServiceAccount or an explicit development kubeconfig path, an operator profile, separately supplied redacted secret values, and an operation deadline. The control plane never puts Kubernetes credentials in `ReleaseSpec`. `Cluster::new` also accepts an existing client; configure that client's transport timeouts and disable its automatic retries as the built-in constructors do.

`apply` uses server-side apply with field manager `leptoskit-cloud-runtime`, then prunes labelled resources no longer present. It preserves PVCs and controller-owned children. Secrets precede workloads; a checksum of only each process's referenced secrets changes its pod template. Rollout readiness requires the current ReplicaSet to have the desired available replicas and the Deployment to have observed its generation. A deadline failure reports retained pod diagnostics without rolling back or deleting a ReplicaSet. Volume processes use Recreate, so the previous-pods-serving guarantee applies only to rolling processes.

Sleep routing for HTTP add-on chart 0.16.0 uses `http.keda.sh/v1beta1` `InterceptorRoute` and `keda.sh/v1alpha1` `ScaledObject`, with an `external-push` trigger naming the route and scaler endpoint. The route uses a concurrency target of 100. Each host/path pair stays in its own rule. The Ingress targets a tenant-local `ExternalName` Service pointing at the interceptor, as the add-on's versioned example documents; Traefik must permit ExternalName Services. Only interceptor pods in the configured namespace may reach a sleeper's application port through its external ingress exception. Wildcard routes omit `tls.secretName` and use Traefik's default certificate in kube-system; private keys are not copied into tenant namespaces. Platform defaults use Traefik and CoreDNS in kube-system, the HTTP add-on in keda, issuer `apps`, and default certificate `apps-wildcard-tls`. Shared database releases allow namespace `database`, TCP 5432.

`status` reports ready/desired counts, the image ID actually reported by a current ReplicaSet pod, and sleeping state. `observed_restarts` sums restart counts across that ReplicaSet's existing pods. Replaced pods take their counts with them, and kubelet can reset counts. `last_oom_kill` is the latest timestamp retained in current/last container termination states, not a cumulative OOM total. An empty image means no current pod has reported an image ID. Durable historical totals are a later slice.

`logs` merges timestamped pod logs newest first, caps lines, and limits returned JSON to 256 KiB. Lines carry process and pod names; leased secret values are redacted from diagnostics and logs. `destroy` deletes the environment namespace, including its claims, waits for disappearance, and succeeds if it is already gone.

`kubernetes::worker_rbac` supplies a ClusterRole and binding for the cluster worker. RBAC cannot restrict cluster-wide verbs by namespace labels or future namespace names: Secret list access exposes data in other namespaces. The generated rules contain no wildcard, exec, role-delegation, or watch permissions. Worker job authorization must restrict which environments it manages. A deployment requiring stricter access needs separately provisioned per-tenant RoleBindings and separate namespace lifecycle authorization.

Unit and loopback axum API tests cover generated requests and recorded rollout states. The ignored real-cluster test requires `LEPTOSKIT_TEST_KUBECONFIG`; no real-cluster apply has been performed in this slice.
