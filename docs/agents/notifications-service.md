# The notifications service

Built 15 November 2026, against `main`; topics, conditions, and the durable fanout were added 16 November 2026, person attributes, segments, and send-to-everyone the same day, and message options — shaping, silent data messages, and test sends — 17 November 2026, and device details with device targeting 18 November 2026. This is the engineering note for the first slice of first-party notification management — the durable store, the send path, and the inbox — for the audience-partitioning slice on top of it, and for the person-registry, message-options, and device slices on top of that. The status of each part is in §8; what follows later is in §9.

It follows the [analytics service](analytics-service.md)'s shape: a service crate whose library holds the operations' types (which apps compile) and whose `service` feature holds their bodies, storage, and binary (which only the service compiles). Nothing here invents a new transport, a management dashboard, or a generic delivery framework — those are non-goals (§7).

**The goal.** Every leptoskit app can add one service, `notifications`, and get durable notification management it owns end to end, instead of a third-party management platform: an app server sends to explicit users, each recipient gets exactly one durable inbox row, and every device signed in as that person sees and mutates the same inbox state.

## 1. What is built

- `crates/leptoskit_notifications`: the crate. Without features, it is the operations' types and the shared validation (`check_send` and friends, `condition` for the FCM condition grammar, `options` for message options), with no server dependencies (`tests/dependencies.rs` keeps it that way, for the wasm client tree). With `service`, it is the service; `postgres` adds the Postgres dialect.
- Operations, all under `/_leptoskit/services/notifications`:
  - `send`, `cancel`, `send_status`, `send_test`, `subscribe_to_topic`, `unsubscribe_from_topic`, `set_person_attributes`, `person_attributes`, and `forget_person` answer only the app (`caller == "app"`, per `ServiceCallers`), as `rpc::client::call_as_app` calls them. Attributes are app-only by design: a person has no operation that sets or reads them, so a segment can't be forged from the client side. `send_test` is the device probe — one attempt per live endpoint of one person, per-endpoint outcomes, nothing written.
  - `inbox`, `unread_count`, `category_preferences`, `my_topics` are live queries for the forwarded person; `mark_read`, `mark_dismissed`, `set_category_preference`, `subscribe`, `unsubscribe` are their mutations. `subscribe` is open only to topics the operator opened (`service::config::OpenTopics`, from `LEPTOSKIT_NOTIFICATIONS_OPEN_TOPICS`; nothing by default), and every person-side operation resolves the owner from the forwarded identity, never an argument.
  - `send` and `send_test` are `#[rpc::action]`s, not mutations: an action runs with no transaction open, so `send`'s `validate_only` walk reads page by page and `send_test`'s provider requests go out without holding SQLite's write lock or a pooled connection. `send`'s write is an internal mutation (`service::SendWrite`, an `rpc::Operation` implemented by hand so it is never routed) that the action runs with `cx.mutate`, with the framework's contention retries; `send_test` reads its endpoints through an internal query the same way. The cost is the RPC layer's request-ID receipts, which only mutations keep: `call_as_app` sends no idempotency header for an action, a retried `send` answers from its idempotency key (`duplicate: true`), and a retried `send_test` pushes again.
  - `wake_send`, `wake_batch`, `fanout_send`, `push_send`, and `cancel_rows` are jobs (`#[rpc::job(service = "notifications")]`), never RPC: only the service's workers run them. `fanout_send` walks one batch per run and enqueues its successor under `fanout:{key}:after:{cursor}` — the cursor it starts from, never a step number. `fanout_send`, `push_send`, and `cancel_rows` are `serialize_by = send_key`, so one send's runs of each never overlap. Every job key goes through `service::job_key`, which names the send by its SHA-256 (`{kind}#{hash}:{what}`) when the verbatim `{kind}:{key}:{what}` would pass the job table's 255-byte key column, so a full 255-byte idempotency key works everywhere.
- Tables: `notifications` (one row per recipient, unique per send and person, `live`, indexed `(person, id)`, with a `kind` — `notification` or the `data` rows a silent send writes, which never surface — and each row's own `options` JSON, which the push engine reads per delivery), `sends` (one row per idempotency key, with a SHA-256 intent hash, the counts, the fanout state, and — for topic/condition/everyone sends — the stored target, spec, and cursor), `topic_subscriptions` (`live`, unique `(person, topic)`, indexed `(topic, person)`), `audience_members` (the registry: unique `person`, `first_seen`, `updated_at`), `person_attributes` (unique `(person, key)`, ≤50 per person, keys `[a-z0-9_]{1,64}`, values ≤256 bytes), `category_preferences` (`live`, unique `(person, category)`), `wakes` (`live`, unique `person`, one row per person the service has woken), plus the `rpc` and `live` packs the service runtime needs.
- Migrations: `migrations/` (SQLite) and `migrations-postgres/`, generated with `leptoskit db --service notifications migration create` against a scratch project that path-depends on the crate (the `topics_and_fanout` migration's copy of existing `sends` rows backfills `targeted = delivered + skipped_opted_out`; the `persons_and_segments` migration's backfill registers every person the `topic_subscriptions`, `category_preferences`, and `push_endpoints` tables already knew — a person only named in a send stays unregistered; the `message_options` migration adds `notifications.kind`, defaulting every existing row to a visible notification, and the nullable `notifications.options`; the `device_details` migration adds the nullable `push_endpoints.locale`, `time_zone`, and `app_version`, no index, and a `down.sql` that drops them — reversed and reapplied by `tests/devices.rs` on SQLite and `tests/postgres.rs` on Postgres), one `init`, one `topics_and_fanout`, one `persons_and_segments`, one `message_options`, and one `device_details` each. Drift is checked with `leptoskit db --service notifications check` from the same scratch projects: one with no `[db]` (SQLite) and one with `[db] dialect = "postgres"`, each declaring `[services.notifications] path = "<checkout>/crates/leptoskit_notifications"`.
- `docs/src/guide/41-notifications.md` is the public page; the "Where things stand" section of `docs/src/readme.md` carries the accurate status.

## 2. Trust boundary

The service takes a `ServiceCallers` exactly as the framework prescribes (`routes_with`), and nothing else:

- **The app** presents `LEPTOSKIT_SERVICE_TOKEN` and is the caller `app`. Only it may `send` and `cancel`; both check `cx.identity().caller` and answer `403` otherwise.
- **A person** is a token the app minted for this service (`forward_identity`, HMAC-derived from the same token, `aud`-bound to `notifications`), surfaced as `ForwardedIdentity`. Every inbox operation resolves the owner with `service::me(cx.identity())` from that context — never from an argument, never from a header. Anonymous calls get `403`; a token for another service, an expired one, or a tampered one gets `401`.
- **There is no arbitrary user-id fallback.** No operation accepts a user id on the recipient side; A reading or mutating B's row is a `404`, indistinguishable from the row not existing.
- The usual forwarding-proxy caveat applies: browsers send the app's cookies to public service paths, so the app must keep its session cookies scoped and its edge honest. This is the same exposure every first-party public service has; `trust = "isolated"` exists for services that must not see cookies, and a deployed notifications service should stay first-party.

## 3. Semantics worth knowing when changing this

- **Idempotency is domain-level, not receipt-level.** `send` writes the `sends` row first (its key is the primary key), then fans out, then records the outcome — all in its write's one transaction. A retry re-reads the row: same intent (the canonical hash of `SendSpec` plus the deduplicated recipient set) answers the stored counts with `duplicate: true`, whenever it is asked; a different intent is a `409`. A concurrent duplicate hits the unique key and the whole mutation runs again (`Error::Contended`; on Postgres the violation aborts the transaction, so there is nothing to read in it), then answers from the store. `send` is an action, so the RPC layer keeps no receipt for it; the domain row is what survives any client's forgetfulness. Options ride the intent hash through `SendSpec` — and an all-default `MessageOptions` serializes to nothing, so a send recorded before options existed keeps answering its own retries byte for byte.
- **A data send is a hidden row, not a missing one.** `kind: "data"` writes `notifications` rows with `kind = 'data'`: the inbox's visibility predicate excludes them (`visible` filters `kind = 'notification'`), so no inbox page shows one and no unread count moves, but the send's whole bookkeeping — delivered counts, push deliveries, status, cancel, replay-safe fanout — runs on the rows exactly as for a visible send. A data row never blocks a cancel, because nobody ever saw it. The transports shape the push accordingly: APNs `apns-push-type: background` at priority 5 with `content-available` alone in `aps` (Apple requires 5 for background, and an `aps` with nothing that interacts with the person), an FCM data-only message with no notification block of any kind (FCM shows a message carrying `notification` or `android.notification` in the tray instead of handing it to the app), and no Web Push at all: browsers require every push to show a notification (Safari revokes the subscription, Edge refuses silent subscriptions), so the transport ends a data delivery `skipped`/`platform_unsupported` before any work. `check_options` refuses `image`, `sound`, `link`, and the platform blocks on a data send; a data send's badge rides as `lkbadge` data. The generated hosts don't yet forward a data message to app code (no `didReceiveRemoteNotification` or `onMessageReceived`), which the guide says.
- **Options resolve per delivery.** The row stores the send's options JSON; the push engine parses it at attempt time and resolves `badge: unread` to that recipient's live unread count (`service::unread_for`, the same predicate `unread_count` answers) — so one send badges each person's own number. Payload limits degrade in one fixed order on every transport, and in tests: the per-platform blocks and the image, then sound, badge, and link, then the send's `data` (the id-only envelope, which keeps its collapse id and, for a data message, its silent shape); past that the delivery ends `oversized` with no request. Each limit is measured on what the provider counts: APNs's encoded JSON, Web Push's encrypted record, and FCM's payload keys and values (notification, data, Android notification options, plus the encoded APNs block for an iOS token) — not the HTTP request, whose token and config the FCM error reference leaves out. FCM's `apns` block carries no second copy of the title and body unless a subtitle needs the alert. `send_test` (app-only) builds the same message from the spec alone, attempts each of the person's live endpoints once inline — no queue, no rows, no transaction open while the providers answer, bounded by the ten-endpoint enrollment cap — and answers per-endpoint states with the same sanitized reason codes. A stored options value the push engine can't parse (a newer build's, before a rollback) is a configuration stall for that delivery, never a pushed message without them.
- **Validation is split by what the clock can move.** `check_send_shape` checks what a send always is — lengths, printable text, `data`'s JSON-object shape, the recipient bound, and `expires_at > visible_at` when the spec names both — and runs before the stored-send lookup, so an accepted send answers identically forever (an expiry in the intent never makes its own retry invalid). `check_send_timing` checks what only a new send can satisfy — the year horizon, and an expiry after now when the send doesn't schedule — and runs only when the key is unknown. `check_send` runs both, for app-side pre-validation.
- **Fanout is bounded at `MAX_RECIPIENTS` (1,000) per send** for the recipients target and inserts one row per recipient in the send's own transaction. Topic and condition targets have no audience bound: they fan out through the job below.
- **The condition grammar is FCM's, extended over the app's own attributes**, in `condition.rs`: `&&`, `||`, `!`, parentheses, single-quoted topic names, and `user.<key>` predicates — `==`, `!=`, `in ['a','b']`, `has(user.<key>)`, and finite-number `<`, `<=`, `>`, `>=` (true only when both sides parse as finite numbers; `NaN` and `inf` are refused as literals). An absent attribute answers false to every predicate, `!=` and `in` included. Bounds: at most 5 distinct topics, at most 10 attribute predicates, nesting depth at most 8, at most 1,024 bytes, parse errors carrying the byte offset they gave up at. One shape is refused outright — a condition true with every membership false and every attribute absent (an "everyone" audience in disguise, checked by evaluating the parsed tree that way) — because the registry now has a plain target for that, `SendTarget::Everyone`. The check is shared code, so an app's server refuses a bad condition before the round trip and the service refuses it all the same.
- **Device details belong to the endpoint.** `register_push_endpoint` takes an optional `device: DeviceDetails` (`locale`, `time_zone`, `app_version`; `#[serde(default)]`, so older clients and stored requests parse as none). `DeviceDetails::normalized` is what the service stores — blank is absent, values trimmed, the locale in canonical BCP 47 case (`canonical_locale`), each detail checked against `MAX_LOCALE_LEN` (35, RFC 5646's minimum), `MAX_TIME_ZONE_LEN` (64), and `MAX_APP_VERSION_LEN` (64) — and a bad one refuses the enrollment by name. `DeviceDetails::sanitized` is what clients send: a bad detail is dropped instead, so an odd device never loses push. The time zone is checked for IANA shape only: no tz database was added, because a device's tzdata can be newer than the server's and an enrollment must not fail over a detail; the next slice, which needs one for local-time delivery, should treat an unknown zone as absent rather than refuse it. A re-enrollment replaces the details wholesale; when the credential and invalidation are unchanged it is a plain column update — the generation, the queued deliveries' generation and `next_attempt_at`, and every in-flight fence stay as they were. Only `push_endpoints` (the owner's list, `EndpointSummary::device`) and the registration answer carry them; `DeliveryStatus`, `TestSendOutcome`, and every app-side read do not.
- **The clients send details with no app code.** The notifications plugin gained `DEVICE` (method 9) on iOS, macOS, and Android, answering Foundation's first preferred language, `TimeZone.current.identifier`, and `CFBundleShortVersionString`, or `Locale.getDefault().toLanguageTag()`, `TimeZone.getDefault().id`, and the package's `versionName`. The `localization` and `application` plugins read the same things, but each is a separate opt-in (a direct dependency plus a `native.plugins` entry) and the CLI has no implied-plugin mechanism, so reusing them would leave details silently absent in most apps; the hosts mirror their sources instead. A host without the method answers `Unavailable` and enrollment goes on with no details. `native::reconcile` reads the details every launch and sends only when the token or the details changed: `Enrollment::sent` holds a 64-bit FNV-1a digest of what the enrollment last sent (`native::digest` — the platform, the destination, and each detail, absent told from present), never the token itself; an enrollment saved before this has none and sends once. The consequence: a launch where nothing changed makes no service call, so a server-side change the device didn't make — a revocation from another device's list — is no longer repaired at launch until the token or details change. On the web, `browser::reconcile` still registers every launch (no handle state to compare), sending `navigator.language`, the `Intl` time zone, and `EnrollOptions::app_version` when the app sets one.
- **Device predicates are judged per device.** `condition.rs` adds `Condition::Device { key: DeviceKey, test }` for `device.platform` (a `PushPlatform::as_str` name; any other literal is refused at parse), `locale` and `language` (case-insensitive; `language` is the locale's first subtag), `app_version`, and `time_zone`, with the `user.` operators, sharing the ten-predicate bound. `device.app_version` compares by `compare_versions`: drop everything from the first `-` or `+`, split on `.`, every part digits or it isn't a version, parts compared as whole numbers left to right (leading zeros dropped, so no overflow), missing parts 0; orderings are false when the held value isn't a version and their literal must be one; `==`, `!=`, and `in` fall back to exact text. With no device every device predicate is false, exactly like an absent attribute, which is also what the parse-time "everyone in disguise" check evaluates with. `Condition::matches_on(holds, attribute, device)` takes the device; `topic_anchored` treats device predicates as unknown, so a device-only condition walks the registry. In the service, `evaluate` loads a page's topics and attributes as before into `Facts` and, only when `mentions_device()`, the page's live endpoints in one query (`push::live_endpoints`); a person matches when the condition holds with no device or on any live endpoint. One inbox row per person, as always.
- **The endpoint filter runs where deliveries are written.** `push::deliveries_in_tx` takes an optional `DeviceFilter` (the condition and the batch's `Facts`) and writes a delivery only for the endpoints it admits, judged against the endpoints as that transaction reads them. That point is the fanout step's own transaction — even for a scheduled send: the fanout job runs at once, writing hidden rows and their deliveries, and the push round waits for `visible_at`. So a device whose details change between the fanout and the send's time keeps the fanout's decision, and an endpoint enrolled after the fanout gets nothing, as before. Recipients and everyone sends, and conditions without `device.`, pass no filter.
- **The person registry is who "everyone" means.** `audience_members` holds one row per person the service knows, and a person becomes known through an act, never by being named in a send: the app's server setting their attributes (`set_person_attributes`, app-only, idempotent, ≤1,000 people per call, ≤50 attributes each with cap-skipping counted per person and key), a topic subscription (batch or self), a category preference, or a push enrollment. Each registering call upserts the registry row in the same transaction; the `persons_and_segments` migration backfilled the registry from those three tables. `forget_person` (app-only, idempotent) removes the row with the person's attributes and topic subscriptions — not their inbox, preferences, or endpoints, so a returning person's own choices survive. Attributes are read back only by the app (`person_attributes`); a person has no operation over them, their own or anyone else's.
- **A condition's fanout walks the index its anchor names.** `Condition::topic_anchored` evaluates the tree three-valued — topics false, attributes unknown (Kleene): a condition that is _definitely_ false for a person holding none of its topics, whatever their attributes, can only match subscribers of the topics it names, so its fanout walks `topic_subscriptions` exactly as before. Anything else — an attribute-anchored condition like `user.plan == 'pro'`, which can match a person holding no topics — walks the `audience_members` registry, as does `SendTarget::Everyone`, which matches every registered person with no condition at all. Both walks are the same job, batches, cursor, and fences; `evaluate` loads only the topics and attribute keys the condition names.
- **The fanout job is durable, batched, and idempotent.** `send` with a topic, condition, or everyone target writes the `sends` row (intent hash, stored target and spec, state `fanning_out`) and enqueues `fanout_send` step 0 in the same transaction, then answers `fanning_out` with zero counts. Each step reads the candidates — the walk's people, ordered by person id, after the stored cursor, 500 at a time — evaluates the condition per person, and commits one transaction that first claims the batch: it moves the cursor from the value the step read to the batch's last person, fenced on that value and on `state = 'fanning_out'`, and the step writes nothing when the claim matches no row. Then the batch's inbox rows (through the same `fanout` code path a recipients send uses, opt-outs included), their push deliveries, and the counts. A cancel that lands between steps, a replayed step whose batch already committed, and two runs of one step at once all lose the claim; the loser re-reads the cursor and enqueues the step for it under that cursor's key, so a step whose winner crashed before enqueuing its successor can't leave the send fanning out forever. Replay safety is still a database constraint too — `notifications` is unique per `(send_key, person)` — and a step that finds people already holding rows skips them and moves no count. A batch whose rows are visible as it commits writes its own people's wakes in the same transaction; one that commits while the send is still scheduled enqueues `wake_batch` for exactly its people at `visible_at`. Either way a batch wakes only its own people, so a send's wake writes grow with its audience, not its square; the send's own `visible` and `expires` wakes still cover the whole send. The wake is needed because a batch's insert alone can't reach an open subscription: a live read's `visible_at <= now` was taken with an earlier `now` (§3), and the wake is the clock event. The audience is snapshotted as the fanout reaches each person.
- **Cancel mid-fanout:** `cancel` on a fanning send marks the send cancelled and cancels every row written so far — visible or not, because an audience this large can't wait for the schedule to turn — and the next step writes nothing, and the push rounds skip the send's queued deliveries as cancelled. `cancel` is set-based: existence, the visible-row rule, and the update are one statement each, no row is read into memory, and a topic/condition/everyone send with more than `FANOUT_BATCH` rows left hands them to the `cancel_rows` job, which cancels them a batch per write; the mutation answers how many it stops, and asked again before the job is through, how many are left. A complete send keeps the original rule: refuse once any row is visible and uncancelled; a known zero-fanout send answers `0` idempotently rather than `404`.
- **`validate_only` is a pure question.** It runs the full shape and timing checks, walks the audience the way the fanout will (pages of candidates, condition evaluated, nothing written), and answers the same counts shape with the audience as it stands now: targeted, minus the category's opt-outs, delivered. Every target answers it — recipients, topic, condition, and everyone. The walk is an internal query the `send` action runs, so it holds no transaction: on SQLite a mutation's transaction is `BEGIN IMMEDIATE`, and a walk inside one held every write in the service for its whole length.
- **What is stored is bounded where it is checked.** `check_spec` refuses a spec longer than `MAX_SPEC_LEN` (8,192) as stored JSON and `check_options` options longer than `MAX_OPTIONS_LEN` (4,096), the `sends.spec` and `notifications.options` columns; `check_send_shape` refuses a topic/condition/everyone target longer than `MAX_TARGET_LEN` (1,200), the `sends.target` column — a condition's quoted values grow when escaped. Each field's own bound passes more than the column holds together (about 5.7 KB of options; `data` that doubles once escaped inside the spec), and a fanout send that failed only at a step's insert was accepted as `fanning_out` and stuck there. The checks run on every target and under `validate_only`. A `visible_at` in the past is stored as the time the row is written, so the inbox and the push's 24-hour window agree on when it became visible.
- **Push rounds are bounded and chained.** One `push_send` round attempts due deliveries a page of `DELIVERY_CONCURRENCY` at a time, after an id cursor, until none is due or it has made 1,000 attempts or spent a minute starting them, then enqueues its successor: at once (keyed by this run's job id and attempt) when it stopped short; at the earliest `next_attempt_at` otherwise (one ordered `LIMIT 1` query, never a load of the queue); and every few seconds while the send still fans out, so later batches' deliveries are found. Those successors are keyed by the whole second they run at, at least a second ahead (`push:{key}:at:{second}`), so two chains of rounds that meet become one and no key names a round that already ran. A fanout kicks the rounds once (`push:{key}:fanout`) and once more as it completes (`push:{key}:final`), when anything is queued. One delivery that fails inside the service — a database error, a panic, a notification row gone before the outcome's write — is put off a minute (or, for the gone row, ended as cancelled) on its own row, never failing the round.
- **Visibility is a SQL predicate; arrival is a wake.** `visible` is `visible_at <= now AND cancelled_at IS NULL AND (expires_at IS NULL OR expires_at > now)`, plus the reader's opted-out categories — but a recorded live read set is judged against the condition it was read with, and its `now` is a constant of that run: a row inserted after the read (scheduled or not) can't match `visible_at <= then`, and no commit happens at all when an expiry's time simply passes. So the service owns the clock event: every send enqueues a `wake_send` job when it becomes visible (now for an immediate send, `visible_at` for a scheduled one) and another at its `expires_at`, in the send's transaction. The job writes one `wakes` row per person the send reached — `inbox` and `unread_count` read the reader's wake row and ignore its value, which puts `wakes` in their read set — and each of their open subscriptions re-runs with a fresh `now`. A wake that changes nothing (cancelled send, dismissed row) re-runs the query and sends nothing, because the result didn't change. The jobs are the framework's own (`rpc_jobs`, claim, lease, retry): no new scheduler, no polling daemon; the workers are started by the service's binary (`service::workers`) beside its routes and poll every second, so a scheduled item lands close to its time.
- **Cancel-before-due:** `cancel` refuses once any row of the send is visible and uncancelled; a fully cancelled send answers `0` whenever it's asked again. Existence is the `sends` row, not the fanout: a send every recipient opted out of has no rows, and cancelling it answers `0` idempotently rather than `404`.
- **Preferences bind at both ends:** the send skips opted-out recipients (counted in `skipped_opted_out`), and the inbox hides rows in categories the reader opted out of since, so an opt-out covers history too. The table is `live`, so the preference write itself re-runs the setter's open inbox, badge, and preferences subscriptions. A raced insert (two devices, one new category) fails the unique key and the mutation runs again, so the last setting to commit is the one that holds — no answer is swallowed. At most `MAX_PREFERENCES` (100) rows per person, so the visibility filter stays a bounded `ne` chain.
- **Row ids are UUID v7**, assigned by the service, so `ORDER BY id DESC` is arrival order and a stable pagination cursor; `notifications` is indexed `(person, id)` for exactly that query. Inbox pages clamp to `MAX_INBOX_PAGE` (100) before the framework's own 1,000-row clamp.
- **Live:** `notifications`, `category_preferences`, and `wakes` are `live` tables. Sends, reads, dismissals, opt-outs, schedules turning due, and expiries all reach watching screens.

## 4. Tests

`tests/service.rs` runs a real server over a migrated SQLite database: authorization (anonymous, wrong token, forged and foreign-service identity tokens, app-only send/cancel), cross-person isolation, cross-device shared state, idempotency across a file-backed database restart — and the same after a send's expiry, with a changed intent still conflicting and a born-expired new send refused — every bound (keys, titles, bodies, data shape and size, recipient count, schedule horizon and ordering), scheduled visibility arriving, cancelling before due and refusing after (including a zero-fanout send), expiry leaving every view, preferences at send and at visibility, three-page pagination with cursor order, concurrent duplicate sends fanning out once, and the migrations themselves (tables and packs exist; the `sends` intent row is written). `tests/options.rs` covers the message-options slice: bad options refused with the field named, a data send delivering without surfacing anywhere, data-send idempotency (options in the intent) and status and cancellation, an invisible topic data send fanning out, and the app-only, write-nothing, per-endpoint `send_test` (bounded, single-endpoint, not-found for foreign ids, refused without transports). `tests/push.rs` covers the round engine — every batch of a 1,201-person topic send pushed with one worker running jobs one at a time, a round bounded at 1,000 attempts with its successor due at once and serialized, an unreadable options value and a row gone mid-attempt each kept to its own delivery, a test send holding up no write while a held provider answers, a 255-byte key pushing, a past `visible_at` pushing inside its window — and its retry tests move the queue's clock (`settled_rewinding`) rather than waiting out the backoff; `src/service/push.rs` unit-tests the schedule (an hour's outage outlasted inside the horizon, jitter differing per delivery, `Retry-After` lengthening only). ## 5. What an app that uses this must set

- `[services.notifications]` with `crate = "leptoskit_notifications"` (or a workspace `package`) and `trust = "first-party"` — a workspace `package` defaults first-party, but a registry `crate` defaults `isolated`, which forwards no identity; the guide's first snippet says it explicitly. `forward_identity` then defaults on.
- The app's server serves `rpc::server::Server` with its sign-in `Identify` (the scaffold's shape) so forwarded-identity tokens can be minted.
- Sending needs the service's token on the server side, which `leptoskit dev`/`serve` and deploys provide as `LEPTOSKIT_SERVICE_NOTIFICATIONS_TOKEN`.

## 6. Performance envelope

SQLite in the service's own file handles the target load — badge polls are one indexed count, inbox pages are one indexed range read per page, sends are one transaction with up to 1,000 small inserts. Postgres is the same code with the other dialect. Nothing here is measured against a production-sized corpus yet; before claiming large-fanout numbers, run the load harness the analytics service has.

## 7. Non-goals

- **No OS push transports** (APNs, FCM, Web Push), no device registry, no tokens-at-rest for vendors. The next slices add transports; this crate only stores and serves.
- **No management dashboard**, no admin UI, no generic "transport" trait with speculative backends.
- **No generic scheduler or polling daemon.** The wake jobs are lifecycle-managed rows in the framework's own `rpc_jobs` table — enqueued in the send's transaction, run once by the service's workers, pruned with them — not a service-owned loop. This revises the first slice's "no daemon" note: time-based arrival on an open subscription turned out to need the wake (§3), and this is the smallest mechanism that provides it on the framework's existing jobs and live invalidation.

## 9. What follows

The server side of push is built: `crates/leptoskit_notifications`'s `push` module holds the typed credentials and enrollment operations, `service::push` the delivery engine (per-instance configuration carried by the routes and named in the jobs — a process may serve several services without sharing credentials), and `service::transport` the APNs, FCM, and Web Push senders behind an injected HTTP boundary, with the shipped-provider host policy for Web Push. All three transports run on ring's constant-time primitives directly: Web Push's RFC 8291 encryption and RFC 8292 VAPID beside the FCM service-account assertion (RS256, as Google's OAuth requires) and APNs's ES256 provider token — the `web-push` crate left when its `jwt-simple`/`ece` chain carried the `rsa` and `crypto-bigint` advisories. The client halves are built too: the `native` module turns the platform's token into enrollment on iOS, macOS, and Android, and the `browser` module serves the receiver worker and enrolls the browser's subscription. Message options are built over all three transports, and the `send_test` probe with them. What follows on the audience side: localization (translated title and body per `device.locale`) and recipient-local-time scheduling (per `device.time_zone`, which then needs a time zone database on the server — treat a name it doesn't know as absent), and analytics. Device details exist now; `device.platform` names the push service, so `'apns'` cannot tell iOS from macOS — an OS detail from the hosts would be the way to add that. The Android host's `encodeSnapshot` wrote its integers big-endian while the bridge codec reads little-endian (the instrumentation test decoded little-endian and would have caught it on an emulator); the device slice fixed it alongside the new `DEVICE` reply. Windows toasts wait on the plugin's backend; Windows and Linux enrollment has no story yet.

Two framework contracts are worth naming for later work. First, a job's context is rebuilt from its owner alone, so a service cannot carry per-instance state to its job bodies through the context: the push job names its instance key in its arguments and looks it up in the service's own registry. A `Jobs::new(db).state::<G>(…)`-shaped hook in `leptoskit_rpc` — or service-scoped job state — would remove that registry. Second, `#[rpc::job]` registration is a stateless `fn`, so the same conclusion holds for any transport-like dependency a job needs.

## Endpoint ownership and credential generations

Endpoint ids never change owner. Provider invalidation preserves ownership, including the oldest invalidated records; only explicit revocation releases a destination. New enrollment after revocation creates a fresh id. Every insert and reactivation checks the live endpoint cap in the RPC mutation’s serializable transaction. Live idempotent enrollment succeeds at the cap.

Endpoints and deliveries carry a monotonic credential generation. Same-owner rotation or reactivation advances the endpoint and its queued deliveries together. Before HTTP, the attempt checks endpoint, delivery, and notification ownership. After HTTP, a short transaction locks the exact endpoint generation and fences outcome writes on delivery generation, queue state, and attempt count. Terminal states remain terminal. No database transaction spans HTTP. Held-response tests cover acceptance, transient failure, and unregistration across rotation and reactivation on SQLite and ephemeral Postgres.

This fix does not complete the feature: native registration and browser receiver integration remain separate work.

Delivery retries stop at eight actual push requests, including requests refused for authentication. On every platform the engine waits one minute after the first, doubling after each (1, 2, 4 … 64 minutes, about two hours in all, so an hour's provider outage loses nothing), plus up to a quarter more of jitter hashed from the delivery's whole id and its attempt count, so deliveries minted together don't retry together. A provider's `Retry-After` is honored when it is longer than that wait, and never shortens it. OAuth token exchanges are separate and do not spend push attempts. FCM refreshes once after a 401; the next push goes through the durable queue and its attempt budget. An exchange failure retries every minute with sanitized `operator_configuration` status. Neither provider diagnostics nor credentials appear in that status.

Every delivery has a deadline: the earlier of notification expiry and 24 hours after `visible_at`, including notifications with no expiry. Provider `Retry-After` accepts delta seconds and HTTP dates; invalid values use backoff. A provider delay is never shortened into an earlier push. If it exceeds the deadline, the queue wakes at the deadline and ends delivery (`expired` or `horizon_exceeded`) without another request. Unrepresentable arithmetic ends with `retry_overflow`. Local schedule, cancellation, expiry, and horizon decisions do not spend attempts. See [FCM error codes](https://firebase.google.com/docs/cloud-messaging/error-codes).
