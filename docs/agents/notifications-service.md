# The notifications service

Built 15 November 2026, against `main`; topics, conditions, and the durable fanout were added 16 November 2026, person attributes, segments, and send-to-everyone the same day, and message options — shaping, silent data messages, and test sends — 17 November 2026, device details with device targeting 18 November 2026, and translated variants with local-time delivery the same day. This is the engineering note for the first slice of first-party notification management — the durable store, the send path, and the inbox — for the audience-partitioning slice on top of it, and for the person-registry, message-options, and device slices on top of that. The status of each part is in §8; what follows later is in §9.

It follows the [analytics service](analytics-service.md)'s shape: a service crate whose library holds the operations' types (which apps compile) and whose `service` feature holds their bodies, storage, and binary (which only the service compiles). Nothing here invents a new transport, a management dashboard, or a generic delivery framework — those are non-goals (§7).

**The goal.** Every leptoskit app can add one service, `notifications`, and get durable notification management it owns end to end, instead of a third-party management platform: an app server sends to explicit users, each recipient gets exactly one durable inbox row, and every device signed in as that person sees and mutates the same inbox state.

## 1. What is built

- `crates/leptoskit_notifications`: the crate. Without features, it is the operations' types and the shared validation (`check_send` and friends, `condition` for the FCM condition grammar, `options` for message options), with no server dependencies (`tests/dependencies.rs` keeps it that way, for the wasm client tree). With `service`, it is the service; `postgres` adds the Postgres dialect.
- Operations, all under `/_leptoskit/services/notifications`:
  - `send`, `cancel`, `send_status`, `send_test`, `subscribe_to_topic`, `unsubscribe_from_topic`, `set_person_attributes`, `person_attributes`, and `forget_person` answer only the app (`caller == "app"`, per `ServiceCallers`), as `rpc::client::call_as_app` calls them. Attributes are app-only by design: a person has no operation that sets or reads them, so a segment can't be forged from the client side. `send_test` is the device probe — one attempt per live endpoint of one person, per-endpoint outcomes, nothing written.
  - `inbox`, `unread_count`, `category_preferences`, `my_topics` are live queries for the forwarded person; `mark_read`, `mark_dismissed`, `set_category_preference`, `subscribe`, `unsubscribe` are their mutations. `subscribe` is open only to topics the operator opened (`service::config::OpenTopics`, from `LEPTOSKIT_NOTIFICATIONS_OPEN_TOPICS`; nothing by default), and every person-side operation resolves the owner from the forwarded identity, never an argument.
  - `send` and `send_test` are `#[rpc::action]`s, not mutations: an action runs with no transaction open, so `send`'s `validate_only` walk reads page by page and `send_test`'s provider requests go out without holding SQLite's write lock or a pooled connection. `send`'s write is an internal mutation (`service::SendWrite`, an `rpc::Operation` implemented by hand so it is never routed) that the action runs with `cx.mutate`, with the framework's contention retries; `send_test` reads its endpoints through an internal query the same way. The cost is the RPC layer's request-ID receipts, which only mutations keep: `call_as_app` sends no idempotency header for an action, a retried `send` answers from its idempotency key (`duplicate: true`), and a retried `send_test` pushes again.
  - `wake_send`, `wake_batch`, `wake_local`, `fanout_send`, `push_send`, `cancel_rows`, `cancel_hidden_rows`, retention's `prune` (hourly cron) and `prune_rows`, and `recur` (at each occurrence's instant, and an hourly cron) are jobs (`#[rpc::job(service = "notifications")]`), never RPC: only the service's workers run them. `fanout_send` walks one batch per run and enqueues its successor under `fanout:{key}:after:{cursor}` — the cursor it starts from, never a step number. `fanout_send`, `push_send`, `cancel_rows`, and `cancel_hidden_rows` are `serialize_by = send_key`, so one send's runs of each never overlap. Every job key goes through `service::job_key`, which names the send by its SHA-256 (`{kind}#{hash}:{what}`) when the verbatim `{kind}:{key}:{what}` would pass the job table's 255-byte key column, so a full 255-byte idempotency key works everywhere.
- Tables: `notifications` (one row per recipient, unique per send and person, `live`, indexed `(person, id)`, with a `kind` — `notification` or the `data` rows a silent send writes, which never surface — and each row's own `options` JSON, which the push engine reads per delivery), `sends` (one row per idempotency key, with a SHA-256 intent hash, the counts, the fanout state, and — for topic/condition/everyone sends — the stored target, spec, and cursor), `topic_subscriptions` (`live`, unique `(person, topic)`, indexed `(topic, person)`), `audience_members` (the registry: unique `person`, `first_seen`, `updated_at`), `person_attributes` (unique `(person, key)`, ≤50 per person, keys `[a-z0-9_]{1,64}`, values ≤256 bytes), `category_preferences` (`live`, unique `(person, category)`), `wakes` (`live`, unique `person`, one row per person the service has woken), plus the `rpc` and `live` packs the service runtime needs.
- Migrations: `migrations/` (SQLite) and `migrations-postgres/`, generated with `leptoskit db --service notifications migration create` against a scratch project that path-depends on the crate (the `topics_and_fanout` migration's copy of existing `sends` rows backfills `targeted = delivered + skipped_opted_out`; the `persons_and_segments` migration's backfill registers every person the `topic_subscriptions`, `category_preferences`, and `push_endpoints` tables already knew — a person only named in a send stays unregistered; the `message_options` migration adds `notifications.kind`, defaulting every existing row to a visible notification, and the nullable `notifications.options`; the `device_details` migration adds the nullable `push_endpoints.locale`, `time_zone`, and `app_version`, no index, and a `down.sql` that drops them — reversed and reapplied by `tests/devices.rs` on SQLite and `tests/postgres.rs` on Postgres), the `scale_indexes` migration adds `push_deliveries (endpoint, state)`, `push_deliveries (send_key, state, id)`, and `notifications (person, kind, dismissed_at, read_at)`, drops `push_deliveries (state, next_attempt_at)`, which no query used, and on Postgres also carries the `audience_members` table comment the ownership work changed without a migration; the `endpoint_seen` migration adds the nullable `push_endpoints.seen_at`, no backfill and no index, with a `down.sql` that drops it; the `open_tracking` migration adds the nullable `notifications.opened_at` and `sends.label`, no backfill and no index, and replaces the `notifications` live triggers so that they capture the new column, with a `down.sql` that drops both columns and restores the triggers), one `init`, one `topics_and_fanout`, one `persons_and_segments`, one `message_options`, one `device_details`, one `scale_indexes`, one `endpoint_seen`, and one `open_tracking` each. Two merged `down.sql` files were corrected: `message_options` now cancels every `kind = 'data'` row before the column goes, so a rollback never surfaces a silent message in an inbox, and the Postgres `init` drops the `live` and `rpc` schemas it created, each only when the rollback left it empty and the role may drop it, so a schema shared with something else stays. `tests/migrations.rs` covers both. Drift is checked with `leptoskit db --service notifications check` from the same scratch projects: one with no `[db]` (SQLite) and one with `[db] dialect = "postgres"`, each declaring `[services.notifications] path = "<checkout>/crates/leptoskit_notifications"`.
- `docs/src/guide/notifications/` is the public chapter (`readme.md` is its overview, `troubleshooting.md` holds the reason codes, `reference.md` the operations, limits and variables); the "Where things stand" section of `docs/src/readme.md` carries the accurate status.

## 2. Trust boundary

The service takes a `ServiceCallers` exactly as the framework prescribes (`routes_with`), and nothing else:

- **The app** presents `LEPTOSKIT_SERVICE_TOKEN` and is the caller `app`. Only it may call the app-only operations (`send`, `cancel`, `send_status`, `send_report`, `list_sends`, `send_test`, the batch topic and attribute calls, `forget_person`, `push_deliveries`, `person_endpoints`, `revoke_person_endpoints`, `preview_push`, the catalogue, the campaign and the recurrence operations; the public chapter's reference page lists them all); each checks `cx.identity().caller` and answers `403` otherwise.
- **A person** is a token the app minted for this service (`forward_identity`, HMAC-derived from the same token, `aud`-bound to `notifications`), surfaced as `ForwardedIdentity`. Every inbox operation resolves the owner with `service::me(cx.identity())` from that context — never from an argument, never from a header. Anonymous calls get `403`; a token for another service, an expired one, or a tampered one gets `401`.
- **There is no arbitrary user-id fallback.** No operation accepts a user id on the recipient side; A reading or mutating B's row is a `404`, indistinguishable from the row not existing.
- The usual forwarding-proxy caveat applies: browsers send the app's cookies to public service paths, so the app must keep its session cookies scoped and its edge honest. This is the same exposure every first-party public service has; `trust = "isolated"` exists for services that must not see cookies, and a deployed notifications service should stay first-party.

## 3. Semantics worth knowing when changing this

- **Idempotency is domain-level, not receipt-level.** `send` writes the `sends` row first (its key is the primary key), then fans out, then records the outcome — all in its write's one transaction. A retry re-reads the row: same intent (the canonical hash of `SendSpec` plus the deduplicated recipient set) answers the stored counts with `duplicate: true`, whenever it is asked; a different intent is a `409`. A concurrent duplicate hits the unique key and the whole mutation runs again (`Error::Contended`; on Postgres the violation aborts the transaction, so there is nothing to read in it), then answers from the store. `send` is an action, so the RPC layer keeps no receipt for it; the domain row is what survives any client's forgetfulness. Options ride the intent hash through `SendSpec` — and an all-default `MessageOptions` serializes to nothing, so a send recorded before options existed keeps answering its own retries byte for byte.
- **A data send is a hidden row, not a missing one.** `kind: "data"` writes `notifications` rows with `kind = 'data'`: the inbox's visibility predicate excludes them (`visible` filters `kind = 'notification'`), so no inbox page shows one and no unread count moves, but the send's whole bookkeeping — delivered counts, push deliveries, status, cancel, replay-safe fanout — runs on the rows exactly as for a visible send. A data row never blocks a cancel, because nobody ever saw it. The transports shape the push accordingly: APNs `apns-push-type: background` at priority 5 with `content-available` alone in `aps` (Apple requires 5 for background, and an `aps` with nothing that interacts with the person), an FCM data-only message with no notification block of any kind (FCM shows a message carrying `notification` or `android.notification` in the tray instead of handing it to the app), and no Web Push at all: browsers require every push to show a notification (Safari revokes the subscription, Edge refuses silent subscriptions), so the transport ends a data delivery `skipped`/`platform_unsupported` before any work. `check_options` refuses `image`, `sound`, `link`, and the platform blocks on a data send; a data send's badge rides as `lkbadge` data. The generated hosts don't yet forward a data message to app code (no `didReceiveRemoteNotification` or `onMessageReceived`), which the guide says.
- **Options resolve per delivery.** The row stores the send's options JSON; the push engine parses it at attempt time and resolves `badge: unread` to that recipient's live unread count (`service::unread_for`, the same predicate `unread_count` answers) — so one send badges each person's own number. Payload limits degrade in one fixed order on every transport, and in tests: the per-platform blocks and the image, then sound, badge, and link, then the send's `data` (the id-only envelope, which keeps its collapse id and, for a data message, its silent shape); past that the delivery ends `oversized` with no request. Each limit is measured on what the provider counts: APNs's encoded JSON, Web Push's encrypted record, and FCM's payload keys and values (notification, data, Android notification options, plus the encoded APNs block for an iOS token) — not the HTTP request, whose token and config the FCM error reference leaves out. FCM's `apns` block carries no second copy of the title and body unless a subtitle needs the alert. `send_test` (app-only) builds the same message from the spec alone, attempts each of the person's live endpoints once inline — no queue, no rows, no transaction open while the providers answer, bounded by the ten-endpoint enrollment cap — and answers per-endpoint states with the same sanitized reason codes. A stored options value the push engine can't parse (a newer build's, before a rollback) is a configuration stall for that delivery, never a pushed message without them.
- **Validation is split by what the clock can move.** `check_send_shape` checks what a send always is — lengths, printable text, `data`'s JSON-object shape, the recipient bound, and `expires_at > visible_at` when the spec names both — and runs before the stored-send lookup, so an accepted send answers identically forever (an expiry in the intent never makes its own retry invalid). `check_send_timing` checks what only a new send can satisfy — the year horizon, and an expiry after now when the send doesn't schedule — and runs only when the key is unknown. `check_send` runs both, for app-side pre-validation.
- **Fanout is bounded at `MAX_RECIPIENTS` (1,000) per send** for the recipients target and inserts one row per recipient in the send's own transaction. Topic and condition targets have no audience bound: they fan out through the job below.
- **The condition grammar is FCM's, extended over the app's own attributes**, in `condition.rs`: `&&`, `||`, `!`, parentheses, single-quoted topic names, and `user.<key>` predicates — `==`, `!=`, `in ['a','b']`, `has(user.<key>)`, and finite-number `<`, `<=`, `>`, `>=` (true only when both sides parse as finite numbers; `NaN` and `inf` are refused as literals). An absent attribute answers false to every predicate, `!=` and `in` included. Bounds: at most 5 distinct topics, at most 10 attribute predicates, nesting depth at most 8, at most 1,024 bytes, parse errors carrying the byte offset they gave up at. One shape is refused outright — a condition true with every membership false and every attribute absent (an "everyone" audience in disguise, checked by evaluating the parsed tree that way) — because the registry now has a plain target for that, `SendTarget::Everyone`. The check is shared code, so an app's server refuses a bad condition before the round trip and the service refuses it all the same.
- **Device details belong to the endpoint.** `register_push_endpoint` takes an optional `device: DeviceDetails` (`locale`, `time_zone`, `app_version`; `#[serde(default)]`, so older clients and stored requests parse as none). `DeviceDetails::normalized` is what the service stores — blank is absent, values trimmed, the locale in canonical BCP 47 case (`canonical_locale`), each detail checked against `MAX_LOCALE_LEN` (35, RFC 5646's minimum), `MAX_TIME_ZONE_LEN` (64), and `MAX_APP_VERSION_LEN` (64) — and a bad one refuses the enrollment by name. `DeviceDetails::sanitized` is what clients send: a bad detail is dropped instead, so an odd device never loses push. The time zone is checked for IANA shape only at enrollment, never against a tz database, because a device's tzdata can be newer than the server's and an enrollment must not fail over a detail; local-time delivery, which does look zones up, treats one it doesn't know as absent (below). A re-enrollment replaces the details wholesale; when the credential and invalidation are unchanged it is a plain column update — the generation, the queued deliveries' generation and `next_attempt_at`, and every in-flight fence stay as they were. Only `push_endpoints` (the owner's list, `EndpointSummary::device`) and the registration answer carry them; `DeliveryStatus`, `TestSendOutcome`, and every app-side read do not.
- **The clients send details with no app code.** The notifications plugin gained `DEVICE` (method 9) on iOS, macOS, and Android, answering Foundation's first preferred language, `TimeZone.current.identifier`, and `CFBundleShortVersionString`, or `Locale.getDefault().toLanguageTag()`, `TimeZone.getDefault().id`, and the package's `versionName`. The `localization` and `application` plugins read the same things, but each is a separate opt-in (a direct dependency plus a `native.plugins` entry) and the CLI has no implied-plugin mechanism, so reusing them would leave details silently absent in most apps; the hosts mirror their sources instead. A host without the method answers `Unavailable` and enrollment goes on with no details. `native::reconcile` reads the details every launch and sends only when the token or the details changed: `Enrollment::sent` holds a 64-bit FNV-1a digest of what the enrollment last sent (`native::digest` — the platform, the destination, and each detail, absent told from present), never the token itself; an enrollment saved before this has none and sends once. A launch where nothing changed sends no registration; it asks the one-row `push_endpoint_standing` query instead, so a server-side revoke is learned at the next launch and never repaired (see the ownership section below). On the web, `browser::reconcile` renews the saved enrollment every launch (no digest to compare), sending `navigator.language`, the `Intl` time zone, and `EnrollOptions::app_version` when the app sets one.
- **Device predicates are judged per device.** `condition.rs` adds `Condition::Device { key: DeviceKey, test }` for `device.platform` (a `PushPlatform::as_str` name; any other literal is refused at parse), `locale` and `language` (case-insensitive; `language` is the locale's first subtag), `app_version`, and `time_zone`, with the `user.` operators, sharing the ten-predicate bound. `device.app_version` compares by `compare_versions`: drop everything from the first `-` or `+`, split on `.`, every part digits or it isn't a version, parts compared as whole numbers left to right (leading zeros dropped, so no overflow), missing parts 0; orderings are false when the held value isn't a version and their literal must be one; `==`, `!=`, and `in` fall back to exact text. With no device every device predicate is false, exactly like an absent attribute, which is also what the parse-time "everyone in disguise" check evaluates with. `Condition::matches_on(holds, attribute, device)` takes the device; `topic_anchored` treats device predicates as unknown, so a device-only condition walks the registry. In the service, `evaluate` loads a page's topics and attributes as before into `Facts` and, only when `mentions_device()`, the page's live endpoints in one query (`push::live_endpoints`); a person matches when the condition holds with no device or on any live endpoint. One inbox row per person, as always.
- **The endpoint filter runs where deliveries are written.** `push::deliveries_in_tx` takes an optional `DeviceFilter` (the condition and the batch's `Facts`) and writes a delivery only for the endpoints it admits, judged against the endpoints as that transaction reads them. That point is the fanout step's own transaction — even for a scheduled send: the fanout job runs at once, writing hidden rows and their deliveries, and the push round waits for `visible_at`. So a device whose details change between the fanout and the send's time keeps the fanout's decision, and an endpoint enrolled after the fanout gets nothing, as before. Recipients and everyone sends, and conditions without `device.`, pass no filter.
- **Variants and local time resolve per person, a batch at a time.** `local.rs` (shared) holds `Variant`, `LocalTime`, their checks, and the locale match; `service/local.rs` holds the tz lookups and the batch resolver. `SendSpec::variants` is a `BTreeMap` from BCP 47 tag to `Variant { title, body, subtitle, actions }` (at most `MAX_VARIANTS`, 32; each field within the bound of the text it replaces; `subtitle` and `actions` only where the send sets `options.apple.subtitle` or names that web action; none on a data send; the whole spec still inside `MAX_SPEC_LEN`, and each variant's resolved options inside `MAX_OPTIONS_LEN`, because the row stores them). `SendSpec::local_time` is `LocalTime { at, default_time_zone }`: `at` is `YYYY-MM-DDTHH:MM[:SS]` with no offset, the default zone is UTC when left out. Both fields skip serializing when unset, so the intent hash and the stored spec of every earlier send are byte for byte what they were; set, they are part of the intent. `SendSpec` derives `Default` so a literal can end `..SendSpec::default()`.
  - _The rule_ (decided, do not reopen): the app's `locale` or `time_zone` attribute, then the person's most recently seen live endpoint that says, then the send's default. `local::resolve` reads a batch's two attribute keys in one query and its live endpoints in another, sorted by `seen_at` (falling back to `created_at`), then `id`; a send with neither feature reads nothing. The recipients send resolves inside its transaction; a fanout step resolves before its transaction opens, beside `evaluate`. An attribute that isn't a BCP 47 tag, or names a zone the tz database doesn't have, falls to the next step; so does an endpoint with such a zone, to the next most recent endpoint. A valid `locale` attribute wins even when no variant matches it.
  - _Locale match_: RFC 4647 lookup, case-insensitive: the whole tag, then with its last subtag dropped (a dangling one-letter extension subtag goes with it), down to the language. It never widens (`pt` does not read a `pt-BR` variant). Variant keys may be spelled in any case; two keys that are the same tag are refused.
  - _Time zones_: `jiff` with `tzdb-bundle-always`, behind the `service` feature only (the client tree stays free of it; `tests/dependencies.rs`). The bundled database makes a deployment's answers independent of the host's `zoneinfo`. `Etc/Unknown`, POSIX TZ strings, and offsets are not zones. A gap takes jiff's "compatible" reading (02:30 in a 02:00→03:00 gap is 03:30), a fold the first occurrence. Every arrival is clamped into `[at − 14 h, at + 12 h]` as UTC, the span real zones fall in, so the checks below hold for every row. The send's `default_time_zone` must be known when the send is new or a dry run (`check_default_zone`, a 400 naming it); a stored send whose default zone a later build lost falls back to UTC rather than failing its fanout.
  - _The checks_: `check_spec` runs `check_variants` and `check_local_time` (so `send_test` gets them too). Shape, forever: `at` parses; `visible_at` and `local_time` together are refused; `expires_at` must be after `LocalTime::latest()`, the wall-clock time plus twelve hours read as UTC, so no row can expire before it shows. Clock, new sends only: `latest()` within `MAX_SCHEDULE_SECS` of now (`check_local_timing`, with `check_local_timing_at` taking the clock for tests). A wall-clock time already past everywhere is not refused: it is now, like a past `visible_at`.
  - _The rows_: `fanout` writes each row's title, body, and options from the person's variant (built once per variant per batch) and its `visible_at` from their arrival, or now when it has passed. `Fanout::delivered_to` carries, per row, the instant it waits for (`None` when visible as written, and for every row of a send with one schedule).
  - _Pushes_: `deliveries_in_tx` writes a waiting row's deliveries with `next_attempt_at` set to that instant, so rounds before then read past them through the index without an attempt, and `next_round`'s existing "earliest `next_attempt_at`" read is what schedules the round for each instant. A local-time send's first round and its fanout kicks run now (`push::first_round`), not at a `visible_at`. Nothing else in the round engine changed: the attempt already re-checks the row's own `visible_at`, cancellation, expiry, and its 24-hour window from the row's own `visible_at`.
  - _Wakes_: a row visible as it commits is woken in its transaction (recipients send and fanout batch alike). Each distinct instant still ahead gets one `wake_local(send_key, after, through, at)`: per recipients send (keyed `wake:{key}:at:{secs}`), and per fanout batch (keyed `wake:{key}:batch:{last}:at:{secs}`). The job reads its range's rows, at most a batch a page, and wakes the ones whose `visible_at` is inside that second. So wake jobs grow with batches times the zones in a batch (about 38 offsets exist), wake writes with the audience, and each person is woken once at their own time. A local-time send has no send-level `visible` wake; its `expires` wake is unchanged.
  - _Cancel_: one rule, `service::cancel`, with no schema: once a complete send has a visible, uncancelled notification row, a cancel can stop only what is still ahead (rows with `visible_at > now`, and data rows). With something ahead it cancels exactly those and answers the count; with nothing ahead it answers `0` when earlier-cancelled rows exist (a repeat) and the old conflict when none do. Every row of a one-schedule send turns visible together, so this is the old behaviour for them. More than a batch ahead on a fanout send goes to `cancel_hidden_rows(send_key, hidden_after)`, which cancels rows not visible at `hidden_after`; the send's state stays `complete`, so a round already coming may push a row whose time arrives before the job reaches it (documented in the guide). A stopped row's queued delivery ends `cancelled` at its instant, as a cancelled scheduled send's always did.
  - _Dry run, status, test sends, retention_: `validate_only` runs every check, including the default zone, and counts the audience; it resolves nothing. `send_status` counts rows written, visible or not. `send_test` pushes the variant the person would read (`TestTargets` reads their locale by the same rule) and ignores `local_time`. Retention already counts from each row's own `visible_at`, so a waiting row is never too old before its time.
  - _`seen_at`_: `register` stamps it on enrollment, on a credential rotation or reactivation, on a details change, and on an unchanged re-enrollment when the stamp is older than `SEEN_EVERY_SECS` (an hour), so a browser's launch-time renewal is usually still no write. Native clients send a registration only when the token or details changed, so for them "seen" is "last told the service something new", which is the signal a time zone or language change needs.
- **The person registry is who "everyone" means.** `audience_members` holds one row per person the service knows, and a person becomes known through an act, never by being named in a send: the app's server setting their attributes (`set_person_attributes`, app-only, idempotent, ≤1,000 people per call, ≤50 attributes each with cap-skipping counted per person and key), a topic subscription (batch or self), a category preference, or a push enrollment. Each registering call upserts the registry row in the same transaction; the `persons_and_segments` migration backfilled the registry from those three tables. `forget_person` (app-only, idempotent) erases everything the service holds about the person — see "Ownership, erasure, and what a caller can grow" below. There is no tombstone: a forgotten person is known again only through a new act, and a renewal of an enrollment the service no longer holds is not one. Attributes are read back only by the app (`person_attributes`); a person has no operation over them, their own or anyone else's.
- **A condition's fanout walks the index its anchor names.** `Condition::topic_anchored` evaluates the tree three-valued — topics false, attributes unknown (Kleene): a condition that is _definitely_ false for a person holding none of its topics, whatever their attributes, can only match subscribers of the topics it names, so its fanout walks `topic_subscriptions` exactly as before. Anything else — an attribute-anchored condition like `user.plan == 'pro'`, which can match a person holding no topics — walks the `audience_members` registry, as does `SendTarget::Everyone`, which matches every registered person with no condition at all. Both walks are the same job, batches, cursor, and fences; `evaluate` loads only the topics and attribute keys the condition names.
- **The fanout job is durable, batched, and idempotent.** `send` with a topic, condition, or everyone target writes the `sends` row (intent hash, stored target and spec, state `fanning_out`) and enqueues `fanout_send` step 0 in the same transaction, then answers `fanning_out` with zero counts. Each step reads the candidates — the walk's people, ordered by person id, after the stored cursor, 500 at a time — evaluates the condition per person, and commits one transaction that first claims the batch: it moves the cursor from the value the step read to the batch's last person, fenced on that value and on `state = 'fanning_out'`, and the step writes nothing when the claim matches no row. Then the batch's inbox rows (through the same `fanout` code path a recipients send uses, opt-outs included), their push deliveries, and the counts. A cancel that lands between steps, a replayed step whose batch already committed, and two runs of one step at once all lose the claim; the loser re-reads the cursor and enqueues the step for it under that cursor's key, so a step whose winner crashed before enqueuing its successor can't leave the send fanning out forever. Replay safety is still a database constraint too — `notifications` is unique per `(send_key, person)` — and a step that finds people already holding rows skips them and moves no count. A batch whose rows are visible as it commits writes its own people's wakes in the same transaction; one that commits while the send is still scheduled enqueues `wake_batch` for exactly its people at `visible_at`. Either way a batch wakes only its own people, so a send's wake writes grow with its audience, not its square; the send's own `visible` and `expires` wakes still cover the whole send. The wake is needed because a batch's insert alone can't reach an open subscription: a live read's `visible_at <= now` was taken with an earlier `now` (§3), and the wake is the clock event. The audience is snapshotted as the fanout reaches each person.
- **Cancel mid-fanout:** `cancel` on a fanning send marks the send cancelled and cancels every row written so far — visible or not, because an audience this large can't wait for the schedule to turn — and the next step writes nothing, and the push rounds skip the send's queued deliveries as cancelled. `cancel` is set-based: existence, the visible-row rule, and the update are one statement each, no row is read into memory, and a topic/condition/everyone send with more than `FANOUT_BATCH` rows left hands them to the `cancel_rows` job, which cancels them a batch per write; the mutation answers how many it stops, and asked again before the job is through, how many are left. A complete send keeps the original rule: refuse once any row is visible and uncancelled; a known zero-fanout send answers `0` idempotently rather than `404`.
- **`validate_only` is a pure question.** It runs the full shape and timing checks, walks the audience the way the fanout will (pages of candidates, condition evaluated, nothing written), and answers the same counts shape with the audience as it stands now: targeted, minus the category's opt-outs, delivered. Every target answers it — recipients, topic, condition, and everyone. The walk is an internal query the `send` action runs, so it holds no transaction: on SQLite a mutation's transaction is `BEGIN IMMEDIATE`, and a walk inside one held every write in the service for its whole length.
- **What is stored is bounded where it is checked.** `check_spec` refuses a spec longer than `MAX_SPEC_LEN` (8,192) as stored JSON and `check_options` options longer than `MAX_OPTIONS_LEN` (4,096), the `sends.spec` and `notifications.options` columns; `check_send_shape` refuses a topic/condition/everyone target longer than `MAX_TARGET_LEN` (1,200), the `sends.target` column — a condition's quoted values grow when escaped. Each field's own bound passes more than the column holds together (about 5.7 KB of options; `data` that doubles once escaped inside the spec), and a fanout send that failed only at a step's insert was accepted as `fanning_out` and stuck there. The checks run on every target and under `validate_only`. A `visible_at` in the past is stored as the time the row is written, so the inbox and the push's 24-hour window agree on when it became visible.
- **Push rounds are bounded and chained.** One `push_send` round attempts due deliveries a page of `DELIVERY_CONCURRENCY` at a time, after an id cursor, until none is due or it has made 1,000 attempts or spent a minute starting them, then enqueues its successor: at once (keyed by this run's job id and attempt) when it stopped short; at the earliest `next_attempt_at` otherwise (one ordered `LIMIT 1` query, never a load of the queue); and every few seconds while the send still fans out, so later batches' deliveries are found. Those successors are keyed by the whole second they run at, at least a second ahead (`push:{key}:at:{second}`), so two chains of rounds that meet become one and no key names a round that already ran. A fanout kicks the rounds once (`push:{key}:fanout`) and once more as it completes (`push:{key}:final`), when anything is queued. One delivery that fails inside the service — a database error, a panic, a notification row gone before the outcome's write — is put off a minute (or, for the gone row, ended as cancelled) on its own row, never failing the round.
- **Visibility is a SQL predicate; arrival is a wake.** `visible` is `visible_at <= now AND cancelled_at IS NULL AND (expires_at IS NULL OR expires_at > now)`, plus the reader's opted-out categories — but a recorded live read set is judged against the condition it was read with, and its `now` is a constant of that run: a row inserted after the read (scheduled or not) can't match `visible_at <= then`, and no commit happens at all when an expiry's time simply passes. So the service owns the clock event: every send enqueues a `wake_send` job when it becomes visible (now for an immediate send, `visible_at` for a scheduled one) and another at its `expires_at`, in the send's transaction. The job writes one `wakes` row per person the send reached — `inbox` and `unread_count` read the reader's wake row and ignore its value, which puts `wakes` in their read set — and each of their open subscriptions re-runs with a fresh `now`. A wake that changes nothing (cancelled send, dismissed row) re-runs the query and sends nothing, because the result didn't change. The jobs are the framework's own (`rpc_jobs`, claim, lease, retry): no new scheduler, no polling daemon; the workers are started by the service's binary (`service::workers`) beside its routes and poll every second, so a scheduled item lands close to its time.
- **Cancel-before-due:** `cancel` refuses once any row of the send is visible and uncancelled; a fully cancelled send answers `0` whenever it's asked again. Existence is the `sends` row, not the fanout: a send every recipient opted out of has no rows, and cancelling it answers `0` idempotently rather than `404`.
- **Preferences bind at both ends:** the send skips opted-out recipients (counted in `skipped_opted_out`), and the inbox hides rows in categories the reader opted out of since, so an opt-out covers history too. The table is `live`, so the preference write itself re-runs the setter's open inbox, badge, and preferences subscriptions. A raced insert (two devices, one new category) fails the unique key and the mutation runs again, so the last setting to commit is the one that holds — no answer is swallowed. At most `MAX_PREFERENCES` (100) rows per person, so the visibility filter stays a bounded `ne` chain.
- **Row ids are UUID v7**, assigned by the service, so `ORDER BY id DESC` is arrival order and a stable pagination cursor; `notifications` is indexed `(person, id)` for exactly that query. Inbox pages clamp to `MAX_INBOX_PAGE` (100) before the framework's own 1,000-row clamp.
- **Retention: an hourly job deletes what is over.** `service::retention`, configured by `service::config::Retention` from `LEPTOSKIT_NOTIFICATIONS_RETENTION_{INBOX,ENDED,DELIVERIES,SENDS}_DAYS` (whole days, or `off`; defaults 365, 30, 30, 90; a bad value refuses to start; `main.rs` prints what it read). The `prune` cron job (`17 * * * *`, queue `prune`) starts a sweep and works for `STEP_BUDGET` (20 s); a step that runs out enqueues `prune_rows(sweep, stage, after)` under a key made of all three, and a sweep older than 55 minutes stops, so sweeps never pile up. A sweep walks the primary key below a UUID v7 bound made from the cutoff, 500 rows a page (100 for `sends`), each page checked with plain reads and deleted in one short write — every condition it checks only ever moves one way, so there is nothing to race.
  - _Notifications_: gone `ended_days` after `expires_at` or `cancelled_at` (a cancelled row never before `ended_days` after its `visible_at`, because its wake job waits until then under the send's key), a `data` row `ended_days` after `visible_at` plus the delivery horizon, any other row `inbox_days` after `visible_at`. Their deliveries go in the same write.
  - _Deliveries_: finished ones, `deliveries_days` after `finished_at`.
  - _Send records_: `sends_days` after `created_at`, and only when no notification and no delivery still names the key.
  - _Never_: a notification with a queued delivery or whose send is `fanning_out`; a queued delivery; a `fanning_out` send record.
  - _The idempotency window_ is therefore at least `sends_days`, and as long as any row of the send remains; after that the key is a new send. `sends_days` has a floor of 2: the service's workers keep a finished job's key for 24 hours, and a send's jobs are keyed by its key. A key reused after its record went but while one of those job keys is still held is refused with `Contended` (409) rather than sent again — `tests/scale.rs` pins that.
  - A recipients send stores no target and no spec, so its record names nobody. A fanout send's record stores its target and spec; a condition can carry personal values, and they go when the record does.
- **The push queue is read through `(send_key, state, id)`.** A round's page of due deliveries is two reads, one per queued state, merged by id (`service::push::due_page`), because one read over both states is planned through `(send_key, id)` on SQLite and the primary key on Postgres, and walks the send's finished rows. A state whose read came back short and inside the page is not read again that round. Not fixed: a send's retries that are not yet due are still read past once per round; `(send_key, state, next_attempt_at)` would only shorten that, and was left out.
- **A condition over several topics is one read per topic.** `service::candidates` reads each topic's next page from `(topic, person)` and merges the pages in a sorted set, taking the first `limit`. A person past the limit in one topic is past it in the merge too, so the cursor never skips anyone.
- **Live:** `notifications`, `category_preferences`, and `wakes` are `live` tables. Sends, reads, dismissals, opt-outs, schedules turning due, and expiries all reach watching screens.

## 5. What an app that uses this must set

- `[services.notifications]` with `crate = "leptoskit_notifications"` (or a workspace `package`) and `trust = "first-party"` — a workspace `package` defaults first-party, but a registry `crate` defaults `isolated`, which forwards no identity; the guide's first snippet says it explicitly. `forward_identity` then defaults on.
- The app's server serves `rpc::server::Server` with its sign-in `Identify` (the scaffold's shape) so forwarded-identity tokens can be minted.
- Sending needs the service's token on the server side, which `leptoskit dev`/`serve` and deploys provide as `LEPTOSKIT_SERVICE_NOTIFICATIONS_TOKEN`.

## 6. Performance envelope

SQLite in the service's own file handles the target load — badge polls are one indexed count, inbox pages are one indexed range read per page, sends are one transaction with up to 1,000 small inserts. Postgres is the same code with the other dialect. `tests/scale.rs` asks each engine for the plan of the reads that grew with the tables — the endpoint updates, the push round's page, the unread count, the multi-topic walk — over a few thousand seeded rows and fails when one stops using its index. The typed queries are mirrored there as SQL, because the database crate renders them privately: change one and its mirror changes with it.

Migrations run at startup, each in one transaction, so `CREATE INDEX CONCURRENTLY` is not available to them. What to expect on a large database: on SQLite, `topics_and_fanout` copies `sends` and `message_options` copies `notifications` (the service is down for the copy), and `scale_indexes` builds three indexes in the write transaction. `endpoint_seen` adds one nullable column on both engines, with no rewrite and no backfill. On Postgres, `topics_and_fanout` builds a unique index on `notifications` and rewrites `sends`, `message_options` validates a `CHECK` over `notifications` under `ACCESS EXCLUSIVE`, and `scale_indexes` builds its indexes under `SHARE` locks (writes wait, reads go on) — or finds them already built by hand with `CREATE INDEX CONCURRENTLY`, since it uses `IF NOT EXISTS`. The public guide's "Upgrading a large database" says the same to operators.

`send_history` adds two nullable columns to `sends` (no rewrite, no backfill) and five indexes: two on `sends`, and one each on `person_attributes (key, value)`, `category_preferences (category, opted_out)` and `push_endpoints (platform, invalidated_at, person)`. On SQLite they are built in the migration's write transaction. On Postgres they are built under `SHARE` locks, or found already built with `CREATE INDEX CONCURRENTLY`, since the migration uses `IF NOT EXISTS`. Each adds one index write to the writes of its table: a send, an attribute set, a preference change, an enrollment.

`tests/scale.rs` (`the_composers_reads_use_their_indexes`) checks the plans of the reads this added on both engines: the send list's page, a category's latest send, a report's push breakdown and reads by hour, the four walks of distinct names, and the capped counts. One known softness: for a count that matches half of a small table (a 1,500-subscriber topic in a 5,000-row table, the people with a live endpoint on a platform) Postgres chooses a sequential scan at this corpus size. The test then asserts only that the plan stops at its `Limit`. The distinct count of people per platform is a `HashAggregate` under that limit in the test corpus, so on Postgres it is not proven to be bounded by the cap on a large table; the overview is the one catalogue read whose Postgres cost is not pinned.

Nothing here is measured against a production-sized corpus yet; before claiming large-fanout numbers, run the load harness the analytics service has.

## 7. Non-goals

- **No push vendor in between.** The first slice had no OS push at all. The transports (APNs, FCM, Web Push), the device registry and stored credentials have since been built into this crate (section 8), and the non-goal that remains is a third-party management vendor.
- **No management screens in this crate**, and no generic "transport" trait with speculative backends. The service answers what a compose screen needs (send history, the audience catalogue, push previews; see "Send history, audience catalogue and push previews") as app-only operations; the screens themselves belong to the admin app and are built there.
- **No generic scheduler or polling daemon.** The wake jobs are lifecycle-managed rows in the framework's own `rpc_jobs` table — enqueued in the send's transaction, run once by the service's workers, pruned with them — not a service-owned loop. This revises the first slice's "no daemon" note: time-based arrival on an open subscription turned out to need the wake (§3), and this is the smallest mechanism that provides it on the framework's existing jobs and live invalidation.

## 9. What follows

The server side of push is built: `crates/leptoskit_notifications`'s `push` module holds the typed credentials and enrollment operations, `service::push` the delivery engine (per-instance configuration carried by the routes and named in the jobs — a process may serve several services without sharing credentials), and `service::transport` the APNs, FCM, and Web Push senders behind an injected HTTP boundary, with the shipped-provider host policy for Web Push. All three transports run on ring's constant-time primitives directly: Web Push's RFC 8291 encryption and RFC 8292 VAPID beside the FCM service-account assertion (RS256, as Google's OAuth requires) and APNs's ES256 provider token — the `web-push` crate left when its `jwt-simple`/`ece` chain carried the `rsa` and `crypto-bigint` advisories. The client halves are built too: the `native` module turns the platform's token into enrollment on iOS, macOS, and Android, and the `browser` module serves the receiver worker and enrolls the browser's subscription. Message options are built over all three transports, and the `send_test` probe with them. What follows on the audience side: localization (translated title and body per `device.locale`) and recipient-local-time scheduling (per `device.time_zone`, which then needs a time zone database on the server — treat a name it doesn't know as absent), and analytics. Device details exist now; `device.platform` names the push service, so `'apns'` cannot tell iOS from macOS — an OS detail from the hosts would be the way to add that. The Android host's `encodeSnapshot` wrote its integers big-endian while the bridge codec reads little-endian (the instrumentation test decoded little-endian and would have caught it on an emulator); the device slice fixed it alongside the new `DEVICE` reply. Windows toasts wait on the plugin's backend; Windows and Linux enrollment has no story yet.

Two framework contracts are worth naming for later work. First, a job's context is rebuilt from its owner alone, so a service cannot carry per-instance state to its job bodies through the context: the push job names its instance key in its arguments and looks it up in the service's own registry. A `Jobs::new(db).state::<G>(…)`-shaped hook in `leptoskit_rpc` — or service-scoped job state — would remove that registry. Second, `#[rpc::job]` registration is a stateless `fn`, so the same conclusion holds for any transport-like dependency a job needs.

## Endpoint ownership and credential generations

**APNs environment.** A device token is known to one of Apple's two servers. The iOS and macOS hosts answer plugin method 11 (`APS_ENVIRONMENT`; `ApsEnvironment::current` in `NotificationsPlugin.swift` reads the embedded provisioning profile, with the simulator as development and a profile-less iOS build as production), `native::device_details` maps it with `native::apns_environment_from` into `DeviceDetails::apns_environment`, and `register` and `import` store it in `push_endpoints.apns_environment` (`sandbox`, `production`, or null) after `DeviceDetails::for_platform` drops it for a non-APNs credential. Every transport takes a `transport::Target` (credential plus that environment); only `apns.rs` reads it, and `host(target.apns_environment.unwrap_or(self.environment))` picks the server, so `APNS_ENVIRONMENT` is the default. It is part of the native details digest only when present, so an enrollment saved before it existed is not re-sent by a host that does not report it. Each re-enrollment replaces it, including with null. Conditions do not read it. The Swift side is not compiled in this repository's gates.

**Imports.** `import_push_endpoints` (app-only, `service::push::import`) inserts endpoints for tokens the app's server already holds, marked with `push_endpoints.imported_at` and with `seen_at` null. It is the one way an endpoint exists without its device presenting the credential, so it never takes a destination over (another holder: skipped) and never touches a row that exists (same holder: unchanged, invalidated or not). `register` clears `imported_at` on the same person's first enrollment of that credential, as a details update that keeps the generation. There is no tombstone for a revoke or an erasure, so a re-import after either enrolls the token again; the guide tells the caller to import once from current records.

Endpoint ids never change owner. Provider invalidation preserves ownership; a destination is released by revocation — the owner's, the app's (`revoke_person_endpoints`, `forget_person`), or a takeover, which revokes the old row and inserts a fresh one (below). New enrollment after revocation creates a fresh id. A person keeps at most `MAX_ENDPOINT_HISTORY` (10) invalidated rows: each new enrollment deletes the oldest beyond that (`trim_history`). Every insert and reactivation checks the live endpoint cap in the RPC mutation’s serializable transaction. Live idempotent enrollment succeeds at the cap.

Endpoints and deliveries carry a monotonic credential generation. Same-owner rotation or reactivation advances the endpoint and its queued deliveries together. Before HTTP, the attempt checks endpoint, delivery, and notification ownership. After HTTP, a short transaction locks the exact endpoint generation and fences outcome writes on delivery generation, queue state, and attempt count. Terminal states remain terminal. No database transaction spans HTTP. Held-response tests cover acceptance, transient failure, and unregistration across rotation and reactivation on SQLite and ephemeral Postgres.

Native registration and the browser receiver were separate work when this was written; both are built now (see "Client hosts" and "Receiving on the device").

Delivery retries stop at eight actual push requests, including requests refused for authentication. On every platform the engine waits one minute after the first, doubling after each (1, 2, 4 … 64 minutes, about two hours in all, so an hour's provider outage loses nothing), plus up to a quarter more of jitter hashed from the delivery's whole id and its attempt count, so deliveries minted together don't retry together. A provider's `Retry-After` is honored when it is longer than that wait, and never shortens it. OAuth token exchanges are separate and do not spend push attempts. FCM refreshes once after a 401; the next push goes through the durable queue and its attempt budget. An exchange failure retries every minute with sanitized `operator_configuration` status. Neither provider diagnostics nor credentials appear in that status.

Every delivery has a deadline: the earliest of notification expiry, the end of the send's `options.push_ttl` (counted from `visible_at`; `transport::push_expiry`), and 24 hours after `visible_at`, including notifications with no expiry. A `push_ttl` of zero gets one attempt whenever the queue reaches it (`only_attempt` in `service::push::attempt`) and is never retried. Provider `Retry-After` accepts delta seconds and HTTP dates; invalid values use backoff. A provider delay is never shortened into an earlier push. If it exceeds the deadline, the queue wakes at the deadline and ends delivery (`expired` or `horizon_exceeded`) without another request. Unrepresentable arithmetic ends with `retry_overflow`. Local schedule, cancellation, expiry, and horizon decisions do not spend attempts. See [FCM error codes](https://firebase.google.com/docs/cloud-messaging/error-codes).

## Ownership, erasure, and what a caller can grow

- **Takeover is for the byte-identical credential, on an explicit enrollment.** `service::push::register` finds the row by destination. When it belongs to someone else and the presented credential equals the stored canonical one (for Web Push that includes both keys, so holding it proves holding the device's subscription), the old row is revoked — deleted, its queued deliveries ended `skipped`/`endpoint_revoked` — and a fresh endpoint is inserted for the caller under the usual live cap. A different credential for the same destination is still a `409`. It happens whether or not the old row was invalidated.
- **A renewal stands on the enrollment it names.** `register_push_endpoint` takes `renews: Option<Uuid>` (absent on the wire when none, so older clients parse and are parsed). With it, the call succeeds only while that endpoint is still the caller's (a rotated token or subscription then enrolls under it as before); otherwise it answers not-found with a message starting `ENROLLMENT_GONE`, which `push::enrollment_gone` recognizes, and writes nothing — no row, no takeover, no registry entry. Both `reconcile`s send it; only a gesture's `enroll` omits it. That is what makes a server-side revoke stick.
- **`reconcile` drops what the server dropped.** Native: a launch whose token and details are unchanged asks `push_endpoint_standing(endpoint)` (one row by id, the person from the forwarded identity) and answers `Outcome::Gone` on `false`; an unanswered check keeps the enrollment. A changed launch registers with `renews` and answers `Gone` on the gone answer. Browser: `reconcile(options, previous)` registers nothing without a saved enrollment and answers `None` when its renewal is gone. Rotation's ownership check uses the same query, so it no longer depends on the first page of `push_endpoints`.
- **Same-person re-enrollment registers nobody.** Only a row insert calls `register_persons`. Together with `renews`, a forgotten person's old client cannot put them back in `audience_members`; a new gesture enrollment, a preference, or a self-subscription can, and should.
- **`forget_person` erases.** In the mutation's transaction: attributes, topic subscriptions, category preferences, the registry row, the wake row, every endpoint (`push::revoke_all`, deliveries ended as revoked), and one `FANOUT_BATCH` of inbox rows with their deliveries. If rows remain it enqueues the `forget_rows` job (`serialize_by` the person), which deletes a batch per step up to `through` — the UUID v7 cutoff taken at the call, so a notification sent after the call survives. Calling it again is safe. Send records (`sends`) name no recipient: a recipients send stores no target or spec, and a fanout send stores its topic or condition. They are kept until retention deletes them (section 3).
- **Bounds on what one caller can make the service hold or read.** Pinned (`until`) pages go through `service::paginate_bounded`: inbox `MAX_PINNED_INBOX_ROWS` (500), endpoints 20, topics 500 — `rpc::paginate`'s own pinned cap is 10,000 rows and ignores `limit`. `set_person_attributes` refuses a call naming more than `MAX_ATTRIBUTE_CHANGES` (100) keys for one person across `set` and `remove`. The condition parser counts nesting (`MAX_CONDITION_NESTING`, 32) on `(` and `!` before it recurses, so depth is no longer bounded only by the 1 KiB length.
- **Condition values.** A value is everything between its quotes; `''` inside one is a single quote; a backslash is an ordinary character; control characters are refused. `condition::quoted` writes a literal from any string. Topic names cannot contain a quote, so every condition FCM accepts parses as before.

`tests/support/ownership.rs` holds these checks once and `tests/ownership.rs` (SQLite) and `tests/postgres.rs` run them on both engines.

## Client hosts

Added 18 November 2026, from the push-clients review ([`notifications-handoff/reviews/clients.md`](notifications-handoff/reviews/clients.md), findings 2, 3, 6 to 9, 12 and 13). What a push-enabled host needs beyond a token, and how far each piece is proven.

- **Gradle.** The scaffold's script applies each id in `.leptoskit/android/gradle-plugins.txt` with `apply(plugin = plugin)`. The positional form is `apply(from = …)`, a script path. `validate_android_push` refuses an app script that still has the positional loop and names the change, since the script is app-owned and never rewritten. Proven by text only: no Gradle runs in the Rust tests, and CI's Android job builds no push-enabled app, because that needs a `google-services.json`.
- **Messaging service.** `ServiceComponent` carries intent-filter actions, and the generated `LeptosKitMessagingService` is declared with `com.google.firebase.MESSAGING_EVENT`. It overrides `onNewToken` and, since the receiving work (below), `onMessageReceived`.
- **Default channel and icon.** The manifest gets `default_notification_channel_id` = `leptoskit.notifications.default` whenever push is on, and `default_notification_icon` = `@drawable/ic_notification` only when `[app.icons] notification` generated that drawable, because naming a missing resource stops the build; without it generation warns. The plugin creates the default channel in its constructor when the manifest names one under its own prefix and none exists, and never touches an existing one. A device therefore has the channel from the first launch, which is before any enrollment.
- **Raw channel ids.** `android.raw_channel_id` is sent without the prefix, for channels an app created itself before it used the plugin; it and `channel_id` are mutually exclusive (`check_options`). The Android foreground post reads the channel from the message, so it follows either.
- **Collapse.** `Message::collapse_key()` is the send's `options.collapse_key` or the notification's id. FCM also gets it as `android.notification.tag` when the send names no tag (`collapse_tag`), kept through the first trim and in the minimal envelope; Web Push carries it as `lktag`, which the worker uses as the banner's tag. The Android foreground post still tags by notification id.
- **Channel ids.** The plugin creates channels as `leptoskit.notifications.<id>`. The FCM transport adds that prefix to `android.channel_id` (`android_channel` in `transport/fcm.rs`), and passes an id that already carries it unchanged. The alternative was to send the raw id and document the full name; that left the guide's own example landing in Firebase's fallback channel and did not fit the 64-byte limit on `channel_id` for longer plugin ids. The cost is that a channel created outside the plugin is reachable only if it is named under the prefix. An app migrating from Firebase with existing channel ids needs a raw-id option; none exists yet.
- **Keep rules and reflection.** Push-enabled builds append `templates/push-proguard-rules.pro` to the bridge's rules: `FirebaseMessaging.getInstance`/`getToken`, `Task.addOnSuccessListener`/`addOnFailureListener`, and the two listener interfaces. The registrar now resolves the listener methods on the public `Task` class instead of the returned task's own class, whose visibility is the SDK's business. `registrationFailure` unwraps `InvocationTargetException` before choosing the code. Whether Firebase's own consumer rules already keep these names was not checked, and no minified build with Firebase runs anywhere, so the rules are reasoned, not exercised. A generated static registrar, compiled against the SDK, would remove the reflection and the rules together; it was not done because nothing here can compile it.
- **Apple permission.** `requestAuthorization` asks for `[.alert, .badge, .sound]`. The plugin's own posts still set no sound and no badge.
- **macOS provisioning.** `com.apple.developer.aps-environment` is a restricted entitlement, so a push-enabled Mac app needs a real signature and an embedded profile. `[native.macos] provisioning-profile` (a path under the project) is required when `aps-environment` is set: `desktop::generate` and `publish` both stop without it. `desktop::build` embeds it at `Contents/embedded.provisionprofile`, signs with the identity in `LEPTOSKIT_MACOS_IDENTITY`, and refuses to ad-hoc sign; `--release --unsigned` signs ad-hoc without the entitlement. `leptoskit publish macos` builds that way and embeds the profile in its copy before signing with the Developer ID identity. One `aps-environment` and one profile serve both paths, so switching from local work to a distribution means changing both lines; separate publish settings would remove that. The profile's contents are not read, so a profile for another bundle id or environment is found only at launch. **None of this has run on a Mac with an Apple developer account**: the tests cover the decisions, the arguments and the file placement, not `codesign`, Gatekeeper, or a launch.
- **Web receiver.** The worker calls `clients.claim()` on `activate`, and a click reads `event.action` and adds it to the opened URL as `lka`. Messaging the page, acknowledgement, and `lkn` on a link target are described under receiving, below.
- **Kotlin tests in CI.** The review says the plugin's instrumentation tests never run. They do: `NotificationsPluginTest.kt` is in `ANDROID_TESTS` in `crates/leptoskit_cli/examples/native_plugin_suite.rs`, which the `android` job copies into the generated app before `connectedDebugAndroidTest`. That fixture has no Firebase, so the tests cover the plugin with an injected registrar, the failure mapping, and the real registrar's no-Firebase answer.

## Receiving on the device

Added 18 November 2026, from the push-clients review (findings 4 and 5) and the tap-routing work. What a device does with a push after the provider delivered it, and how app code hears about it.

- **One contract, three hosts.** The plugin has one new method, `RECEIVED` (10). The request is a wait in milliseconds, capped at 10,000. The reply is a batch of at most sixteen items, each a kind (0 tapped, 1 shown while open, 2 handed over without a tap), the pressed action's id, the local notification's id, and the provider's payload as JSON text (at most 8 KiB; larger is handed over empty rather than cut). Hosts interpret nothing. `leptoskit_notifications::receive::from_host` reads `lkn`, `lklink`, `lk`, and `lkbadge` on Apple payloads and the flat FCM data map on Android, where the envelope's keys and Firebase's reserved ones are taken out of `data`. This keeps the logic where it can be tested here: the Swift and Kotlin sides are a lock, a list, and an encoder.
- **Process-wide broker.** Like remote registration, the items live in a static, because a tap that starts the app arrives before the plugin and its guest exist. It keeps the latest sixteen and is emptied by each read. It is memory only: a process the system ends loses what it held.
- **Launch.** `native::Receiver` never waits on its first ask, so what that ask answers is exactly what arrived before the app asked; those taps are marked `launched`. This is a definition by timing, not by the system's launch options. A tap that lands in the first moments after the process starts, before the guest's first ask, is marked `launched` too; that is the wanted reading, since the app has drawn nothing yet. A second `Receiver` in the same process sees no launch tap.
- **Long poll.** `next` asks with the full ten-second wait in a loop. The Swift host sleeps in slices of 100 ms and checks the broker and cancellation; the Kotlin host does the same with `delay`. A continuation woken by the broker would be more exact; the slice was chosen because it needs no cross-thread resumption and so is easier to get right without a compiler.
- **Apple delegate.** `NotificationCenterDelegate.shared` is installed by `NotificationsPlugin.installDelegate()`, which the generated app delegates call from `willFinishLaunching`. `didFinishLaunching` is too late for the response that launched the app. `willPresent` answers `[.banner, .list, .sound, .badge]` for every notification, local or pushed. The centre has one delegate: an app that sets its own replaces this one and must forward to `ReceivedNotifications.noteResponse` and `notePresented`. Dismiss actions are ignored. Action buttons are reported when pressed, but nothing registers `UNNotificationCategory` sets, so APNs sends cannot show buttons yet.
- **Apple data messages.** `application(_:didReceiveRemoteNotification:fetchCompletionHandler:)` on iOS and `application(_:didReceiveRemoteNotification:)` on macOS call `noteRemoteNotification`. iOS generation adds the `remote-notification` background mode when `[native.ios] aps-environment` is set, and only then, so an app without push declares nothing new to App Review. The completion handler is called at once with `.newData`: the guest gets no background time beyond what the system grants the process anyway.
- **App-owned host files.** `hosts/ios/App.swift` and `hosts/macos/App.swift` are scaffolded once. Existing apps do not get the delegate lines; the guide says which to add. The menu-bar template (`MacMenuBarApp.swift`) was left alone, and the menu-bar swap still compares an app's `App.swift` with the current `MacApp.swift` template byte for byte, so an app scaffolded before this change that later turns on menu-bar mode is not swapped. That comparison was already fragile and is not changed here.
- **Android taps.** No change to `MainActivity`. A notification Firebase posts, and one this plugin posts, both open the launcher activity with the message's data as string extras. The plugin reads the activity's intent when it is constructed and on every `RECEIVED` slice, and removes its own marks (`lkn`, the local id) so one tap is read once. A push tap is recognised by `lkn` together with `google.message_id` or the plugin's own `leptoskit.notifications.open`; an intent launched from history is ignored. `MainActivity.onNewIntent` already calls `setIntent`, which is what makes a tap on a running app visible. Reading the intent avoids both a template change in an app-owned file and reflection that R8 could break.
- **Android foreground.** `onMessageReceived` calls `ReceivedNotifications.noteMessage`. A message with a title or body reaches that callback only while the app is in the foreground; the plugin posts it under the tag `leptoskit.push.<id>` in the named channel or the manifest's default one, and records it as shown. Image, color, sound, and click action from the FCM notification block are not applied to this post. A message with neither is a data message and is only recorded. Local `show()` posts now carry a content intent as well, so a tap on one opens the app and is reported with its local id.
- **Web.** The worker posts `{ lkn_event: { kind, id, link, action, data, token } }` to window clients. For a click it posts to the best client first and waits 500 ms for `{ lkn_ack: token }` from that page. An acknowledged click is done: the page changes its own route and nothing reloads. Without an answer the worker falls back to `client.navigate` or `openWindow`, as before. Link targets now carry `lkn` as well as inbox targets, so a freshly opened page can tell which notification was clicked; `browser::Receiver` reads `lkn` and `lka` from the address at startup, reports them as the launching tap, and removes them with `history.replaceState`. The 500 ms is a guess at "longer than a busy page takes to answer, shorter than a person notices"; it is one constant in `receiver.js`.
- **Web data envelope.** The service still never sends one. A push flagged `lkdata` that arrives anyway is posted to pages, and shows the generic banner unless a window client is visible. Showing nothing with no page open was the harm in finding 5: Chrome shows its own notice and Safari can revoke the permission. The badge call is now awaited inside the event's lifetime.
- **What is proven here.** Rust: the codec, the payload reader, the intake order and launch marking (unit tests), a compiled guest against a fake host through the real bridge (`notifications_guest.rs`), and the worker and page receiver in headless Chrome (`tests/browser.rs`). Generation: the messaging service's text, the background mode, and the template snapshots. **Not compiled or run here:** every Swift and Kotlin line of this section. The Swift file parses under `swift-format` and the Kotlin files pass `ktlint`; that is syntax, not types. The Swift tests run in the plugin's Apple test job and the Kotlin tests in the Android emulator job. No device has received a real push through this code.
- **Left out.** A `link` on local `show()`. Apple category registration. A delegate for the menu-bar host. Windows and Linux, which receive no push.

## Open tracking and a send's report

Added 18 November 2026, from rows 19, 29, 48 and 66 and plan item 8 of the Firebase parity review. What the service knows about a notification after a device showed it, and what it answers about a send.

- **`mark_opened`.** A person-side mutation taking a notification id, authorized through `service::own_row` exactly like `mark_read`: another person's id and an unknown id are the same not-found, and a caller who is not a forwarded person is forbidden. The first open writes `opened_at` and, when the row was unread, `read_at` with the same timestamp, in one `UPDATE` filtered on `opened_at IS NULL`. Later calls write nothing and succeed, so the operation is idempotent per row without an idempotency key. A row that was already read keeps its `read_at`. A row of kind `data` is answered with the same not-found, because a data message is never shown and has no open. No visibility check is made, as in `mark_read`: a push for a row that has since expired or been cancelled can still be tapped, and that tap is recorded.
- **Opening implies read.** Decided here: a person who tapped the push has seen the notification, so the badge on their other devices should drop without a second call. The cost is that `read` in a report includes opens; the report says so.
- **The client helper.** `receive::Opened::mark_opened` is one method for both hosts, because `leptoskit_rpc::client::call` is the same call on the guest transport and on the browser's. It answers `Ok(false)` without calling when the tap carries no notification id (a local notification, an unreadable payload). It sends a fresh idempotency key and does not retry. The receiver worker (`receiver.js`) is unchanged and still calls no server: it holds no person token, so the page records the open after the worker hands it the tap, or after it reads the launch tap from its address. No Swift or Kotlin changed.
- **Storage.** `notifications.opened_at`, a nullable timestamp, and `sends.label`, a nullable `varchar(64)`. The `open_tracking` migration adds both with no backfill. On Postgres both `ADD COLUMN`s are metadata-only and the trigger is dropped and created in the migration's own transaction, so the table is locked briefly and no write goes uncaptured; nothing is rewritten on either engine.
- **`send_report`.** An app-only query: `SendSummary { progress, label, created_at, inbox }`, where `progress` is what `send_status` answers and `inbox` is `InboxCounts { rows, read, opened, dismissed, cancelled }`. The operation is named `send_report`, as S2 of the compose-screen plan names it, so its generated request type is `SendReport` and the answer needed another name. Both answer types are `#[non_exhaustive]` and every field added later should carry `#[serde(default)]`, so the plan's remaining fields (`spec`, `target`, `push`, `reads_by_hour`) can be added without breaking a caller. `send_status` and `SendProgress` are unchanged, so a fanout poll costs what it did.
- **Cost and the index decision.** The counts are one statement, `SELECT count(*), count(read_at), count(opened_at), count(dismissed_at), count(cancelled_at) FROM notifications WHERE send_key = ?`, issued as a `Statement` because the typed builder has no conditional aggregates. It reads the send's rows through the existing unique `(send_key, person)` index and fetches each row once: work in step with the size of the send, never with the table. No index was added. An index on `(send_key, opened_at)` would make only the opened count index-only, would still leave the other three counts fetching rows, and would add a write to every fanout insert and every open on the hottest table. `tests/scale.rs` asks both engines for the plan of the service's own statement (`service::plans::send_counts`) over a 300-row send in a 12,000-row table: SQLite searches the index, Postgres does a bitmap scan of it. For a send that is a large share of the whole table Postgres may rightly choose a sequential scan. A report over a send of millions of rows reads millions of rows; if that becomes a page people open often, counters on the send's record are the next step.
- **After retention.** Counts are of rows still stored. Pruned rows are counted nowhere, so a report's `inbox` shrinks to zeroes while `progress` (kept on the `sends` row) stays. Once the `sends` row is pruned, `send_report` answers not-found. Counters that survive pruning were considered and left out: every open would then update the one `sends` row of its send, which serializes the opens of a large send on a single row.
- **Label.** `SendSpec::label`, 1 to 64 ASCII letters, digits, `-`, `_` and `.`, checked by `check_label` inside `check_spec`. It serializes to nothing when unset, so the intent hash of every earlier send is unchanged, and it is part of the hash when set. It is copied to `sends.label` for every kind of send, because a recipients send stores no spec. It is never written to a notification row or a push payload.
- **What is proven here.** `tests/opens.rs` (SQLite) and the `_on_postgres` twins in `tests/postgres.rs` share `tests/support/opens.rs`: first open wins and marks read, an earlier read time is kept, authorization equals `mark_read`'s answer for answer, a data row has no open, the report's counts and who may read it, the counts after pruning, the label's validation, storage and intent, and the migration applied over existing rows. The guest probe's scenario 13 and `tests/browser.rs` run the helper through the real guest and browser transports against a played service.
- **Left out.** A list of sends (`list_sends`), the report's push breakdown and reads by hour, and the stored spec and target in the report: task I. Opens per platform or per device: the open is stored per person's row, with no device. Conversions and funnels: the analytics module.

## Send history, audience catalogue and push previews

Added 18 November 2026, as S1 to S4 of the compose-screen plan (`notifications-handoff/reviews/compose-screen-plan.md`). What the service answers so that a screen can list sends, build an audience, and show a push before it goes. All of it is app-only, read-only, and bounded. No screen is part of this.

- **Conditions render to text (S1).** `impl Display for Condition` writes one canonical spelling: single spaces around binary operators, parentheses only where precedence or grouping needs them, `!(…)` always parenthesized, values through `quoted`, and a number in exponent form only when its plain form is longer than 24 characters. The parser builds `&&` and `||` chains to the left, so a right operand that is the same operator is parenthesized; without that the round trip changes the tree (three tests fail when the rule is removed). The plan's `targetable` flag on attribute values is not built: every value `check_attribute_value` accepts, the empty value included, has a literal, and a test walks the boundary cases.
- **The history's order (S2).** `sends.history_id` is a UUID v7 assigned when the send is written, nullable, indexed alone. The plan proposed a block of denormalized columns on `sends`; this keeps `sends` as it was and stores the spec for every kind of send instead, so the list reads the title, kind and schedule from the spec it already holds. `sends.category` is the one denormalized column, because `categories` needs the latest send per category as an index seek (`(category, history_id)`). Paging on `created_at` was rejected: two sends in one millisecond would share a cursor.
- **A recipients send now stores its spec.** It stored none before. Its `target` column stays `NULL`, which is still how `answer_send` tells a recipients send from a fanout, so a retry answers exactly as before (`a_retried_recipients_send_still_answers_correctly`). The recipient list is not stored: `TargetSummary::recipients` is the send's `targeted` count.
- **Older sends.** No backfill. A send from before the migration has no `history_id`, is not listed, and still has a report, with `spec: None` when it stored none.
- **Names.** The operation is `list_sends`, not the plan's `sends`, because the generated request type `Sends` would sit beside the `AppSend` table named `sends`. A list item is `SendEntry` because `SendSummary` is already the report.
- **The report's additions.** `SendSummary` gained `spec`, `target`, `push` and `reads_by_hour` and lost its `Eq` derive (`SendSpec` is not `Eq`). `push` is one `GROUP BY platform, state, reason` over the send's deliveries through an index that leads with `send_key`. `reads_by_hour` groups the send's read rows by UTC hour through `(send_key, person)` and stops at `MAX_REPORT_HOURS` (168). Both read the send's own rows, like the inbox counts.
- **The catalogue's lists (S3).** Distinct names come from a recursive CTE that does one index seek per name (a loose index scan), so listing 50 topics costs 50 seeks whatever the table holds. `categories` takes the smaller of two seeks per step, one in `sends` and one in `category_preferences`, inside the same statement, so the merged list has the database's own order and a cursor cannot skip a name. The plan's `limit`/`more` shape for `attribute_values` and `categories` is replaced by `rpc::PageArgs`/`rpc::Page` like every other list.
- **Prefix search and collation.** On SQLite text is ordered by bytes, so a prefix is a seek to it and a stop at the first name that doesn't start with it. On Postgres the order is the database's collation, where names sharing a prefix need not be adjacent. There the walk is not seeked: it examines up to `PREFIX_SCAN` (500) names per call and filters them in Rust, and may answer a short page with `has_more`.
- **Capped counts.** `SELECT count(*) FROM (SELECT 1 … LIMIT cap + 1)`, answered as `Count { count, exact }`. `COUNT_CAP` is 100,000; the overview uses 1,000,000 for people and 1,000 for topics.
- **`estimate_audience`.** It runs the fanout's own candidate walk and `evaluate` for at most `ESTIMATE_WALK` (5,000) candidates, holding no transaction. Below that it is exact and equals a dry run. Above it, it answers what it walked with `exact: false`. `reach` counts people who would be delivered to and hold a live endpoint the condition admits, per platform; invalidated endpoints are not counted. `category` is optional: without it nobody is counted as opted out.
- **`person_endpoints`.** The person's own `push_endpoints` list (`EndpointSummary`), readable by the app for any person. No credential, fingerprint or generation is in it.
- **Preview (S4).** Each transport's request building moved into a `shape` function that answers `Shaped { headers, body, bytes, limit, trims, fits }`, and `attempt` now sends what `shape` answers. `preview_push` calls the same three functions, so there is no second encoder to drift. Stand-ins: the notification id (nil unless sampled), the FCM token (`<device token>`), the unread count behind an unread badge (1 unless sampled). The authorization header and `apns-topic` are left out, and no credential or configuration is read. Web Push shows the envelope before encryption; `bytes` is predicted as plaintext plus 103 bytes of RFC 8291 overhead, which a unit test checks against the real encryption.
- **Retention.** No new table. The history lives on `sends` rows, which the sends sweep already deletes, and the report's new counts are over `push_deliveries` and `notifications` rows, which their sweeps already delete.
- **Left out.** Any screen. Search of sends by label or text. A per-device breakdown of reads. An exact count of a large audience from the catalogue: `validate_only` is that.

## Campaigns

Added 19 November 2026, as S5 of the compose-screen plan. A campaign is a draft of a send kept in the service, revised under optimistic concurrency, and turned into exactly one send. Shared types and operations are in `src/campaign.rs`, the bodies in `src/service/campaign.rs`. All eleven operations are app-only.

- **Storage.** `campaigns` holds one row per campaign: the draft's spec and target as JSON, `revision`, `state` (`draft`, `launched`, `cancelled`, `archived`), `send_key`, and who created, changed, launched, and cancelled it, with when. `campaign_events` is append-only, indexed `(campaign, id)`. Ids are UUID v7, so both lists page by the key. `campaigns` has `(state, id)` for the state filter and the draft count.
- **Lenient drafts.** `check_draft` bounds size only: name, note, the spec's stored length (`MAX_SPEC_LEN`), the target's stored length, the recipient count. A missing audience, an empty title, and a condition that doesn't parse all save. `launch` runs `check_send_shape` and `send_write`'s own checks. One limit of leniency: `SendSpec` deserializes with `title` and `category` required, so a JSON caller sends them as empty strings.
- **The schedule is the spec's.** The plan's `CampaignDraft::schedule: Schedule` is not built. `SendSpec` already carries `visible_at`, `local_time`, and `expires_at`, and a second place for the same thing would need a rule for when they disagree.
- **Every state change is one filtered `UPDATE`.** Save, launch, archive, and cancel each update `WHERE id = ? AND revision = ? AND state = ?` and read the changed-row count. A save that changed nothing reads the row to say why (stale revision, or not a draft) and answers a conflict. Nothing depends on a read made earlier in the transaction, so the same code is correct under SQLite's single writer and Postgres's row locks. `racing_saves_keep_one` runs eight saves from one revision on both engines: one is kept, seven conflict.
- **Launch.** A mutation: it claims the draft (`draft` to `launched`, for exactly this revision), records the event, and calls `send_write` with the key `launch_key(id, revision)`, all in one transaction. A refused send rolls the claim back, so a failed launch leaves a draft. A launch that loses the claim answers `Contended`, the framework runs it again, it finds the campaign launched at the same revision, and `send_write` answers the existing send as a duplicate. `racing_launches_make_one_send` runs eight at once on both engines: eight successes, one non-duplicate, one send, one set of rows, one event. No `send_in` refactor was needed: `send_write` already took a `MutationCx`.
- **A launch after the send was pruned.** A repeated launch whose send record retention has deleted is refused with a conflict. Without that check `send_write` would find no send under the key and make it again.
- **Past schedules.** Refused for a new launch when `visible_at <= now`. A repeated launch is judged by its key alone, like a retried send, so it still answers after the time has passed. A local-time schedule is not checked here; `check_timing` in `send_write` applies as for any send.
- **Broadcast.** `launch_campaign` takes `broadcast: bool`, default `false`, and refuses `SendTarget::Everyone` without it (forbidden). The service has no roles; the flag is the admin server's statement that it checked `notifications.broadcast`. The plan's audience-size threshold (10,000) is not enforced here: the admin can compare `estimate_audience` or a `validate_only` count with its own threshold before it sets the flag. The launch event's detail records a broadcast.
- **`by`.** A string from the caller, 1 to 128 bytes, no control characters, stored and answered and never interpreted. It is not added to `send`, as the plan says.
- **Events.** `created` (with what it was copied from), `tested` (with how each push ended), `launched`, `cancelled` (with the rows stopped), `archived`. A save is not an event, because an autosaving screen would write thousands; `updated_by` and `updated_at` on the row record the last save. A test event names platforms and outcomes and never the person or the endpoint, so the table holds no person id.
- **Test.** An action: it reads the campaign, clears `visible_at` and `local_time`, runs `check_spec` and `check_timing`, calls the existing `send_test`, then records the event in a mutation. If the provider call succeeds and the event write fails, the push went out unrecorded; the reverse cannot happen.
- **Archive.** Allowed from any state, idempotent. It cancels nothing. An archived campaign that was launched keeps its `send_key`, and its send can still be cancelled with `cancel`.
- **Sends are not marked.** The plan's `sends.campaign` and `sends.created_by` columns and `SendFilter::{origin, campaign}` are not built. The link runs from the campaign to its send (`send_key`), and a campaign's send is recognizable by its key. Adding the columns means another migration on `sends` and a change to every `write_send` caller for a filter no screen exists to use yet.
- **Retention: none, on purpose.** Neither table is swept. A draft is saved work; deleting it on a timer would be data loss. Growth is at the rate of people pressing buttons: drafts are capped at `MAX_DRAFT_CAMPAIGNS` (1,000), each row is at most about 50 KiB, and a campaign records at most a few lifecycle events plus `MAX_CAMPAIGN_TESTS` (100) tests. Launched, cancelled, and archived campaigns are not capped and accumulate. If that ever matters, the sweep to add is "archived longer than `SENDS_DAYS`", in `service::retention`.
- **Erasure gap.** `forget_person` does not edit campaigns. A draft whose target lists recipients keeps a forgotten person's id until the draft is changed, and a condition in a draft can hold personal values, as a stored send's can. Launching such a draft names the id again, exactly as an app server calling `send` with it would. Scrubbing drafts in `forget_person` needs a scan of stored JSON and is left for review.
- **What is proven here.** `tests/campaigns.rs` (SQLite) and twelve `_on_postgres` twins share `tests/support/composer.rs`: drafts and revisions, one send per launch, the launch's checks, the schedule rule, cancel before and after, both duplicates, the test's event and absence of rows, archive, authorization on all eleven operations, the caps, and the two races. `tests/scale.rs` checks the plans of both lists and both counts on both engines.
- **Left out.** Any screen. Roles. The audience-size threshold. Marking sends with their campaign. Deleting a campaign. Search by name.

## Recurring sends

Added 19 November 2026, as L4. A recurrence is a stored schedule that makes one send per occurrence. Shared types and the six operations are in `src/recurrence.rs`, the bodies and the job's work in `src/service/recurrence.rs`. Every operation is app-only.

- **Storage: its own table.** `recurrences` holds one row per recurrence: the spec, target and rule as JSON, `state` (`active`, `paused`, `ended`), `next_on` (the next occurrence's date in the rule's zone), `due_at` (the instant its send is to be made), `sent`, `skipped`, `last_at`, `last_send_key`, `error`, and who created and last changed it. It is not a column on `campaigns`: a campaign is a draft that becomes exactly one send and is never deleted, and a recurrence has neither a draft state nor a revision, makes many sends, and is swept once ended. Indexes are `(state, due_at)` for the due read and `(state, id)` for the state filter and the cap's count. Ids are UUID v7, so the list pages by the key.
- **The rule is typed.** `RecurrenceRule { repeat, at, time_zone, starts_on, ends, local_time }`, with `Repeat::{Daily { every }, Weekly { every, on }, Monthly { every, day }}` and `RecurrenceEnd::{On(date), After(count)}`. No cron strings. `check_rule` and `check_recurrence` are shared with the client build; only the time zone lookup needs the service. At most one occurrence per date, so the smallest interval is a day.
- **Wall-clock rules.** `Schedule::at` resolves a date and `at` in the zone with `jiff`'s compatible strategy, through the same `local::arrives_in` a local-time send uses: a time in a gap goes out as far past the gap's start as it was into it (02:30 becomes 03:30), and a time in a fold goes out at its first instant. `Monthly { day: 31 }` in a shorter month is the month's last day. `every` is counted from `starts_on` (its week, starting Monday, or its month), which the service fills in with the creation date in the rule's zone.
- **One occurrence is one transaction.** `Occur` (an in-process mutation named `recur`) reads the row, works out what is owed, and writes a claim: an `UPDATE` filtered on `id`, `state = active` and the `next_on` it read, which moves the row to the following occurrence or ends it. Then it calls `send_write` with the key `occurrence_key(id, instant)` and enqueues the job for the next occurrence, all in the same transaction. A turn that loses the claim answers `Contended`, runs again, and finds nothing due. The idempotency key is the second fence: a turn that somehow repeated an occurrence would get the first send back as a duplicate. `racing_runs_make_one_send_per_occurrence` runs eight at once on both engines.
- **Scheduling.** Create, resume, and every occurrence enqueue an unkeyed `recur` job for the next `due_at`; the `recur` cron (`47 * * * *`) is the safety net for a lost job. The wake is unkeyed because a keyed enqueue that conflicts inside a transaction is `Contended`. A wake that finds nothing due does nothing. A per-minute cron was not used: it would write 1,440 job rows a day to find nothing.
- **Time is passed in.** `service::recurrence::run(db, push, now)` takes `now`, as `retention::prune` does, because the test job clock moves only the job clock. Tests call it with instants they choose and never sleep.
- **Catch-up.** A turn steps over every due occurrence to the latest one (at most 1,000 steps a transaction). It sends that one only if its send is no more than `CATCH_UP_SECS` (24 hours) late; everything stepped over is added to `skipped`. So downtime never becomes a backlog, and a monthly occurrence missed by three days is not sent late.
- **First occurrence, and resume.** Both use `Schedule::first_ahead`: the first occurrence whose send is still ahead of now. A paused recurrence does not send what passed while it was paused.
- **Local time.** With `rule.local_time`, each occurrence's send gets `spec.local_time = { at: "<date>T<HH:MM>", default_time_zone: <rule zone> }` and is made fourteen hours before that wall time read as UTC, so it exists before the first zone reaches it. `next_at` still answers the instant in the rule's own zone.
- **What the stored spec may not carry.** `label` (the service sets `recurrence.{id}`), `visible_at`, `local_time` and `expires_at` are refused at create. There is therefore no expiry per occurrence yet; a relative lifetime would be the field to add.
- **A refused occurrence pauses.** `Invalid`, `Forbidden`, `NotFound` and `Conflict` from the checks or from `send_write` pause the recurrence, store the reason in `error` (cut to 256 bytes), and count the occurrence as skipped. Other errors fail the job, which retries. Resume clears `error`.
- **Limits.** `MAX_RECURRENCES` (100) counts active and paused together and is refused by name; `MAX_EVERY_DAYS` 365, `MAX_EVERY_WEEKS` 52, `MAX_EVERY_MONTHS` 12, `MAX_OCCURRENCES` 10,000, `MAX_START_AHEAD_DAYS` 366; name, note and `by` as campaigns. `SendTarget::Everyone` needs `broadcast: true`.
- **No update.** A recurrence is immutable. Changing the rule mid-flight needs an answer for what `every` is counted from and which occurrences were already made; end and create again.
- **Erasure.** `forget_person` calls `recurrence::forget`: it finds rows whose stored target contains the person's id as text, rewrites a `Recipients` target without them, and ends a recurrence left with nobody, with `error` saying so. A condition's text is not searched, as for a stored send. The campaign-draft gap is unchanged.
- **Retention.** `recurrence::sweep` deletes ended recurrences `sends_days` after `ended_at` (never when that setting is `off`). The hourly `prune` job and `retention::prune` both call it; it is not counted in `Pruned`.
- **What is proven here.** `tests/recurring.rs` (SQLite) and twelve `_on_postgres` twins share `tests/support/composer.rs`: one send per occurrence with its key and label, the race, catch-up, both ends, pause and resume and end, both refusals, authorization on all six operations, the limits by name, local time, erasure, the sweep, and the job with its next wake. Unit tests cover the gap, the fold, month ends, weekly and monthly stepping. `tests/scale.rs` checks the plans of the due read, the list, the state filter and the cap's count on both engines; on Postgres a sort is accepted for the two reads the cap bounds.
- **Left out.** Any screen. An update operation. More than once a day. Rules such as "last weekday of the month". Expiry per occurrence. Marking a send with its recurrence other than by label.
