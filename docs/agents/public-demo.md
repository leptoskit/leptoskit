# The public demo service

`demo_service` is the public demo's runtime: one process image serves one UTC day's generation, resets itself at midnight by re-executing the same binary in the same PID, and shares a volume with the previous and next images safely through kernel file locks. This page is the operator contract: the environment it takes, the rules a release must follow, and what it deliberately does not do yet.

The service is a Unix process, and deliberately so: its locks are `flock`, its reset re-executes through `execve`, and it is deployed on Linux (developed on macOS). The workspace still checks on Windows, but there the binary refuses to start — a nonzero exit naming the Unix `flock`/`exec` requirement, before reading configuration, binding, or creating state — instead of emulating any of it, and the integration tests compile only on Unix.

## The environment

| Variable                         | Meaning                                                                                                                                                                                                                                                                                                          |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DEMO_BIND`                      | The private loopback address to bind, e.g. `127.0.0.1:8080` (bracketed IPv6 accepted). The edge terminates the public origins and forwards here.                                                                                                                                                                 |
| `LEPTOSKIT_SERVICE_VOLUME_STATE` | The state root: a real directory, mode `0700`, owned by the service account, not a symlink. Refused otherwise.                                                                                                                                                                                                   |
| `DEMO_SITE_ORIGIN`               | The site's public origin. HTTPS, except loopback/localhost HTTP for development.                                                                                                                                                                                                                                 |
| `DEMO_ADMIN_ORIGIN`              | The admin's public origin, same rules, a distinct authority — and a distinct **host** — from the site's.                                                                                                                                                                                                         |
| `DEMO_CLIENT_IP_HEADER`          | Optional. The request header the edge sets to the visitor's canonical IP (lowercase, a valid header token, e.g. `x-forwarded-for`). Absent locally: the socket peer is used when the process serves with one, and nothing else is trusted.                                                                       |
| `LEPTOS_SITE_ROOT`               | The directory `leptoskit build --release --platform web` wrote for `examples/demo_service/pages`. Its `pkg/` holds the pages' Wasm client (`demo_pages.js`, `demo_pages_bg.wasm`, and their `.br` and `.gz` copies). Read once at start and served from memory; a missing or foreign directory refuses to start. |

A misconfigured service refuses to start (nonzero exit) instead of serving half-configured.

On Linux the process also refuses to start while a file descriptor beyond the standard streams survives into it: the guard lists `/proc/self/fd`, closes its own enumeration handle, and refuses every number still there, naming each with its target. There is no exemption by name — a spare open of `/proc/self/fd` itself, or a handle to any file or directory named `fd`, is refused like any other — and an inspection failure other than a descriptor genuinely gone is fatal rather than silently excused. The proofs are `examples/demo_service/tests/inherited_descriptors.rs` (Linux-only process tests).

The two origins, the bind, and every incoming `Host` header share one host normalization: lowercase, exactly one DNS trailing dot folded away, IPv4 plain, IPv6 canonically bracketed (`[::1]`, whatever the header wrote), and explicit or implicit default ports equal — `https://Notes.Example.:443` and `https://notes.example` are the same authority. Only HTTPS is accepted, or HTTP when the host is a loopback address or a `localhost` development name; no other scheme is accepted anywhere. After normalization the site, the admin, and the bind must still be three distinct authorities — configuration that folds two of them into one is refused — and the site and the admin must additionally name **different hosts**, because a browser tells its cookie jars apart by host name alone: the same host on another port or scheme is one cookie host, and both roles cannot share it.

## Visitor sign-in

The site's visitors mint their own identity: `POST /demo/pass` (same-origin only — exactly one usable `Origin` must equal the site origin; `Sec-Fetch-Site: same-origin` stands in only when `Origin` is absent) takes a bounded form (`persona=ada|grace`, optional `return_to`) and answers 303 to `/sign-in?as=…&return_to=…`, where `return_to` is validated against the exact local paths `/`, `/notes`, and `/oauth/authorize` and falls back to `/notes`. The pass travels in an `HttpOnly`, `SameSite=Lax`, `Path=/` cookie — `__Host-demo-pass` with `Secure` on HTTPS, `demo-pass` without on loopback HTTP, never a `Domain` — whose value is `<UTC day>.<32 random bytes, hex>` and whose lifetime ends at the next 00:00 UTC. The visitor tables store only the token's domain-separated SHA-256 and an optional salted hash of the canonical client IP (derived from that day's site key), never the raw IP or token. Auth's own request auditing is separate. A cookie from an earlier day is cleared and reported as a `new_day` state; an unknown or malformed one is cleared and reported as `absent`.

A pass owns at most two people, one Ada and one Grace, each with a synthetic `<persona>-<random>@demo.invalid` address whose uniqueness is enforced by the database. Caps are enforced atomically — counted and inserted in one immediate transaction, so concurrent requests and two service processes on one volume cannot race past them: 10 new passes per canonical IP per hour (429 with `Retry-After`) and 5,000 new passes per generation day (503, stable `full` code — this bounds passes at up to about 10,000 people, not people directly). Minted passes keep signing in when either cap is full.

`POST /auth/email/send` and `POST /auth/email/verify` are gated: the gate requires a valid pass whose people own the normalized address, and refuses anything else with 403 `not_your_identity` before Auth writes a challenge, sends mail, or counts a rate-limit hit. Auth's own same-site checks, limits, and response bytes are untouched; sign-in is email-only by configuration (`sign_in_methods(["email"])`), so no wallet, passkey, password, or development route offers another way in, and neither dev sign-in nor the dev mailbox is mounted. On sign-up, a person is claimed — by its pre-minted address and an absent account id, inside Auth's transaction — or nothing is created. Roles follow the persona: Ada carries `admin`, Grace none. The admin's registered client gains the `roles` scope, so the real OIDC flow admits Ada to the admin and turns Grace away on its pages and APIs.

`GET /demo/inbox` (`Cache-Control: no-store`) answers only a valid pass, and only with that pass's people and mail; query parameters change nothing. The mailer is a bounded in-memory stand-in: at most 2,000 open addresses (least-recently-opened evicted), 3 messages each, a 10-minute lifetime pruned on every call, subjects and bodies truncated on character boundaries. Every send to a known person records a random receipt id durably before reporting success, including sends dropped because this process has no open inbox. Delivered messages retain that id in memory. The inbox compares the persisted receipt with what it still holds: a recent receipt with no matching message — sent by another process, evicted, or dropped — is reported `lost` with its sent time, without claiming which release caused it. Older retained mail cannot stand in for the missing message. Dropped mail is counted; no message content reaches disk, a log line, or a `Debug` output.

Client IPs are trusted from exactly one place: `DEMO_CLIENT_IP_HEADER` when configured — refusing pass minting and email send/verify when the header is missing, duplicated, comma-chained, or not a single parseable address — or the socket peer when the setting is absent. An empty or malformed setting prevents startup. The planned deployment sets `x-forwarded-for` behind the edge, which overwrites it with the visitor's IP. Local router tests may have neither the setting nor a socket peer: those requests have no IP bucket. A public deployment must configure the header and prevent callers from bypassing the edge; the deployment itself is a later task, with no deployed proof yet.

The generation format is now **3**. Format 2 added the visitors' tables and the admin client's `roles` scope; format 3 adds the private notes table (`demo_notes`, below). A release builds `gen/<day>.f3` beside any recent format-2 generation, which stays recognized rollback state and is never reopened, so the day's notebooks start empty rather than a live generation being migrated. A same-day reopen preserves passes, people, account claims, sessions, and the admin client; the inbox memory is lost and reported `lost`, and a resend works. A new day's keys invalidate the old pass and every old session.

## What the process serves

One listener, three authorities, validated the same way on every request:

- the **site origin** — the front door, sign-in with the demo inbox, Notes' notebook, visitor passes and inbox, the private notes routes, real email-code sign-in, the identity provider, the admin's two fonts at `/demo/assets/`, and `/demo/generation`;
- the **admin origin** — the deploy console's admin, and `/demo/generation`;
- the **bind authority** — only `/healthz`, `/readyz`, and the token-authenticated analytics service prefix. No pages, no admin.

Every other `Host` is refused with 421, before a generation exists and after — including a request whose `Host` header is missing, duplicated, or malformed: exactly one usable `Host` header names the authority, and it is never resolved by silently taking one of several values. `/healthz` and `/readyz` answer on all three authorities. Before a generation is ready, ordinary pages answer 503 with `Retry-After: 5` and a styled "Notes is opening today's demo" page, and `/readyz` names the failing `generation` check. That page has no script, no outside request, and a `<meta http-equiv="refresh" content="5">`, so it works with scripts off and checks again by itself; it says only that the demo is not ready, because a release, a failed start, and midnight look the same from there.

## The visitor pages

The pages are real leptoskit component trees, written as `view!` markup in `examples/demo_service/pages/` (the `demo_pages` crate), rendered on the server and hydrated in the browser (see [Hydrated pages](#hydrated-pages)), in the admin's paper, ink, ember, and mint: `leptoskit_admin::theme_css()` shares the admin's `--admin-*` custom properties (light, dark, and `data-lk-appearance`), and nothing else of its styles. `assets/demo.css` holds what the class compiler cannot say, by test id, and is inlined into each page. There is no hand-written script: a page makes no request but the site's own client (`/pkg/`), its operations (`/rpc/`), its live connection, and Auth's routes. No page loads a font, script, or image from another origin, and the two faces the admin draws with are served from `/demo/assets/`.

| Route                | What it is                                                                                                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /`              | The front door. First visit, a pass from an earlier day (cleared, explained), welcome back, and signed out (`?signed_out=1`). Mint goes through a same-origin `fetch` to `POST /demo/pass`, and a plain `<noscript>` form posts the same fields. |
| `GET /sign-in`       | Choose, or sign in as the person this pass minted (`as=ada\|grace`). Signed in already and not asking for the admin: `303` to the validated `return_to`. For `/oauth/authorize` it always shows, because that request asks for a fresh sign-in.  |
| `GET /notes`         | The welcome and the private notebook for the account the request is really signed in as, and the door to the admin. Anyone else: `303` to sign-in, then back.                                                                                    |
| `GET /demo/assets/*` | `sketch.woff2` and `mono.woff2`, the admin's faces. Nothing else.                                                                                                                                                                                |

Every page response is `no-store`. `return_to` is validated by `return_to.rs`, carried in the page value, and followed with `location.assign` only after a verify. Dynamic text, such as a note, is always a `Text` element's text, never markup.

**Sign-in** drives Auth's real routes and reads the private inbox only after a send or on **Check for mail**, plus once on load when the server says this process holds or lost mail for the person. The code appears only in the demo inbox; **Fill in code** copies it into the form, and nothing in the page's HTML, the pass gate's refusals, or the script invents one. The states are: choose, ready, sent, lost (the person's latest receipt names a code this process does not hold, shown with the time it was sent and without claiming why), a wrong code (`invalid_code`, announced and tied to the field), rate limited (`Retry-After` becomes a countdown), a pass that is gone (`not_your_identity`), and a busy or restarting server. A send disables itself for 30 seconds on top of Auth's own limit. The station rail is a tab list: one tab stop, arrows, Home, End.

**Notes** welcomes the person the session names and links to the admin address built from `DEMO_ADMIN_ORIGIN` (`<origin>/_leptoskit/admin/`), in a new tab. Grace follows the real refusal; **Switch account** there goes through the identity provider's `prompt=login`, and the site's sign-in shows the choice with Ada selected. **Switch to Ada** from the account menu signs out through Auth's client (`sign_out_mutation`) and mints the other person. The menu is `leptoskit::aria::Menu`: focus enters it on open, arrows move, Escape closes and returns focus, and **Open the admin** opens a new tab. A sign-out that fails stays on the page and says so in an alert. Below the welcome is the visitor's notebook, described next; the pretend checkout is not built.

**The band and the countdown.** Every page carries the demo band: the reset time, "shared with everyone today", "infrastructure is simulated", and **What's real?**. The countdown is the generation's `day` plus the server's clock at render (`now_ms`, which honours the debug clock), counted forward in the browser, so a visitor with a wrong clock still sees the right midnight. It turns to a warning inside ten minutes.

**The new-day dialog.** Each page holds one live connection and watches the `generation` stream on it. Only a server naming a different day than the page was made for opens the focus-managed alert dialog (a modal `<dialog>`: the rest of the page is inert, Tab stays inside, Escape closes); a 503 or a dropped stream proves nothing.

### Private notes

A signed-in visitor writes private notes, and each one sends one real analytics event. The contract lives in `src/notes.rs` (the table and the store), `src/activity.rs` (the event), the ownership gate in `src/site.rs`, and the page's two operations, `notes` and `save_note`, in `src/site/operations.rs`. The JSON routes below are the same notebook behind the same gate; the page uses the operations, and the Rust proofs drive both.

- **`demo_notes`** holds `id`, `account_id` (a cascading reference to the Auth account), `text`, and `created_at`. Its policy (`cx.signed_in` with the owning account) lets an account read and write only its own rows, and every note operation runs on a database handle acting for the request's session, never a system bypass. The account always comes from the session; a body cannot name one (`deny_unknown_fields`).
- **`GET /demo/notes`** answers the signed-in person's notes, newest first, at most 20, with the limits and the person's analytics actor. **`POST /demo/notes`** takes JSON `{"text": "…"}`. Both require a valid pass of the current generation **and** a session for the account one of that pass's people claimed, the same ownership the pages use; otherwise `401 no_visit` with a `pass` of `absent`, `new_day`, or `signed_out`, before any body is read. A pass with someone else's session is refused the same way. Every note response is `Cache-Control: no-store`, and note text is never logged.
- **The order of refusals for a post** is: not same-origin (`403`, the same strict check as the pass mint: one `Origin` that equals the site's, with Fetch Metadata only when `Origin` is absent; the session layer's own same-site check may answer first); no visit (`401`); media type that is not `application/json` (`415`); a body over 4 KiB (`413`); malformed JSON or unknown fields (`400 bad_request`); then the text, trimmed, 1 to 280 Unicode scalar values (`422 empty_note` or `note_too_long`). A refusal has no note and no event as a side effect.
- **20 notes per account**, counted and inserted in one immediate transaction, so two requests or two service processes on one volume cannot race past it; the next save is `409 notes_full`. There is no edit or delete, so one person causes at most 20 note events a day.
- **The event** is the typed `admin_demo::analytics::NoteCreated { words, shared: false }`, stored as `note_created`, where `words` is the whitespace-separated word count. It goes through the analytics service's own ingestion route in process (`wire::encode`, `POST …/v1/batch`, the app's token, `tower::ServiceExt::oneshot`) on a private clone of the generation's one analytics router, which the generation starts before the site is built so the build and the reopen inject the same real service. The actor is `v-` plus the hex SHA-256 of the random person id over a domain separator: stable for that person for the generation, and derived from nothing a visitor typed. The only property beside the event's own fields is `persona`. No email, text, IP, user agent, URL, or referrer is sent, and no person row or history is invented.
- **Delivery is confirmed, not promised.** One attempt, bounded to 2 seconds and 16 KiB of answer. The response says `"analytics": "confirmed"` only when the service's typed receipt accounts for exactly the one entry (stored, with no duplicate, refusal, or rate limit). An error, a timeout, a refusal, or a partial receipt returns the saved note with `"analytics": "unconfirmed"`. Nothing retries: a timed-out request may have committed, so a second send could count a note twice. The note and the event are **separate transactions**, so a crash between them leaves a saved note with no event, and a client that disconnects mid-request can leave a saved note it never heard about. Nothing here claims exactly-once delivery.
- **The operations** answer like the routes. `notes` is a query and `save_note` a mutation; a visit that is not signed in as one of the pass's people is refused `401` with the code `no_pass`, `new_day`, or `signed_out`; a save from another origin is `403`; the text's rules are `422 empty_note` or `note_too_long`; a full notebook is `409 notes_full`. A saved note answers `200` with the note, the word count, `analytics`, and the actor.
- **The page** (`pages/src/notes.rs`) is a labelled `TextArea` with a visible count, a **Save note** button (Ctrl or ⌘ + Enter saves too), `n of 20`, and the saved notes, each drawn as text. It reads the notebook once it is open; the server never puts the notes in the page. A confirmed save shows the exact actor and the admin's Live link, and says the event is named `note_created` there. An unconfirmed save says the note is saved and delivery was not confirmed, and never invites a resend. Failures keep the typed text: validation at the field (announced once through the page's status region), a full notebook, a signed-out or new-day `401`, and network or server errors (their own alert).
- **Reading notes emits no event.** Live filters by event name, so a visitor filters for `note_created` and finds the row whose actor starts with theirs; no person row exists for an actor, so People does not list it.

### Hydrated pages

The pages are hydrated leptoskit. A page lives in `examples/demo_service/pages` (the `demo_pages` crate), which is both sides: the service links it with `ssr` and renders the page from it, and `leptoskit build --release --platform web` compiles the same crate to Wasm with `hydrate`. The browser attaches that client to the server's markup, so a page works before the client arrives and behaves once it has.

- **Converted:** every page. The front door, with the band, its countdown, and the new-day dialog; sign-in, with the person's choice, the emailed code, and the demo inbox with its five stations; and Notes, with the notebook and the account menu. `assets/demo.js` is gone. The only page the service still draws itself is "opening today's demo", which needs no script.

What a hydrated page does goes through leptoskit's typed operations, declared in `pages/src/ops.rs`. The operations hold no logic: each calls a port (`ops::Backend`) the service implements per request in `src/site/operations.rs`, so the stores, transactions and limits are the ones the plain routes use.

- `POST /rpc/mint` mints the visitor's pass. It is the same code path as the form post `POST /demo/pass`, which stays for a visitor without scripts (the page carries it in `<noscript>`). The cookie is set by a small layer around the operation, because an operation's answer has no headers. A full demo is refused with the code `full`; the per-address limit is leptoskit's `rate_limited` with its wait.
- `generation` is a resumable stream on the site's live connection (`/live`). It names the generation's day once and then stays open; the client reconnects after a reset, hears another day, and opens the dialog. It has its own cap of 1,000 watchers. `/demo/generation` (server-sent events) stays: no page uses it, but the lifecycle and shutdown proofs watch it.
- `inbox` is a query: this pass's mail for one of its people, oldest first, with when a code this process no longer holds was sent. Sign-in reads it after a send and when the visitor asks. A pass that is gone or from an earlier day is refused with `no_pass` or `new_day`, and a stale cookie is cleared. The page value itself only says how many messages the server holds, never a code.
- `notes` and `save_note` are the notebook, as [Private notes](#private-notes) describes.
- Sending and checking the code, and signing out, use leptoskit's Auth client (`leptoskit::auth::client::send_code` and `verify_code`) against Auth's real routes. The pass gate in front of `/auth/email/send` answers in Auth's error shape (`error` and `message`), so the client names `not_your_identity` instead of a failure it could not read.
- Only the operations listed in `SERVED` in `src/site/operations.rs` are reachable. Anything else under `/rpc/` is `404`, whatever else is linked into the binary.
- Idempotency receipts for these operations live in a private in-memory SQLite database, so the generation's schema and format are unchanged.

`GET /pkg/{file}` serves the client from memory in the smallest encoding the browser accepts, with `Cache-Control: no-cache`: the file names carry no hash, so a browser revalidates and a release is never served stale. The service reads the client before it binds and never again, so the markup a process renders and the client it hands out always come from the same start.

Without scripts the front door still mints through its form, and so does sign-in while nobody is chosen; with a person chosen it says the code needs scripts, Notes says writing notes needs them, and the band's panel and the route's drawer stay open (`@media (scripting: none)` in `assets/demo.css`).

### Proving the pages in a browser

`examples/demo_service/tests/visitor_pages.mjs` drives the real debug service in headless Chrome through the repository's `browser.mjs` harness; Rust rendering and route proofs are in `tests/signin.rs`, `tests/notes.rs` (two cookie jars on the real router, the real analytics service read back through its own `run` query, the 20-note race across two database handles, and the refusing, rate-limiting, or stalled stand-ins that isolate the unconfirmed path), and the `pages` unit tests. The notebook journey signs in normally, saves a markup-bearing note by keyboard, reloads, opens the real admin's Live to find the matching event, and checks a second visitor sees none of it; it runs on a volume of its own because the real limit is ten new passes per network address per hour.

```sh
cargo build -p demo_service
(cd examples/demo_service/pages && leptoskit build --release --platform web --out /some/client/dir)
DEMO_SERVICE_BIN=<target dir>/debug/demo_service \
LEPTOS_SITE_ROOT=/some/client/dir \
DEMO_SHOTS=/some/scratch/dir \
deno test --allow-env --allow-read --allow-net --allow-run --allow-write \
  examples/demo_service/tests/visitor_pages.mjs
```

It needs a debug build, because the debug clock and failure hooks (`DEMO_TEST_CLOCK`, `DEMO_TEST_CLOCK_TICK_MS`, `DEMO_TEST_FAIL_INIT`, `DEMO_TEST_RETRY_MS`) are compiled out of release builds. `DEMO_SHOTS` also saves screenshots at 1280 and 400 px in light and dark, with an `index.html` gallery; keep them out of Git. The identity provider accepts plain-HTTP redirects only to `localhost`, `127.0.0.1`, and `[::1]`, so the harness serves the site at `localhost:<port>`, the private bind at `127.0.0.1:<port>`, and the admin at `127.0.0.1:<other port>`, a byte forwarder to the same listener; `admin.localhost` is refused.

## The daily generation

State lives under `gen/<UTC day>.f<format>` — one directory per day and format, always at its final path. A generation becomes visible only when its `published` marker is renamed into place, which happens after credentials, databases, the seeded month, and the identity provider's client all exist **and a durability barrier has fsynced every one of them — the databases, their WAL sidecars, and the directory entries up to the volume root** (the SQLite connections run WAL with `synchronous=NORMAL`, where a committed transaction alone is not a power-loss barrier; a barrier failure publishes nothing). Other processes open a generation only after validating that marker against their own format and schema fingerprint — **before** any database is opened, so a mismatch is refused while the data is untouched.

The marker's `seed_events` is a **historical initialization receipt** — proof the build finished and its seed read back — never an invariant over today's analytics. Visitors add events and legitimate deletions remove them; a warm open re-reads the catalogue only to prove the generation answers, so a mutable day restarts and overlaps freely. The initial seed itself must be _complete_: every batch's typed capture answer is checked (nothing refused, nothing rate-limited, every entry accounted), and the read-back must match it exactly before publication.

A marker that exists but cannot be read (corrupt, truncated), or that does not name its own directory, is a **fail-closed fault**: the process stays unready and reports it without touching a database, credential, or marker byte. Only a genuinely absent marker permits the unpublished build path. Collection holds the same rule: an unreadable marker is never a deletion reason.

Three locks, all `flock` files under the volume, all held by the process image rather than by tasks, so neither an aborted task nor the runtime's shutdown timeout can drop one while a writer runs:

- **`build.lock`** — one builder or collector at a time, taken by cancellable polling. A failed initializer keeps it until exec/exit: its background writers may still run, so no other process touches the volume until the image is gone.
- **`<generation>/lifetime.lock`** — held shared by every process with the generation open, from before the first database opens until exec or exit. Collection deletes a generation only if it can take the lock exclusively without blocking, which is how clock jumps, paused candidates, and older formats refuse to have live databases unlinked.
- **`<generation>/worker.lock`** — held by the one process running the control service's worker. A ready candidate polls for it once a second; taking it interrupts operations the previous holder left running.

Retention recognizes a published generation **structurally** — a marker that names its directory with seed evidence — regardless of the format or fingerprint this binary serves. Today and yesterday are kept per format, so a recent generation of a foreign format (the rollback target after a same-day format bump) survives collection with no live holder; only genuinely expired published generations and genuinely unpublished leftovers are deleted, and only under the exclusive lifetime lock. What survives counts against a finite budget of four generation directories and 1 GiB total. When live holders or unreadable markers prevent collection and the budget would be exceeded, the process stays **unready with an honest error** — it never unlinks a live generation and never grows without bound.

## Reset and stopping

The day watch reads the UTC wall clock at most every 30 seconds. When the date differs from the generation's, or a failed initialization's bounded retry (60 seconds) comes due, the image drains in-flight requests and SSE streams for at most 3 seconds, gives the runtime at most 2 more seconds, and **execs the same binary with the same arguments in the same PID**. Every descriptor closes at exec, so the kernel releases the locks and databases only once the old execution has fully stopped. A SIGTERM follows the same drain and exits 0 within 8 seconds.

**Termination is authoritative.** The SIGTERM listener installs before the listener binds and stays armed for the whole process life, so a signal observed during a reset's drain — or after `run` has already reported the reset, while the runtime is finishing — outranks it, and the process exits 0 instead of re-executing. The exit-or-exec choice reads the stop state once, after the runtime has stopped; a signal delivered after that read is past the boundary and is not claimed as observed. A failed handler install is a truthful refusal to start before anything serves.

After a failed initialization the process never retries inside the same image — background tasks may already be running — it keeps the fallback for 60 seconds, then re-executes for a bounded retry. `Restart=on-failure` plus a successful exit is not a reset: the process never exits 0 on its own.

## Release rules

- **Don't release between 23:58 and 00:05 UTC.** A release that observes its candidate during the midnight re-exec sees it change and reverts; retry afterwards.
- **Schema changes need a `GENERATION_FORMAT` bump.** The published marker carries a fingerprint of the build's schemas: the analytics migration list, the deploy console's migration list (`Store::schema_fingerprint()`, computed from the migrations themselves — no duplicate list to keep in step), and the linked SQLite table schema. A binary that finds a same-format marker with a different fingerprint refuses to open the generation, before anything is migrated — the fix is a format bump and a fresh directory, never a silent migration. Adding a deploy-console migration moves the fingerprint, so such a release needs the bump too.
- **Keep the volume's mode and ownership right.** The service refuses a symlinked, foreign-owned, or non-0700 root.

## Deliberately not here yet

- **No checkout, and one event only.** The site's only analytics emission is `note_created`, from a saved note. There is no pretend checkout, no anonymous history, no signup event, no public capture endpoint, and no outbox or retry: an event that isn't confirmed stays unconfirmed. Notes cannot be edited or deleted.
- **No real browser overlap proof.** The authenticated admin SSE overlap (a real browser crossing a process handover) remains its own task, as do Linux/systemd acceptance and the edge deployment. The browser proofs cover the site's pages, a same-day restart, a next day, and the build-time page on macOS, in Chrome only.
- **No cross-process live broadcasts.** Operation progress SSE is process-local. During an overlap, an operation that finishes in the old process is seen by a candidate's viewer through reconnection: the runtime ends successful authenticated operation streams after 15 seconds, so the browser's EventSource reconnects into the durable terminal snapshot the shared store holds.
- **No cloud provider, no real executor.** Operations run against the simulated executor only; nothing contacts a provider.

## Measured, on macOS (arm64, release build)

- Fresh-volume startup with the full month, timed from **before process creation** to the first `/readyz` 200: median **493.2 ms** with the demo's 5 ms ingestion window (482.5–513.2 ms), versus **1869.7 ms** with the 50 ms default (1843.1–1947.3 ms). Five alternating runs per side on a warmed host, with no failed runs. These measurements include process creation but do not establish first-launch performance on a cold host.
- After the private notes slice (generation format 3), five sequential fresh-volume release runs on a busy, unwarmed development host measured a median of **926 ms** to the first `/readyz` 200 (686–1593 ms, the first run slowest), all stopping cleanly on SIGTERM. That host was not the quiet one behind the figures above, so the two are not a like-for-like comparison; both are well inside two seconds, and no sweep was needed.
- The seed sends 30 sequential batches and waits for each committed acknowledgement. Reducing the collection window from 50 to 5 ms predicts 1350 ms less waiting; the observed median saving was 1376.5 ms. The demo retains a short window for grouping concurrent visitor submissions into transactions; the analytics service's production default and all other ingest settings stay unchanged. A diagnostic sweep of 1, 2, 5 and 10 ms supported the batching-delay explanation. The residual startup time was not separately profiled into process loading, SQLite transactions and the publication barrier.
- Every measured generation's seed receipt matched its actual analytics row count: 7,963 rows in this run. Counts depend on when the month's seed is generated. The real capture acknowledgements and durability barrier remain in the timed path. Warm reopenings took 20.6–24.2 ms, with marker bytes, credentials and row counts unchanged. All 20 measured cold/warm runs stopped successfully on SIGTERM.
- Method: an out-of-tree Rust harness ran frozen release binaries on fresh mode-0700 volumes and free loopback ports, using production configuration without `DEMO_TEST_*` variables. One unmeasured run warmed each binary before the five alternating before/after pairs; warm runs reopened those volumes. The harness counted SQLite events locally after shutdown and treated nonzero exits or forced kills as failures. Host load was 5.3–5.8 on 12 logical cores. These are configuration measurements on this host, not a general analytics throughput benchmark.
- Binary size: 49,775,424 bytes (`cargo build --release`, unstripped; the `dist` profile strips). Generation size: about 15 MB.
- Reset outage was measured in debug builds only, where the stream closes within the 3 s drain and the new day becomes ready a few seconds later. Release binaries ignore the debug clock hooks, so an accelerated midnight is not a release-mode measurement.
- **Linux/systemd acceptance remains pending.** No target-host readiness bound or real systemd/CLOEXEC behavior is claimed from these macOS measurements. Linux-only descriptor and lifecycle tests must run there before deployment.
