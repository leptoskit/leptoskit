# Deployment graph ownership

Graph frontend placement is declared under `[infra.frontends.<name>]`. The top-level `[frontends.<name>]` table belongs to application build targets. Graph unit identifiers such as `frontends.docs` still select the same independently owned deployment units.

The required dogfood project is `leptoskit.dev`: landing, docs and lazy playground frontends, plus a database-free compile API on an exclusive CPU-heavy host. The platform must own the complete lifecycle through `lk infra`. A separate provisioning script or external application supervisor does not meet this requirement.

## Implemented core

`leptoskit_config::graph` provides common unit identities and validated ownership. It runs no build, filesystem traversal, provider request or deployment:

- `routes::Routes` validates hostname/mount ownership and ingress placement. Matching chooses the longest segment prefix. `/docs` redirects to `/docs/`; `/docs2` belongs to the root route; a missing `/docs/file` remains the docs frontend's responsibility. Hostnames are canonicalized for case and a terminal DNS dot. URI paths decode once; encoded separators, invalid escapes, traversal and ambiguous paths fail before fallback.
- `artifacts::Trees` partitions one build output into disjoint release trees. The root website excludes `docs` and `play` when those subtrees belong to other units. Nested ownership is explicit, duplicate claims fail, and unclaimed files do not silently enter another release. This is lexical ownership; actual regular-file membership, symlinks, modes, containment and copied bytes still need verification at the filesystem boundary.
- `plan::Plan` joins hosts, placements, named artifact inputs, routes, trees, call relationships and readiness ordering. An exclusive host cannot hold another unit. A declared runtime requirement must match the host's requested runtime. This is configuration consistency, not an observation that the runtime is installed or safe.
- Readiness dependencies form a DAG; call relationships can contain cycles. Selecting docs does not select the compile API. Backend and toolchain artifact inputs are explicit, so selecting the compiler does not omit its build inputs. Nonselected transitive readiness prerequisites remain checks, not automatic deployments. A shared recipe appears once in the selected build inputs.

## Validation boundaries

The core has no external dependencies. A lightweight test harness compiles exact copies of the production module hierarchy with the repository's pinned Rust compiler, without stubbing types or algorithms. It checks the website graph, route/file ownership, placement, selective release behavior, and every four-unit directed readiness graph against an independent transitive-closure oracle. Source hashes and command output are retained in `/Users/mini03/Developer/leptoskit-graph-evidence-20261107`.

These checks do not replace Cargo integration, full hooks, generated static-server/container acceptance, or provider validation.

## Configuration integration

The branch now implements an explicit `InfraConfig::{Managed, Graph}` lifecycle. Untagged existing infrastructure tables still deserialize as `ManagedInfraConfig`; graph tables require `mode = "graph"` and reject fields from the managed preset. Empty new root maps and absent service fields are omitted from serialization, preserving existing configuration fingerprints.

`deployment::compile` joins named artifact recipes, frontend trees, service placement, readiness dependencies and call relationships into the checked core. Static projects require `build.backend = false`, with no root database, auth or backend probes. An SSR frontend declares its own executable and `serve.probes` contract. Service ports are unique per host. Runtime bindings cannot alias each other or shadow explicit environment/secrets. Separate producers cannot write overlapping output directories. The full service name is retained in derived artifact names, including at the name-length limit.

The parser fixture in `leptoskit_config/tests/fixtures/website-graph.toml` covers the website's three frontends and exclusive compiler. Its provider identifiers are documentation values. Declared capabilities, image-pin paths and readiness contracts are not evidence that a runtime, pinned image or probe actually works. Graph builds reject inherited service-manifest public routes, application bindings, pool settings and volumes; only explicit graph placement and ingress are supported. Source selection remains the graph service table’s declared package/path/registry/git source, never a manifest override. Initial graph service declarations must explicitly say `database = false`; persistent graph data, external service nodes and legacy app-level bindings remain unsupported until their ownership and recovery contracts exist.

The new `lk infra graph [--unit frontends.docs]` reporting module prints declared hosts, routes, tree exclusions, call relationships and selected artifacts/stages. It exposes no service environment values, runs no recipe and makes no provider request. `lk infra generate` also handles graph declarations as described below. Remaining graph operations currently refuse before entering the managed single-app path. This is inspectable configuration, not a working website deployment.

Scoped validation compiles the exact configuration crate and reporting module against existing dependency artifacts, without rebuilding dependencies while the machine's heavy slot belongs to another task. Configuration unit/integration tests, editor schema validation and report tests run without skips. The production schema generator updates and checks all three app schema aliases; the workspace alias stays unchanged. Those scoped checks preceded the full CLI build, reviewed help snapshots and official `schema:update` run recorded below; they did not establish normal pre-push acceptance. Evidence and commands are under the `config` directory beside the core evidence.

## Provider generation

`lk infra generate` writes `infra/<name>/main.tf.json` and `graph.json`. Each named host retains its own compute provider, region, server type and SSH keys. Public hostnames point at the host that owns their routes; multiple path mounts on one hostname share its DNS records. Static-only graphs produce no app server, database or backup resources. Generated hosts have replacement protection.

HTTPS generation fetches both official Cloudflare IP-range lists, rejects empty, malformed, local, overly broad or noncanonical ranges, and records the canonical lists and their digest. Public origin firewalls allow application traffic only on TCP 443 from that snapshot. SSH remains restricted to declared administrator CIDRs. The Tunnel variant opens no public application port, generates a separate tunnel per ingress host, and marks token outputs sensitive. Private services create no Cloudflare resources.

The HTTPS output accepts public CSRs for origin certificates. The private-key store, CSR lifecycle, certificate installation and renewal are still required before graph apply is enabled. Generation deliberately leaves existing Cloudflare zone settings and configuration rules alone: per-host strict TLS policy must preserve or import the existing zone-owned ruleset before changing it. Generated cloud-init currently hardens SSH and installs base packages; it does not install the gateway, static server, service supervisor or container runtime. `graph.json` records these incomplete lifecycle stages explicitly.

OpenTofu 1.13.9 accepted HTTPS, Tunnel, mixed-provider, static-only and private-service configurations against the installed provider schemas. Mock-provider evaluation also checked expanded firewall ports/CIDRs, hostname-to-host addresses and tunnel fallback rules. Those checks exercise the generated expressions and schema, not provider API behavior or actual ingress. The repeatable ignored test is `infra::graph::provider::acceptance::graph_provider_schemas_and_expanded_boundaries`; set `LEPTOSKIT_TEST_TOFU` to a standalone OpenTofu executable if it is not on PATH. All provider operations in its five fixtures are explicitly mocked. No cloud infrastructure or production DNS was changed.

The integrated local acceptance below covers the CLI build, command boundaries and reviewed snapshots; the normal local gate remains the publication requirement. The build command dispatches graph roots to selected units; dev, serve, native and single-app deployment entry points still require an application root before generating files or selecting default targets. Graph dev and release dispatch remain open.

Connect the captured graph builds to exact release descriptors, static publication, SSR backends, service-specific images, host provisioning, Cloudflare DNS/TLS/firewalls, readiness and independent release/recovery. Use a managed static host first; Pages and R2 can be additional output adapters. Keep the existing Cloudflare Tunnel preset distinct from explicit Cloudflare-only HTTPS origin ingress.

The current `leptoskit-site` packager already emits landing, docs and playground output. Run it once and partition its output instead of building the same package three times. Actual acceptance must bind the candidate CLI/toolchain and all output members. The current playground router exposes `/healthz` but lacks `/readyz`; add and test actual runtime/image/warm-up readiness before declaring `serve.probes`.

Required final acceptance includes a docs-only release leaving the compile API's image, container ID, start time and history unchanged; the converse service-only release; bounded benign compilation with no database; correct nested assets, CSP and CORS through the generated edge; partial-failure retries and rollback with current approvals; and real provider/DNS/TLS/firewall validation separately from fixtures. No production cutover has been performed.

## Selected local builds

`lk build --unit frontends.docs` runs the recipes needed by that unit and captures only its owned tree. Repeating `--unit` selects additional units; omitting it selects all units. Shared recipes run once per invocation. `--out` chooses the receipt parent (default `.leptoskit/graph/builds`); each successful build creates a new child with a manifest, its SHA-256 and the captured files. A failed build leaves no successful receipt. Recipe working outputs can remain, as in an ordinary local build.

Recipes run their declared argv from the graph root. `LEPTOSKIT_CLI` names the exact invoking executable, and `LEPTOSKIT_BUILD_PROFILE` is `dev` or `release`. The website packager accepts that CLI and profile, so a graph does not accidentally pick a different installed `lk`. Other recipe programs must deliberately use the profile; it does not rewrite their arguments. Service builds run independently through the existing Cargo resolver, with immediate executable capture so another service's features cannot replace the captured binary. Readiness-only dependencies do not become build selections.

Static captures require a nonempty `index.html`. SSR captures separate the executable from public files and allow an empty asset directory. The shared asset reader preserves website descriptor serialization and checks exact paths, directory membership, modes, lengths and hashes through directory handles. Symlinks, special files, unexpected membership and mutation during copying fail. Copied input trees have bounded counts, depth and bytes. Declared service toolchain pins are read before recipes and checked again before publishing the receipt. The receipt hashes configuration and recipe values instead of copying private environment values into the manifest.

These are ordinary trusted local builds, not isolated source reproduction. Receipts explicitly leave reproduction, authorization and runtime unchecked. They are not yet consumed by graph release or approval commands. Unix exact-mode capture is required; other hosts return an explicit unsupported error. The initial scoped gate executed the production asset, website and graph capture modules with cached dependencies: 23 tests and workspace Clippy passed. That evidence preceded the actual CLI, opt-in Cargo journey and packager acceptance below. A complete production website capture remains outside that evidence.
