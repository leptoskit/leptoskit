# 3D scenes

`leptoskit_3d` draws host-owned 3D scenes on the GPU: glTF models, their animation, lights, and a camera, in a `Scene3d` view on every platform that has a host for it. The crate's contract is in `crates/leptoskit_3d/readme.md`, and app authors read [the guide](../src/guide/33-3d-scenes.md). This note records how it is built, what the brief asked for that it does differently, and what is left.

The first consumer is Reapers, an AR game: six characters of about 40 rigid parts each, 64 node-animation clips, morphing robes and faces, drawn over the phone camera. Its models use `EXT_meshopt_compression` and `KHR_mesh_quantization`.

## Who owns what

The host owns the scene. A guest never holds GPU objects: it picks ids for scenes, nodes, and assets and sends `Op`s (load, spawn, transform, visibility, named parts, clips, morph weights, material overrides, attachments, camera, light, backdrop, exposure, raycasts). The host answers with `Event`s (asset loaded or failed, clip finished, raycast hits). Both travel in a little-endian binary form (`protocol.rs`) that rejects anything malformed, and every op is sanitized (`sanitize.rs`) before it applies.

The guest never draws, and never runs in the frame loop. Animation sampling, the pose, skinning and morphs (on the GPU), culling, and sorting all run on the host, on the display link, and only while the scene changes or animates.

| Piece                 | Where                                   | Runs on                                                                           |
| --------------------- | --------------------------------------- | --------------------------------------------------------------------------------- |
| `client::Scene`       | the guest (`guest` feature) or the page | the guest thread, or the page's thread                                            |
| `host::Scene3dPlugin` | `leptoskit.scene3d`, an async plugin    | `APPLY` applies in `invoke`, so batches apply in submission order                 |
| `host::Hub`           | one per process                         | any thread; each scene has its own mutex, held briefly                            |
| asset loading         | one loader thread per process           | never the UI or guest thread; assets are shared by path while any scene holds one |
| `host::View`          | one per `Scene3d` view                  | the thread that attached it (the main thread), from the display link              |
| `Gpu`                 | one per process                         | the environment, shaders, pipelines, and uploads are shared by every renderer     |

Events reach the guest through `NEXT_EVENTS`, a long-polling call that resolves when the scene has events and ends on cancellation or close. That keeps 3D off the app's single `guest::Events` receiver.

Views advance a scene by display timestamps, not elapsed time, so two views of one scene advance it once per frame. A view that is idle is woken by a waker the host sets; Swift posts to the main queue, and Kotlin posts to the view's looper.

## Loading

`gltf/` reads `.glb` and `.gltf` (with `data:` URIs or files beside it, never outside its folder). `gltf/meshopt.rs` decodes `EXT_meshopt_compression` in pure Rust, written from the extension's specification: vertex codec 0, index codecs 0 and 1, index sequences, and the octahedral, quaternion, and exponential filters. It bounds-checks every read. Hand-built cases and a random-input test cover it in this repository; the `LEPTOSKIT_3D_MODELS` test checks decoded positions against each accessor's declared bounds and rotation keys for unit length, and passed on all thirteen of Reapers' models. Quantized attributes are dequantized at load. Textures are PNG or JPEG, decoded to RGBA with mips built on the CPU.

## Rendering

- **Forward, 4× MSAA** where the target format and `Depth32Float` allow it.
- **HDR lighting, tonemapped in the forward shader** with Khronos PBR Neutral, then encoded for the target (sRGB in the shader for a `Unorm` target, by the hardware for an `…Srgb` one). Output is premultiplied, so a view composites over native views.
- **Skinning and morphs on the GPU.** Joint matrices (three rows each) and active morph weights go in a per-frame `Rgba32Float` texture read with `textureLoad`; morph deltas are packed as six halves in an `Rgba32Uint` texture, one texel per vertex and target. No storage buffers: WebGL2 has none, and many Android GLES drivers have none in the vertex stage.
- **Environment.** A neutral studio sky with a soft key light, baked on the CPU into a 64² cubemap with six roughness mips and nine spherical-harmonic irradiance coefficients, once per `Gpu`.
- **Light and shadow.** One directional light, and a soft disc on the ground under each model (the instance's origin is its ground), fading as the model rises.
- **Rim.** A Fresnel rim per part (`MaterialOverride::rim`).
- **Batching.** Opaque draws sorted by pipeline, asset, and material, then front to back; identical static meshes share one instanced draw; transparent draws are sorted back to front; culling tests each view's frustum (skinned parts by their joints' reach, which the loader computes per joint).
- **Targets.** `Renderer::render(&RenderTarget)` takes views (`ViewParams { view, projection, viewport }`), a `TargetColor` (one texture with viewports, or one texture or layer per view), a `Background` (the scene's, a colour, or a `CameraImage` of Y and CbCr planes or RGBA with a display transform), and optional `Occlusion` (real-world depth with a transform, a scale to metres, and a tolerance).

## Native hosts

`leptoskit_bridge_ffi`'s `scene3d` feature adds the plugin (`lk_app_enable_scene3d`) and `lk_scene3d_*`: attach a view to a `CAMetalLayer` or an `ANativeWindow`, set a waker, resize, draw a frame at a display time, and detach. Every function exists in every build, so the Swift and Kotlin renderers always link; without the feature nothing attaches. `leptoskit build` turns the feature on when the app builds `leptoskit_3d` with more than its protocol (`registry.rs`, `uses_scene3d`), and stages the app's `assets/` folder: Android packs it under the APK's `assets/`, the Xcode project references it as the bundle's `assets` folder, and the macOS app copies it into `Resources/assets`.

- **iOS and macOS:** `NativeScene3dView` (`mobile/NativeScene3d.swift`) hosts a `CAMetalLayer`, attaches while in a window with a size, and draws on a `CADisplayLink` (on macOS, `NSView.displayLink`) only while the scene wants frames.
- **Android:** `NativeScene3dView` (`mobile/NativeScene3d.kt`) is a translucent `SurfaceView` drawn on the `Choreographer`. `app.cpp` acquires an `ANativeWindow` from the surface and releases it only after Rust has let the wgpu surface go. Assets are read through `AssetManager` from Rust's loader thread.
- **Web:** `Scene3d` renders `<canvas data-lk-scene3d="id">`. `leptoskit_3d::web` attaches to such canvases through a `MutationObserver` that starts when a scene first applies ops, so a page that never uses 3D never links wgpu. WebGPU canvases share one device; WebGL2 contexts cannot share, so each WebGL2 canvas has its own, and only the first canvas showing a scene draws it there.
- **The Rust widget backends** (AppKit, UIKit, GTK, Win32) keep an empty view in its place; the terminal draws it like an image, and the watch surfaces refuse it.

A scene whose backdrop is `Backdrop::Camera` draws over whatever `CameraFeed` the hub has (`Hub::set_camera_feed`): `leptoskit_xr`'s `scene3d` feature installs its phone sessions there, and the feed's painter then chooses the views and the background (see [xr.md](xr.md#phones)). Hosts pass the interface's rotation with `lk_scene3d_view_set_rotation`, and the Android view moves below the window while `lk_scene3d_view_shows_camera` reports the opaque camera picture.

## Where it differs from the brief

- **`Backdrop` for the guest, `Background` for the renderer.** The guest's choice is `Op::SetBackdrop(Backdrop)`, so the renderer's `Background` (scene, colour, or camera image) keeps the name the XR contract uses.
- **No multiview yet.** Stereo draws one render pass per view: into viewports of one texture, or into one texture or array layer each (`TargetColor::Layers`). A multiview pipeline variant, with the view index choosing the globals, is the next step for headsets.
- **Tonemapping in the forward shader**, not a separate HDR target and pass. On a phone at three times density the extra full-screen pass costs bandwidth the camera image already uses; blending then happens after tonemapping.
- **A disc shadow, not a shadow map.** In AR there is no floor geometry to receive a shadow map, and a soft disc reads as contact.
- **Android defaults to OpenGL ES**, chosen per app with the `dev.leptoskit.scene3d.backend` manifest metadata (`vulkan` opts in). `Backend::Auto` is Metal on Apple platforms, Direct3D 12 on Windows, Vulkan on Linux, and WebGPU with a WebGL2 fallback in the browser.
- **Clips replace each other.** One clip plays at a time per instance, with crossfades between them; there are no additive layers. A morph weight set by the guest overrides what a clip sets for that target.
- **Textures use one sampler per material** (the first texture's), only `TEXCOORD_0`, and no `KHR_texture_transform`.
- **The surface hosting is 3D's own.** The brief asked for generic GPU surface hosting shared by canvas and 3D. `host::View` hosts a scene, not a canvas; `Gpu` exposes its device and queue, so `leptoskit_canvas`'s renderer can draw on the same device, but no `Canvas` element is hosted yet (see [gpu-canvas.md](gpu-canvas.md)).

## What is left

- GTK, Windows, and HarmonyOS hosts for `Scene3d`.
- Multiview, a real shadow map for indoor scenes, image-based lighting from the camera (ARKit's environment probes), and a configurable environment per app.
- Hosting `leptoskit_canvas` in the same surfaces.

## Checks

`crates/leptoskit_3d/tests`: `protocol.rs` (round trips, every truncation, 20 000 mutated batches, sanitizing), `world.rs` (the scene, driven by ops and read back through events and raycasts), `render.rs` (headless pixels; skipped without an adapter), and `host.rs` (the hub and plugin). `benches/frame.rs` measures a frame of six animated characters. `examples/render_model.rs` renders any model to a PNG. `examples/scene3d` is the app.

Not checked yet: a run on an iOS device or simulator, an Android device or emulator, and a browser. The Kotlin is not compiled in this repository's checks, and `app.cpp`'s Android branch was type-checked against a stub header, not the NDK.
