# LeptosKit Cloud

Engineering note, 18 November 2026. LeptosKit Cloud is a hosted platform that runs any leptoskit app. A developer signs up and runs one command, or presses one button, and the cloud runs their server, database, web client, over-the-air updates and store submissions from the `leptoskit.toml` they already have.

This note is the contract every cloud pull request builds against. When a slice finds it wrong, the slice stops and the note changes first. The foundation and Control 1 are built; §12 says what exists and what each part's evidence is.

## CLI accounts and projects

Tables are server-only; every client-visible type is a plain serde type, and an operation never returns a table row.

CLI 1's account slice is built and verified: Cloud all-feature tests passed 97/97 with Postgres required, including the isolated featureless-client check with no backend, SQLite, Postgres, both backends, and wasm. CLI cloud tests passed 13/13, help snapshots passed 14/14, and the control-plane app suite passed 11/11, including real-binary device login, whoami, project creation, token creation and API-token use. Cloud native and featureless wasm clippy, CLI all-target checking, and CLI and control-plane app native clippy passed with warnings denied.

The CLI reads cloud discovery for the client, scopes and RPC path, then OpenID Connect discovery for device authorization, token and revocation endpoints. The fake provider advertises different paths to verify that the CLI follows discovery. The binary builds its own routes (readiness, and the console with `ssr`) in full, layers them with sign-in and then the identity provider last, and hangs them as the fallback of the control plane's already layered router (`server::router`). Axum's merge replaces the default fallback that carries protocol middleware, so nothing may be merged after those final layers. `leptoskit_cloud_app/tests/binary.rs` starts the real binary and checks OIDC discovery, device authorization, Cloud discovery, readiness and health. `leptoskit_cloud_app/tests/cloud_cli.rs` verifies the end-to-end CLI journey.

The account part of CLI 1 lives in `crates/leptoskit_cli/src/cloud/`. It adds this command tree; deployment commands belong to a later slice, and `lk deploy` keeps its existing behavior:

```text
lk cloud login [--no-browser]
lk cloud logout
lk cloud whoami
lk cloud org list
lk cloud org create <name> [--slug <slug>]
lk cloud org members <org>
lk cloud org invite <org> <email> --role <role>
lk cloud org invitations <org>
lk cloud org revoke-invitation <org> <invitation-id> --confirm <invitation-id>
lk cloud org set-role <org> <account-id> --role <role>
lk cloud org remove-member <org> <account-id> --confirm <account-id>
lk cloud project list
lk cloud project create <name> [--region <region>]
lk cloud project show
lk cloud project delete <project> --confirm <project>
lk cloud env list
lk cloud env create <name> [--kind staging|preview]
lk cloud env update <name> [--size xs|s|m|l|xl] [--min <n>] [--max <n>] [--sleep never|when-idle]
lk cloud env delete <name> --confirm <name>
lk cloud token list
lk cloud token create <name> --scope <scope> [--scope <scope>] [--expires 30|90|365]
lk cloud token revoke <token-id> --confirm <token-id>
lk cloud link [--force]
```

Every command accepts `--json`, `--url`, `--org` and `--project`, before or after its subcommand. Organization and project default from `[cloud]`; without an organization link, the caller's personal organization is used. Organization operations name their organization positionally. Token creation's optional `--project` binds the token to that project; without an explicit or linked project it creates an organization token. Destructive operations always require `--confirm`, including in a terminal. There are no interactive confirmation prompts.

The cloud origin is chosen from `--url`, `LEPTOSKIT_CLOUD_URL`, `[cloud].url`, then `https://cloud.leptoskit.dev`. It must be HTTPS, or HTTP on loopback, without credentials, path, query or fragment. Requests have a 30-second timeout, follow no redirects and bypass proxies for loopback.

Login reads `/.well-known/leptoskit-cloud` for the first-party client ID, scopes and RPC path. It prints the verification URL and user code, opens a browser only in an interactive terminal unless `--no-browser` was supplied, and polls at the server's interval, adding five seconds after `slow_down`. Device codes, access tokens and refresh tokens are never displayed. The identity provider has no client-description field in device authorization, so no host name is sent. The control plane must add this field before the release sheet can say “signed from the terminal on <host>”.

Sessions are stored per normalized origin in `$XDG_CONFIG_HOME/leptoskit/cloud/<sha256-origin>.json`, falling back to `~/.config/leptoskit/cloud/`. On Unix the directory is mode 0700 and the files mode 0600. Broader permissions and symbolic links are refused with a repair command. Writes use a private temporary file, file synchronization, atomic replacement and directory synchronization. A separate `<sha256-origin>.lock` file is locked throughout refresh and storage. The session is read again after acquiring the lock, preventing two processes from reusing a rotating refresh token. Login replacement and logout use the same lock. Access tokens are refreshed 30 seconds before expiry and once after an HTTP 401. Logout removes local credentials even when revocation cannot reach the server, and reports that the remote session may remain live.

`LEPTOSKIT_CLOUD_TOKEN` supplies a CI API token instead of the stored session for that invocation and is never stored. Listing members accepts API tokens. Membership changes, invitations and token management use `Permission::requires_person` and reject this override before making a request, explaining that they need a person signed in through `lk cloud login`.

JSON output is the bare operation result, without a wrapper or terminal styling. UUIDs are strings, timestamps are RFC 3339 strings, roles and scopes use their lower-case API spellings, and optional fields are `null`. These shapes come from the client-safe types in `leptoskit_cloud`:

| Command                                                     | JSON result                                                                                                                    |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `login`                                                     | `{ "signed_in": true }`                                                                                                        |
| `logout`                                                    | `{ "local_credentials_removed": true, "revoked": boolean }`                                                                    |
| `whoami`                                                    | `WhoAmI`: `account`, `email`, `via`, `operator`, `organizations`, `token`                                                      |
| `org list`                                                  | Array of `OrganizationSummary`: `id`, `slug`, `name`, `plan`, `personal`, `role`                                               |
| `org create`                                                | One `OrganizationSummary`                                                                                                      |
| `org members`                                               | Array of `Member`: `account`, `email`, `role`, `joined_at`                                                                     |
| `org invite`, `org invitations`                             | One or an array of `PendingInvitation`: `id`, `email`, `role`, `invited_by`, `expires_at`, `created_at`                        |
| `project list`                                              | Array of `ProjectSummary`: `id`, `slug`, `name`, `region`, `created_at`                                                        |
| `project create`                                            | `CreatedProject`: `project`, `environment`, `detected`                                                                         |
| `project show`                                              | `ProjectDetail`: `project`, `environments`, `detected`                                                                         |
| `env list`                                                  | Array of `EnvironmentSummary`                                                                                                  |
| `env create`, `env update`                                  | `EnvironmentSummary`: `id`, `name`, `kind`, `scale`, `revision`, `scale_differs`, `created_at`, `updated_at`                   |

| All deletions, revocations, member removal and role changes | `null`                                                                                                                         |

`scale` contains `app` and a map of `services`; each process has `size`, `min`, `max` and `sleep`. `detected` contains arrays `targets` and `variables`. `whoami.token` contains public caller-token metadata, never its secret. Token creation warns on stderr that the value is shown once, including in JSON mode. A lost response is not retried: `token_name_taken` preserves the server's explanation naming the token to revoke. Environment updates first read their revision, preserve service scale, and report `stale_revision` as a request to retry after another writer's change.

`link` checks the project through the API before editing `leptoskit.toml` with `toml_edit`. It writes `project`, omits `organization` for the personal organization, omits the default `url`, preserves unrelated comments and formatting, and requires `--force` to replace a different link.

Evidence is in `cloud/tests.rs` (fake control plane, device outcomes, refresh rotation and lock race, CI precedence, logout, permissions, command requests, error messages, help and human snapshots) and `leptoskit_cloud_app/tests/cloud_cli.rs` (real `serve --dev`, device approval, whoami, project creation and API-token creation/use).

## 1. Why a separate product

The repository already deploys apps in three ways, and all three keep working unchanged:

| Existing                                                      | What it does                                                                 |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `lk infra` and `lk deploy` (`crates/leptoskit_cli/src/infra`) | The app author provisions their own VM with OpenTofu and Kamal.              |
| `lk console serve` (`leptoskit_deploy_console::control`)      | A self-hosted deployment service for one owner.                              |
| The hosted pilot (`leptoskit_deploy_console::hosted`)         | An operator-enrolled broker: customers bring their own compute and a worker. |
| `lk publish` (`crates/leptoskit_cli/src/publish`)             | Uploads to six stores from the developer's machine.                          |

The cloud adds public sign-up, organisations and teams, shared compute on Kubernetes, cloud builds, managed Postgres, custom domains, metering and billing, and store publishing from cloud build machines. [The deployment control plane note](deployment-control-plane.md) said, under "Hosted operation", not to turn the single-owner executor into a multi-tenant one by adding an organisation ID. The cloud is the separate design it asked for.

What makes it ours rather than another host:

1. **One file.** `leptoskit.toml` already describes the server, database, services, native apps and stores. `[cloud]` adds only placement and scale, so nothing is declared twice.
2. **One release, many targets.** A release is the server deployment, the over-the-air update and the store builds, with one version and one rollback. A fingerprint of the native inputs decides whether a change can go over the air or needs a store build.
3. **Show the workings.** Every screen can reveal the config table, the Kubernetes objects, the build steps and the cost behind it, as [the admin design](admin-design.md) does. The cost shows before a deploy, and a spend cap is on by default.
4. **Honest limits.** Regions, the provider, cold-start time and what happens at a cap are stated. Rollback exists from the first release; [Serverpod Cloud](https://www.serverpod.dev/cloud) has none.
5. **Store releases signed by the developer's wallet.** The Solana dApp Store needs the publisher's wallet to sign prepared transactions. The cloud prepares them and the developer signs; the cloud never holds the wallet.
6. **Agents first.** Every action is a typed RPC operation with an OpenAPI export, a generated CLI and scoped tokens.

No core crate (`leptoskit`, `leptoskit_native`, …) depends on a cloud crate. The pilot's existing `leptoskit-cloud` binary in `leptoskit_app` keeps its name.

### Where the shared types live

`Slug`, `Size`, `Scale`, `Sleep`, `DatabaseSize`, `Backups` and `Region` are defined once, in `leptoskit_config::cloud`, and `leptoskit_cloud::slug` and `leptoskit_cloud::size` re-export them. Config has to validate `[cloud]` with these types, and `leptoskit_cloud` reads the resolved table for the estimate, so the definitions sit in the crate both already depend on. Putting them in `leptoskit_cloud` would have made config depend on a cloud crate, which the rule above forbids. Config builds for wasm with light dependencies, so the dashboard pays nothing extra.

## 3. Technology choices

- **API.** `leptoskit_rpc` operations over `leptoskit_db`, as `leptoskit_notifications` does: typed operations, live queries for deploy timelines and logs, durable jobs with retries and cron for builds and billing, idempotency keys, and an OpenAPI export. The control plane is an app, not a `[services]` service, so its operations carry no `service = "…"`.
- **Database.** Postgres in production and SQLite for tests and single-node self-hosting. Both migration directories ship.
- **Identity.** `leptoskit_auth` for people (email codes, passkeys, GitHub and Google, Solana wallets), and `leptoskit_idp` for the CLI's device-code sign-in. Organisations, memberships, invitations and API tokens are cloud tables, not additions to `leptoskit_auth`.
- **Runtime.** Kubernetes, one namespace per environment. Tenant pods run under a [gVisor](https://gvisor.dev/docs/architecture_guide/platforms/) RuntimeClass with a default-deny NetworkPolicy, a ResourceQuota, no service-account token and the restricted Pod Security profile. Each `[services.<name>]` becomes its own Deployment and Service. [KEDA](https://keda.sh/) scales, with its [HTTP add-on](https://github.com/kedacore/http-add-on) for sleeping when idle.
- **Nodes.** [k3s doesn't run embedded etcd across its multicloud WireGuard overlay](https://docs.k3s.io/networking/distributed-multicloud), so control-plane servers share one private network, and workers join from anywhere over `wireguard-native`. Launch is one bare-metal server; growth is three small VMs as the control plane with bare-metal workers. Each node admits only the peers and ports the topology needs, plus administrator addresses on SSH and the API. Cloud nodes get this from a provider firewall and existing machines from a generated nftables file. Cloud nodes' addresses exist only after `tofu apply`, so generation has two phases: the OpenTofu configuration, then bootstrap and peer lists rendered from it and OpenTofu's outputs.
- **Cluster access.** The control plane never holds a cluster's credentials. A `cluster` worker runs inside each cluster with a scoped ServiceAccount, connects outward, and claims release jobs. The same mechanism attaches a customer's own cluster later.
- **Builds.** Customer code never builds in the control plane or on a shared daemon. A `build` worker runs each job in a fresh sandbox (an ephemeral VM, or a gVisor pod with rootless BuildKit) and destroys it afterwards. macOS workers are a separate pool.
- **Tenant Postgres.** [CloudNativePG](https://cloudnative-pg.io/). By default each environment gets a database and a login role on a shared cluster; paid sizes get their own instance. WAL goes to object storage.
- **Edge.** Cloudflare in front, default hostnames under a wildcard, and custom domains through [Cloudflare for SaaS](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/), or cert-manager for an operator without Cloudflare. Object storage is S3-compatible (R2 or [B2](https://www.backblaze.com/cloud-storage/pricing)) through the existing `rusty-s3` seam.
- **Money.** Stripe: a flat plan price plus metered usage. Prices are operator configuration, never constants in code. Reaching the spend cap stops new work and sleeps what can sleep. It never deletes data.
- **Secrets.** Envelope encryption with AES-256-GCM-SIV, as `leptoskit_auth` and `leptoskit_deploy_console` already use. Each organisation has a data key wrapped by a master key from the environment; a KMS adapter can replace that later. Organisation, project and secret name are authenticated data. A value leaves the vault only as a lease for one job on a single-tenant worker.

The launch substrate is self-managed k3s on one [Hetzner AX41](https://www.hetzner.com/dedicated-rootserver/matrix-ax/) (about €59 a month, and bare metal, so `/dev/kvm` exists), gVisor, CloudNativePG, Cloudflare's free plan plus Cloudflare for SaaS, R2 or B2, and owned Mac minis for Apple builds. That puts a sleeping hobby app at roughly $0.15–0.30 a month and an always-on small app at $3–4. None of it is hard-coded: the platform crate reads it as configuration.

## 4. Vocabulary

- **Organisation**: the billing and membership boundary. Signing up creates a personal one.
- **Member**: a person in an organisation, with a role: `owner`, `admin`, `developer`, `billing` or `viewer`.
- **Project**: one leptoskit app, one `leptoskit.toml`. Its slug is unique within the organisation.
- **Environment**: a running copy of a project, such as `production`, `staging` or a preview. It owns its database, secrets, domains and scale.
- **Deployment**: one attempt to put one build of the server into one environment. Immutable once created, and numbered per environment.
- **Build**: one run on a build worker, for the server or a native target.
- **Release**: a version of the whole app: a deployment, plus an optional over-the-air update and store submissions.
- **Worker**: a `build` or `cluster` process paired with the control plane.
- **Cluster**: a place environments run, in a region.

Identifiers are UUID v7. A slug is 3 to 40 characters: lower-case letters, digits and single hyphens, starting with a letter and ending with a letter or digit. `api`, `www`, `admin`, `cloud`, `console`, `app`, `status` and `docs` are reserved. `Slug::suggest` turns a name such as "My Notes App" into `my-notes-app`.

### Sizes

| Size | CPU request / limit (millicores) | Memory (MiB) |
| ---- | -------------------------------- | ------------ |
| `xs` | 100 / 500                        | 128          |
| `s`  | 250 / 1000                       | 256          |
| `m`  | 500 / 2000                       | 512          |
| `l`  | 1000 / 2000                      | 1024         |
| `xl` | 2000 / 4000                      | 2048         |

These are the defaults in code, as methods on `Size`; an operator override can come later. A `Scale` holds `min` and `max` with `min ≤ max`, `1 ≤ max ≤ 20`, and `min = 0` meaning the process sleeps when idle. `DatabaseSize` is `shared` (a database on the shared cluster) or `s`, `m` or `l`, dedicated instances with 1, 2 and 4 GiB.

### Deployment states

```text
queued → building → migrating → rolling_out → live → superseded
   ↘          ↘        ↘            ↘
    failed { stage, blocker }              cancelled (from queued or building)
```

- A rollback is a new deployment whose source names an earlier one, and it goes from `queued` straight to `migrating`. `DeploymentState::can_become` allows that edge; `DeploymentState::advance` also checks the source, so an upload can't skip its build.
- `failed` records the stage it failed in and a `Blocker`: `build_failed`, `builder_unavailable`, `schema_incompatible`, `migration_failed`, `not_ready`, `quota_exceeded`, `spend_cap_reached`, `payment_required`, `cluster_unavailable`, `interrupted` or `secret_unavailable`. Each has a stable code for errors and the wire.
- A worker that dies mid-job leaves the deployment `failed` with `interrupted` only after an operator or the reconciler has confirmed what the cluster is actually running. An expired lease doesn't prove the old process stopped; see "Durability" in [the control plane note](deployment-control-plane.md).
- A queued deployment fails, in the `queued` stage, only for a reason that stops it before any work starts: `builder_unavailable`, `quota_exceeded`, `spend_cap_reached` or `payment_required` (`Blocker::fails_queued`). Every other blocker needs the stage it names, so a deployment never fails `queued` with, say, `migration_failed`.

### Deployment sources

`upload { archive }` (a source archive's digest), `git { repository, commit }` (an `https` address and a full commit ID), `template { name }` (the cloud scaffolds a starter with `lk new`, for a first deploy with no local setup), and `rollback { deployment }`.

### The source archive

The CLI packs and the build worker unpacks, both with `leptoskit_cloud::archive` behind its `archive` feature.

- **Which files.** `git ls-files --cached --others --exclude-standard` in a Git checkout, otherwise a walk that honours `.gitignore`. A `.leptoskitignore` at the project's root excludes more, with `.gitignore` syntax. `target/`, `.leptoskit/`, `.git/`, `dist/` and `node_modules/` are always left out, at any depth.
- **Deterministic.** Sorted paths, zero modification times and owners, modes of 0644 or 0755, and a gzip header with no time or OS. The digest is the SHA-256 of the compressed bytes, written `sha256:<hex>`. Two packs of the same files give the same bytes on the same build of the crate; a different compressor version may not.
- **Bounds.** At most 20,000 files and 512 MiB uncompressed; a file over 64 MiB fails with its path.
- **Paths.** Absolute paths, `..` components, backslashes and symlinks that leave the root are refused on both sides. A link is followed through the archive's own other links, never the filesystem, so packing and unpacking judge it the same way, and a loop is refused after 40 hops.
- **Secrets.** `.env`, `.env.*`, `*.pem`, `*.p8`, `*.p12`, `*.jks`, `*.keystore` and `credentials*.toml` are refused, naming every such file and pointing at `lk cloud secret set`, unless `.leptoskitignore` already leaves them out. A file Git ignores never reaches the list.
- **Unpacking** goes into an empty or missing directory, creates each file only if it doesn't exist, counts directories towards the file limit, checks sizes against the headers before writing, and never runs anything. Links are checked after every entry is read and created last. Hard links, devices and FIFOs are refused, as are Git submodules when packing.

## 5. `[cloud]` in `leptoskit.toml`

```toml
[cloud]
project = "notes" # written by `lk cloud launch`
organization = "acme" # optional; the signed-in person's own organisation by default
region = "eu-central" # optional; the cloud's default region by default
url = "https://cloud.leptoskit.dev" # optional; for a self-hosted cloud

[cloud.database]
size = "shared" # shared | s | m | l
backups = "daily" # daily | continuous

[cloud.environments.production]
size = "s" # xs | s | m | l | xl
min = 1
max = 3
sleep = "never" # never | when-idle; when-idle needs min = 0
domains = ["notes.example.com"]

[cloud.environments.production.services.search]
size = "m"
min = 1
max = 2
```

`CloudConfig::resolved` turns this into a `ResolvedCloud`, where every default is filled in and every rule below has held. `LeptoskitConfig::validate` runs it whenever the config loads, so every command refuses a bad table with `invalid [cloud]: …` and the table and key at fault.

- **Defaults.** With only `[cloud] project = "…"`, production runs at `xs`, `min = 0`, `max = 1`, sleeping when idle, on a shared database when the app has `[db]`. `production` always exists, even when no table names it.
- **Filling in.** Writing only `sleep` sets `min` (0 for `when-idle`, 1 for `never`); `max` defaults to `min`, or 1. `sleep = "when-idle"` with `min > 0`, `sleep = "never"` with `min = 0`, `min > max`, `max = 0` and `max > 20` are errors.
- **Databases.** `[db]` decides whether there is a database and which dialect. `[cloud.database]` without `[db]` is an error. A SQLite app gets a persistent volume and one replica, so `max > 1` is an error that names Postgres; that holds for a service with `database = true` on SQLite too. SQLite can't take a dedicated size or continuous backups.
- **Services.** `[services.<name>]` decides the processes. A cloud table for a service that doesn't exist is an error, and remote services (`url = …`) take no cloud settings. A service without a table follows the app: it sleeps when the app sleeps and keeps one replica when the app keeps any.
- **Live connections.** Sleeping closes live connections. When the app shows it serves them (`rpc.live.relay_url_env`, `rpc.live_path`, or `db.live_capture = "replication"`), the default becomes one replica that never sleeps, and an explicit `when-idle` or `min = 0` is refused unless the environment says `allow_sleep_with_live = true`. The error names the setting it found.
- **Domains.** Lower-case, fully qualified hostnames with no wildcard, port or trailing dot. The same hostname can't appear twice in one environment or in two environments. `leptoskit.app`, `leptoskit.dev` and their subdomains are the cloud's own and are refused.
- **Names.** Environment names are slugs, so `qa` is too short. `url` must be `https`, or `http` on localhost, with no path, query, fragment or credentials.
- **Alongside `[infra]`.** `[cloud]` and a managed `[infra]` can coexist: `lk deploy` uses the cloud when `[cloud].project` is set, and `lk infra …` keeps addressing the app's own infrastructure. `[cloud]` together with `infra.control_url` is an error, because both would claim `lk deploy`.
- Spend limits, secrets and billing never live in the repository.

| `operator` (operators only)  | `clusters`, `register_cluster`, `workers`, `jobs`, `issue_pairing`, `revoke_worker`, `reconcile`                                                                                                                                                                                |

- Mutations that start work take an idempotency key and return the same result for a repeat. An operation whose result is a secret is an action instead, because a receipt keeps the result: see `create_token` below.
- Destructive operations take an explicit confirmation argument, and scoped tokens can't call them unless the scope names them.
- Errors are `rpc::Error` variants whose message starts with the blocker's stable code.
- Secrets are write-only. No operation returns a secret's value.
- Token scopes are `read`, `deploy`, `manage` (config and domains), `publish`, `billing` and `admin`. A token belongs to an organisation and optionally one project, is hashed at rest, is shown once, and expires by default.

### Accounts, tokens and projects as built (Control 1)

The `account`, `tokens` and `projects` operations are declared at the top of `leptoskit_cloud` (`account.rs`, `tokens.rs`, `projects.rs`), so the CLI and the dashboard call them without the server; their bodies, identity and authorisation are under `server/`. The rules below are what the code and its tests hold.

**Identity.** `server::CloudIdentify` checks a request's credentials in this order, and the first that holds decides who is calling:

1. a `leptoskit_auth` session: the browser's cookie, or a session token as a bearer;
2. the CLI's device-flow access token, which `leptoskit_idp`'s layer has already turned into a delegation, accepted only for the first-party CLI client (`server::CLI_CLIENT_NAME`, registered once at start, found again by name on every later start);
3. an API token, `lkc_<prefix>_<secret>`, as a bearer.

Anything else, including an unknown, malformed, expired or revoked credential, is anonymous, and every operation answers an anonymous caller `401 sign_in_required`. A malformed bearer that looks like a JWT is refused by `leptoskit_idp` first with `401 invalid_token`. The audit log records how a person called (web or CLI) or which token, never its value. A live socket keeps a token's identity for at most a minute before checking it again, so revocation reaches a socket that late.

**Permissions.** `access.rs` holds the one table; `server/authorize.rs` is the only code that applies it, reading the organisation, the caller's membership and the role from the database on every call. A "person" is someone signed in with a session or through the CLI's device-flow delegation; an API token is never one.

| Permission            | Level        | owner | admin | developer | billing | viewer | Token scope         |
| --------------------- | ------------ | :---: | :---: | :-------: | :-----: | :----: | ------------------- |
| `view_organization`   | organisation |   ✓   |   ✓   |     ✓     |    ✓    |   ✓    | any                 |
| `view_projects`       | project      |   ✓   |   ✓   |     ✓     |    ✓    |   ✓    | any                 |
| `manage_members`      | organisation |   ✓   |   ✓   |           |         |        | none: a person only |
| `manage_owners`       | organisation |   ✓   |       |           |         |        | none: a person only |
| `manage_tokens`       | organisation |   ✓   |   ✓   |           |         |        | none: a person only |
| `create_project`      | organisation |   ✓   |   ✓   |     ✓     |         |        | `manage`            |
| `manage_environments` | project      |   ✓   |   ✓   |     ✓     |         |        | `manage`            |
| `delete_project`      | project      |   ✓   |   ✓   |           |         |        | `admin`             |
| `delete_environment`  | project      |   ✓   |   ✓   |           |         |        | `admin`             |

`Permission::requires_person` marks the three person-only permissions, and `Access::require` refuses a token for them with `403 person_required` before it looks at the role or the scopes. Who is in an organisation, with what role, and which tokens act in it are the authority to act there: a token that could invite someone, change a role or make a token could turn itself into a membership or a credential that outlives its own scopes, expiry and revocation. So a token can't make or revoke tokens either, whatever its scopes; the `admin` scope means deleting projects and environments, and nothing else.

- A token has a permission when one of its scopes grants it _and_ its maker's current role does, so a demotion or removal takes effect on their tokens at once; removing a member also revokes their tokens. A token bound to a project has no organisation-level permission except `view_organization`, and every other project is "not found" to it.
- `access::OPERATIONS` lists every served operation with its requirement. `tests/authorization.rs` checks that list against everything the server's router serves (`leptoskit_rpc::server::registrations_in(None)`, nothing filtered, the `rpc.*` operations included) and that the OpenAPI document publishes nothing else. It then runs every operation as a person with each role, as that person through the CLI, as a token for each role × each scope × bound to a project or not (60 tokens; a token whose maker isn't an owner or admin is made by an owner who is then demoted, which is how one comes to exist), and as nobody, and checks each answer's status and code against the table, so an operation without a decided permission fails the build.
- Seeing comes before being allowed: an organisation or project the caller can't see is `404 organization_not_found` / `project_not_found`, worded the same whether or not it exists. Then a token asking for a person-only permission is `403 person_required`, and a missing permission is `403 insufficient_role`, `insufficient_scope` or `project_token`, in that order. Organisations, projects and environments are named by slug; the IDs that name a member, an invitation or a token are looked up only inside the organisation already authorised, so another tenant's ID is the same `404` as a made-up one.
- Deleting a project takes `confirm` equal to its slug, and an environment its name (`409 confirmation_mismatch` otherwise), plus the `admin` scope by name for a token. Production can't be deleted (`403 production`).

**Organisations and members.** The first call from a person makes their personal organisation. Its slug is tried in this order: their primary verified address's local part made a slug (`ana`), or `personal` without a usable one; then `ana-2` and `ana-3`; then `ana-` and ten random hex characters (40 bits), up to eight times. A reserved or taken slug moves on to the next. The friendly slugs stay derivable from an address, because the console shows the slug and a recognisable one is friendlier, so anyone who knows an address can take them first; that only moves its person to a random slug nobody can take in advance, so nobody can stop another person's first sign-in. Running out of random slugs means the server's randomness is broken, and is a `500`. A unique `personal_owner` column makes the organisation once however many first requests race: a request that loses looks again and finds the winner's. Slugs refuse the console's route words: `sign-in`, `device`, `welcome`, `invitations`, `todo`, `account`, `organizations` and `operator` for organisations; `new` and `settings` for projects; `releases`, `stores`, `publish`, `sign`, `settings`, `ship` and `logs` for environments. Only owners make or unmake owners, and the last owner can't be demoted or removed (`409 last_owner`). A person may remove themselves (leave) without `manage_members`, subject to that; a token removing its own maker is managing members, and refused. Concurrent changes keep an owner: the changes run serializable, so when two owners demote or remove each other at once, the one that runs second finds its caller no longer an owner.

**Invitations.** An invitation is a single-use token, 32 random bytes in hex, stored as its SHA-256 and mailed once in plain text through the auth `Mailer` after the transaction commits. It lasts seven days, and an organisation has at most 100 pending. The rules:

- Only a person invites, and only to a role they may give (`Role::may_give`): `manage_members`, and `manage_owners` for the owner role.
- Inviting an address again revokes its pending invitations, and the inviter must be allowed to give each of their roles too, so an admin can't cancel an owner's invitation by re-inviting the address as a viewer. Each revoked invitation gets its own `invitation.revoke` audit entry naming the one that replaced it.
- An invitation is only as good as its inviter's authority when it is accepted: accepting checks that the inviter is still a member whose role may give the invited role, and otherwise answers like an unknown invitation.
- Demoting or removing a member revokes, with an audit entry each, the pending invitations they sent that their new role can't give, so the list stays truthful and re-promoting them doesn't revive old invitations.
- Accepting needs a person whose verified address is the invited one. Unknown, used, revoked, expired, wrongly addressed and outranked invitations all answer `404 invitation_invalid`, so the token proves nothing. Accepting again, or as someone already a member, changes nothing and keeps their role.

**Tokens.** A token is `lkc_`, 12 lower-case hex characters that find it, `_`, and 64 that prove it. Only the SHA-256 of the secret is stored, compared in constant time, and the value is returned once, by `create_token`. Lifetimes are 30, 90 (the default) or 365 days. `last_used_at` is written at most every five minutes. Revoking is immediate. Only a person makes, lists or revokes tokens, and can't make one stronger than themselves: scopes their role can't grant are `403 token_too_strong`. An organisation has at most 200 live tokens.

`create_token` is an `#[rpc::action]`, not a mutation, because a mutation's receipt stores its whole result for a repeated `Idempotency-Key`, and this result is the secret. The action runs the work as an unregistered mutation operation through `ActionCx::mutate`, so the token row and its audit entry still commit in one serializable transaction with the usual retries, and nothing is kept for a repeat. Instead, a live token's name is unique in its organisation, checked in that transaction. A retried `create_token` (the same name, sent again because the answer was lost) is refused with `409 token_name_taken`, which names the first token's prefix, creation time and ID and says that nobody saw its value: revoke it and ask again. A retry never makes a second token its caller can't tell from the first, and the header is ignored. The other operations return no secret, so their receipts hold nothing secret: the invitation's link is only mailed, after the commit, and a receipt keeps a hash of the arguments, never the arguments.

**Projects and environments.** `create_project` takes the slug, the region (default from the operator's configuration) and the targets and variable names the CLI detected (never values), records them, and makes the `production` environment asleep. An organisation has at most 200 projects and a project 50 environments. `update_environment` takes the revision the caller read; a stale one is `409 stale_revision`, and a change of scale marks the environment `scale_differs` until a later slice applies it.

**The audit log** gets a row in the same transaction as every change: the actor (account, and token ID when a token acted), how they called, the organisation and project, the action, its target, and the time. Tokens are named by ID and prefix, invitations by ID and address; no row carries a secret. Nothing updates or deletes a row. The database can't enforce that: `leptoskit_db` lets only schema packs declare triggers, so an app's own table has no rule that refuses updates and deletes in both SQLite and Postgres, and the migrations are generated, never hand-written. The convention is held by a test instead (`server::audit::tests::only_this_module_writes_the_audit_log_and_only_inserts`): only `server/audit.rs` names the table's rows, it only inserts, and neither dialect's migrations give the table a foreign key that could delete entries with what they name.

**Operators** are granted and revoked only on the server's command line (`leptoskit-cloud-control operator …`), recorded in the audit log, and reported by `whoami`. The operator operations are described under Control 2 below.

**Discovery.** `GET /.well-known/leptoskit-cloud` returns the CLI client's ID, the scopes it asks for (`openid email cloud`) and the operations' path, so `lk cloud login` needs only the cloud's origin. Device approval is `POST /oauth/device` from a signed-in browser; the console's `/device` page arrives with the UI slices.

**The server.** `leptoskit-cloud-control` (`crates/leptoskit_cloud_app`) reads everything from `LEPTOSKIT_CLOUD_*` variables, listed in [its readme](../../crates/leptoskit_cloud_app/readme.md). Keys, SMTP and the origin have no defaults and it refuses to start without them; `--dev` (debug builds only, loopback only) adds dev sign-in, an in-memory mailbox, a key for the run and migration on start. `serve` refuses a database with pending or unknown migrations; `migrate` applies them.

What `leptoskit_rpc` should offer instead of the action: a mutation whose result is never kept, such as `#[rpc::mutation(receipt = "outcome")]`. That is the same contract `create_token` now builds by hand from unique names. A field-level `#[rpc::redact]` that blanks marked result fields in the stored receipt would also work, but it is easier to forget on a new field than a per-operation switch.

## 7. The worker protocol

- **Pairing.** An operator, or later an organisation for its own workers, issues a one-use pairing code that expires in ten minutes. `pair { code, role, capabilities }` returns a worker key, stored hashed. A worker belongs to the shared pool or to one organisation.
- **Claiming.** `claim` long-polls and returns at most one job matching the worker's role, pool, region and capabilities, with a lease. `renew` extends the lease, `append_log` streams bounded log chunks, and `finish { job, outcome }` is idempotent.
- **Crash safety**, as the hosted pilot's worker does it: the worker writes a pending marker before running a job and the result before acknowledging it. A marker without a result means the effect is unknown, so the worker refuses to repeat the job and it is reconciled rather than replayed. Builds are the exception: their only effect is artifacts keyed by digest, so an interrupted build is retried.
- **Jobs.** `build_server { archive, toolchain, targets }` returns an image digest, web assets and migration fingerprints. `build_native { platform, … }` returns an artifact. `publish { store, submit, leases }` returns a "What to do next" report (`publish::steps::Report`). Cluster workers take `release { spec }`, `scale`, `destroy_environment`, `fetch_logs` and `sample_usage`.
- **Secret leases.** A job that needs a credential gets a lease naming the secret versions. The lease is recorded before release, delivered in the claim response over TLS, and valid for that job only. Where a store's API allows it, the control plane mints a short-lived token so the worker never sees the long-lived key.
- **Tenancy.** A build worker runs one job at a time in a fresh sandbox and keeps no cache another organisation's job can read.

### Deployments and workers as built (Control 2)

The `deployments`, `workers` and `operator` operations are declared in `leptoskit_cloud` (`deployments.rs`, `workers.rs`, `operator.rs`) with plain serde argument and result types: clients and workers never see a table row or an `Id<…>` of a table, and `tables` compiles only with the `server` feature. The bodies are under `server/` (`uploads.rs`, `deployments.rs`, `lifecycle.rs`, `jobs.rs`, `workers.rs`, `logs.rs`, `operator.rs`, `status.rs`, `storage.rs`).

**Migrations.** Each dialect gets a `shipping` migration after `init`, adding the ten new tables and nothing else. Both were generated with the workspace's `lk db migration create shipping --no-renames`, from a temporary `leptoskit.toml` at the repository root (`[db] crate = "leptoskit_cloud"`, with `features = ["server"]` and `migrations = "crates/leptoskit_cloud/migrations"` for SQLite, then `dialect = "postgres"`, `features = ["postgres"]` and `migrations-postgres`), which was deleted afterwards. Inside a mutation, read only through the caller's transaction: SQLite's test database has one connection, so a second handle (`Services::db`) waits for the transaction forever, a hang rather than an error.

**Permissions.** A new permission, `deploy` (owner, admin and developer; the `deploy` token scope), covers `begin_upload`, `complete_upload`, `deploy`, `cancel_deployment` and `rollback`. Seeing a deployment, its events, its logs, the environment's status and a release preview is `view_projects`; `in_flight` is `view_organization`. Worker operations take a worker key only (`403 worker_required` for anyone else, `401 worker_key_required` for nobody), operator operations a person in the `operators` table (`403 operator_required`, and `403 person_required` for a token), and `pair` takes its pairing code as the credential. A worker key reaches nothing else: every organisation operation answers it `403 not_for_workers`.

**Object storage.** `server::ObjectStore` keeps source archives and log chunks in two buckets. In production it is an S3-compatible store (`rusty-s3` signs, `reqwest` sends). For `--dev` and tests it is a local directory the control plane serves itself at `/_leptoskit/storage/<bucket>/<key>`, on loopback only, with HMAC-signed addresses that expire and an upload path that hashes the body as it streams. Keys are made by the server, never taken from a client: `sources/<organisation id>/<archive id>/<sha256 hex>` and `logs/<organisation>/<environment>/<chunk id>`. Presigned addresses are credentials: no table, receipt, event, sheet or `Debug` output carries one, and `tests/deployments.rs` scans every table for their signatures.

**Uploads.** `begin_upload { digest, size }` checks `deploy`, the bounds (`400 archive_empty`, `400 archive_too_large` past `archive::Limits`), and the organisation's storage cap (`409 storage_full`, 5 GiB by default). An archive is the organisation's: two organisations uploading the same bytes each store them, and neither learns the other has. Within one organisation, bytes it already has answer `stored`; otherwise the answer is a `PUT` ticket bound to the size and SHA-256 (the S3 store signs `content-length` and `x-amz-checksum-sha256`), valid for 15 minutes. `complete_upload` checks what the store holds, from its checksum or by streaming the object, before anything may deploy it (`404 upload_missing`, `409 upload_mismatch`, which deletes the object). Begun archives that never complete expire with the ticket; verified ones are kept seven days past their last deployment, and the sweeper deletes expired ones that no in-flight deployment uses.

**Deploying.** `deploy { organization, project, environment, source, config, host }`:

1. refuses Git and template sources (`400 source_unavailable`) and an archive that isn't the organisation's and verified (`404 archive_not_found`);
2. records the signer from the caller's identity, never from the arguments: a person (account and address) or a token (ID, name, prefix and maker), how they called, and the `host` the client names;
3. refuses a second deployment while one is in flight in the environment (`409 deployment_in_flight`, naming it and its state), enforced by a unique `in_flight_environment` column so a race has one winner;
4. checks the `[cloud]` table's project, organisation and region against the target, resolves it (`release::resolve`, `400 invalid_config: …`), and plans the processes (`release::plan`: Postgres needs a cluster with a Postgres server, or it is refused as `postgres_unavailable`; see "Managed Postgres as built");
5. places the environment at its first deployment on the least-loaded cluster in the project's region, ties to the oldest, with its hostname (`<project>-<organization>.<apps domain>` for production); with no cluster there it answers `503 cluster_unavailable` and creates nothing;
6. records the deployment with its number, lines, fine print, the resolved config and plan, and queues a `build_server` job, all in one transaction.

**The lifecycle.** States change only through `DeploymentState::advance`, called from one module (`server/lifecycle.rs`; a test fails if any other server file writes a state). Every change records an event in the same transaction.

| From                 | To                                                        | When                                                                                           |
| -------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `queued`             | `building`                                                | a build worker claims the build                                                                |
| `queued`             | `failed` (`builder_unavailable`)                          | no worker claims it within an hour                                                             |
| `building`           | `migrating`, then `rolling_out`                           | the build succeeds and the schema check passes: one transaction, which also queues the release |
| `building`           | `failed` (`build_failed`)                                 | the build fails, or its output can't become a `ReleaseSpec`                                    |
| `building`           | `failed` (`builder_unavailable`)                          | the build's lease lapses on its third attempt                                                  |
| `migrating`          | `failed` (`schema_incompatible`)                          | the build's migrations don't start with the ones the placement has applied                     |
| `rolling_out`        | `live`                                                    | the cluster worker reports `applied`; the previous live deployment becomes `superseded`        |
| `rolling_out`        | `failed` (`not_ready`, `migration_failed`, `interrupted`) | the cluster worker reports it, or an operator reconciles an unknown release as not applied     |
| `queued`, `building` | `cancelled`                                               | `cancel_deployment`: a queued build is abandoned; a leased one is told at its next `renew`     |

**What `migrating` means.** A leptoskit server applies its own migrations as it starts, before `/readyz` answers, so no step runs migrations apart from the release. `migrating` is the control plane's schema check: the migrations the environment's database has applied (recorded on the placement from each applied release) must be a prefix of the build's. The Migrations line then says "the new server applies N migrations as it starts", is `working` through `rolling_out`, and is stamped `migrated` when the release is live. A release whose outcome is unknown marks the placement `schema_uncertain`, and later releases say so in their fine print.

**Lines and stamps.** A deployment's sheet has a line for the server, one per service, one for migrations and one for web assets, each with a stamp (`pending`, `working`, `built`, `migrated`, `live`, `skipped`, `failed`, `unknown`), a one-line detail, its time, and the build's steps with their durations and cache use. `deployment` returns the sheet with the spec once built; `deployments` lists an environment's or a project's, newest first, in pages; `deployment_events` and `in_flight` are live.

**Rollback** returns an environment to a deployment that was live before and is not live now, reusing its image and spec with no build, only when the database has exactly the migrations that deployment carries, so its server will start (`409 rollback_unavailable` otherwise). It goes straight to `rolling_out` with a release whose migration step is `none`. **`preview_release`** answers the next release's number, hostname, lines and fine print, and a monthly estimate from the configured price catalogue, or `unpriced` with the reason when there is none.

**The worker protocol.**

- **Keys.** A worker key is `lkw_`, 12 hex characters that find it, `_`, and 64 that prove it; only the secret's SHA-256 is stored. It is a fourth kind of caller beside a session, the CLI and an API token, checked before an API token, and re-checked for revocation on every call and on the live socket's lease.
- **Pairing.** An operator issues a one-use code, `lkp_` and 32 hex characters, stored hashed and valid for ten minutes, for a build worker (in the shared pool or bound to one organisation) or a cluster's worker. `pair { code, name, capabilities }` answers the key once.
- **Jobs.** `build_server` (for build workers), `release` and `destroy_environment` (for the worker of the job's cluster). A job carries its organisation and the capabilities it needs; a worker bound to an organisation takes only its jobs, and a cluster worker never takes a second job for an environment while one is leased.
- **`claim { wait_seconds }`** long-polls for up to 20 seconds and leases at most one job for two minutes. A worker holds one job at a time (`409 job_held`). The archive's download address is presigned for each attempt and never stored.
- **`renew`** extends the lease, and answers `cancelled: true` once the deployment is cancelled.
- **`append_log { attempt, seq, lines }`** takes chunks of at most 1,000 lines and 64 KiB, in order (`409 log_out_of_order`); the same chunk again is accepted, different lines under its number are not (`409 log_chunk_conflict`).
- **`finish { attempt, outcome }`** is idempotent: the same outcome again answers `repeated: true`, a different one `409 outcome_conflict`, and an attempt whose lease lapsed `404 job_not_held`.
- **`report_status`** is a cluster worker's report of what one of its environments runs, with up to 500 runtime log lines; `environment_status` and `runtime_logs` read it.

**Crash safety.** The sweeper runs every 15 seconds:

- a lapsed build lease is retried, with a `retrying` event, until its third attempt, then fails with `builder_unavailable`;
- a lapsed release or teardown is never replayed: the job becomes `unknown`, the deployment says so and stays in flight, and it settles when the worker's saved `finish` arrives or an operator calls `reconcile { job, found }` from what the cluster runs (`applied` or `not_applied`); after a reconcile the worker's late finish is `409 already_reconciled`;
- expired archives and log chunks are deleted.

**Logs** are kept as chunks in the store, indexed by rows that number their lines, so `build_logs` and `runtime_logs` page by line number with at most 1,000 lines or 256 KiB a page. Lines longer than 4 KiB are cut. Every line is redacted before it is stored: the store's credentials, any `lkc_`/`lkw_` key's secret, pairing codes, presigned signatures and `Bearer` values. Secrets are looked for across a chunk's lines as well as in each, and control characters are written out, so a log can't drive its reader's terminal. Build logs are kept 30 days and runtime logs 7.

**Deleting an environment** that ever ran queues a `destroy_environment` job for its cluster; a deployment still queued or building is stopped first, and one rolling out, or an unsettled release, refuses the deletion (`409 deployment_in_flight`).

**Operators** list and register clusters (`clusters`, `register_cluster` with its region, runtime class and whether it wakes sleeping processes), list workers and jobs (`workers`, and `jobs`, which defaults to the unfinished ones), issue pairing codes, revoke workers (their leased jobs lapse at once), and reconcile unknown jobs. Each change is audited.

### The worker as built (Worker 1)

`crates/leptoskit_cloud_worker` is the `leptoskit-cloud-worker` binary and the library behind it: the loop every role shares, and the `build` role. It isn't published. Its readme is the operator's reference.

**Commands.** `pair` trades a pairing code for a key and keeps it in the state directory; `run` claims and runs jobs; `forget` clears a job that an operator has reconciled. The control plane's address must be `https`, or `http` on the same machine, and the client follows no redirects, so the key goes only where it was told to.

**The state directory** must be the worker user's own directory and not a link; it is made `0700`, its files `0600`, and it is locked (`flock`) while a worker runs from it. It holds `worker.json` (the address, the key, the worker's ID, name and role), `job.json` (the job in hand, written before it runs) and `result.json` (its outcome, written before `finish`). Every write is a fresh temporary file (never one already there, never through a link), synced and renamed.

**The loop** (`run.rs`). Each turn settles what an earlier run left, then calls `claim`, waiting 20 seconds. For a job it writes the marker, starts renewing the lease every third of it, and starts sending the log. `renew` answering `cancelled` stops the build and the outcome is `stopped`. A `renew` that is refused, or unanswered until the lease has run out, stops the build and reports nothing. Otherwise the outcome is saved, then sent with `finish`, again while the control plane can't be reached and the lease holds. `job_held` from `claim` waits five seconds; a key that is nobody's any more ends the worker (`revoked`). The worker stops after the job in hand at the first signal and at once at the second.

**Crash safety**, as §7 set it out. Started again with a saved outcome, the worker sends it before it asks for anything; an outcome the control plane no longer wants is dropped. A marker without an outcome is dropped for a build, which the sweeper gives out again when the lease lapses, and for any other kind of job the worker refuses to run until `forget`: it never runs such a job twice.

**The log** (`logs.rs`). Lines are read 4 KiB at most at a time, so a build that never ends a line is sent in pieces, and lose their control characters but tabs; they are gathered for a quarter of a second and sent in order in chunks of at most 1,000 lines and 32 KiB. A chunk is sent again while the control plane can't be reached, six times. The build never waits for its log: past 20,000 lines waiting, lines are dropped.

**A build** (`build.rs`, `command.rs`). The archive is downloaded from its presigned address with no key and no redirects, refused at the first byte past the job's `size`, and refused unless its size and SHA-256 are the job's; then `archive::unpack` writes it into a fresh directory under the workspace. A store that doesn't answer leaves the job for another attempt; an archive that is wrong fails the build. The `Builder` trait turns the source into an image. The one implementation, `CommandBuilder`, runs a program the operator names, in the source, with a cleared environment (`PATH`, a fresh `HOME` and `TMPDIR`, and whatever the operator names), an input file that leaves out the archive's address, and an output file the program writes its outcome to. An image named in another repository than the job's is a failed build. The output file is opened without following a link or waiting on a pipe, and believed only as a regular file of 1 MiB at most; a failure's reason is cut to 500 bytes and loses its control characters; every image it names, the app's and each process's, must be in the job's repository. The program leads its own process group, which is ended (`TERM`, then `KILL` after ten seconds) when the build is cancelled or runs past its time, an hour by default, and killed when the program exits and when the worker is stopped at once. The archive's address must be `https`, or on the same machine. Each build's directory is `0700` in a workspace that must be the worker user's and is made `0700`; it is deleted when the build ends, and what a killed worker left is deleted when it next starts.

**Tests.** Unit tests for the address, the state directory, the log's bounds, the download (a byte flipped, added and removed; a store that answers 503) and the build command (the environment, the output file, a wrong repository in the image or a process, a link or a pipe for the output, a long reason, a line that never ends, a time limit and a stop that reach what the program started), an archive address that isn't `https`, a state directory that is a link and a temporary file planted as a link. `tests/worker.rs` runs the worker against a real control plane, built from `leptoskit_cloud`'s own test support: a deployment built from an uploaded archive and taken live, a failing build, a cancelled deployment, a worker that died with an outcome saved and one that died mid-build, a started job of unknown effect, a revoked worker, and the loop stopping when asked. They run on SQLite only.

**Honest limits.**

- **The worker doesn't isolate a build.** The build command runs as the worker's user, can read the worker's key and can reach the network. §3's rule, a fresh sandbox for each job, isn't met: the sandbox (an ephemeral virtual machine, or a gVisor pod with rootless BuildKit) isn't built, and until it is this worker must not build code from more than one organisation, or code its operator doesn't trust.
- A process the build starts outside its process group (`setsid`, or a container a daemon started) outlives the build and is never stopped. Until builds are isolated it can read and change the next build's source and output on the same machine.
- Every variable the operator passes with `--build-env` reaches every build. A registry credential passed that way lets any organisation's build push to any repository it reaches; per-job push credentials from `claim` aren't built.
- A build's log can hold lines that look like the worker's own (`worker: …`): nothing marks the worker's lines apart.
- No build command ships. Nothing here turns a leptoskit project into an image: the scenarios' build command is a shell script that writes an outcome. So no real project has been built by this worker.
- The worker has never talked to a control plane over TLS, or through a proxy.
- The cluster role came with Worker 2, and store publishing with Worker 3.
- A build's cache isn't kept between builds at all, so every build is a cold one.
- Lines dropped from a log aren't counted in the log itself.
- A build left for another attempt holds its lease until it lapses, up to two minutes, and the worker takes nothing meanwhile.

### The cluster role as built (Worker 2)

`crates/leptoskit_cloud_worker/src/cluster.rs` and `postgres.rs`. A worker paired as `cluster` runs every job but a build through `ClusterRole`, in the same loop as a build: the marker before it starts, the lease kept, the log sent, the outcome saved before `finish`. A cancelled deployment doesn't stop a cluster's job; a lost lease abandons it, and the control plane marks it unknown.

**The cluster.** A `Place` gives a `Runtime` for each job, holding the secrets the claim leased to that job. `Kubernetes` is `leptoskit_cloud_runtime::Cluster`, with the pod's service account (or `--kubeconfig`), `ClusterProfile::platform_defaults()` and the rollout deadline (`--rollout-timeout-minutes`, 10). Nothing configures the profile yet.

**A release.** Its policy must keep within the operator's `Bounds` (`--runtime-class`, and the one database server `--postgres-namespace` and `--postgres-port` name), or it is refused before anything is touched. If it has a `DatabaseStep`, which must be named for the release's own environment, the database comes first, with the password from the leased `DATABASE_URL`; then the spec is applied. `Applied` when the runtime says every process is ready; `NotReady` with the runtime's process and reason when one never is; any other failure (the database, the cluster unreachable or refusing) is `NotReady` naming the spec's first process, with the reason. `MigrationsFailed` is never reported: a server whose startup migrations fail never becomes ready, and the worker doesn't tell the two apart.

**The managed database.** `Postgres` connects as the administrator the operator names (`--postgres-url`), over TLS unless `sslmode=disable` (`prefer` is made `require`), with `statement_timeout` and `lock_timeout` of 30 seconds. It refuses any name that isn't `env_` and 32 lower-case hex digits, and a role named otherwise than its database; the cluster role also refuses one that isn't the job's own environment's. A control plane can still name another environment as the job's environment: the worker can't tell that from a real job. The role is made, or reset, as `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS NOINHERIT CONNECTION LIMIT 20 VALID UNTIL 'infinity'` with a SCRAM verifier of the leased password, its settings cleared and its memberships, both ways, revoked; the database is made from `template0`, owned by the role, with its settings cleared and every right revoked from `PUBLIC`, and one another role owns is refused; `CONNECT` and `TEMPORARY` are revoked from `PUBLIC` on every other database that takes connections, once per worker. Each step is checked afterwards and fails the release if it didn't take. Names are quoted as identifiers and literals with `postgres-protocol`'s escaping, and no error repeats a statement. Dedicated sizes fail the release.

**A removal.** The database it names must be the environment's, and the worker must have a database server, both checked first; then the runtime removes the environment's namespace, then the database and its role are dropped (`DROP DATABASE … WITH (FORCE)`, `DROP ROLE`), if they are there.

**Backups and restores** are answered `failed`, which keeps the database as it was.

**Tests.** `tests/cluster.rs` runs a cluster's worker against a real control plane, with a recording fake for the cluster: a release applied and live, one that never becomes ready failing its deployment, one outside the operator's bounds refused, and a deleted environment removed. `tests/postgres.rs` makes a database on a throwaway Postgres 16 and checks the role's attributes, its connection limit, the owner, who may connect where (other databases included), that the password is stored as a SCRAM verifier, a second run with a new password, a role found there with settings and memberships made plain, a database someone else owns refused, the drop, and that other names are refused.

**Honest limits.**

- It has never applied a release to a real Kubernetes cluster: the scenarios use the fake. `leptoskit_cloud_runtime::Cluster` has its own tests against a fake API.
- The cluster's profile isn't configurable; the platform's defaults are used.
- No backup, restore or dedicated database.
- A release's secrets are held in memory while it applies; they aren't written down.
- A cluster job whose lease is lost goes on until it ends or the rollout deadline passes; the control plane marks it unknown, which holds the environment, so nothing runs twice, but the cluster may still be changing while an operator looks.

### Store publishing as built (Worker 3)

`lk publish` already builds every native target a store needs and uploads it in one command, so the cloud runs that command on a build worker instead of splitting it into native build jobs and an artifact store. Native builds therefore have no job of their own: a publish builds what its stores take.

**Operations** (`crate::publishing`, tag `publishing`). The source goes up as for a deploy (`begin_upload`, `complete_upload`). `publish { organization, project, environment, archive, stores, submit }` (permission `deploy`) queues one job and answers a `PublicationSummary`; `publication { …, id }` and `publications { …, limit }` (`view_projects`) read it back with its report; `publication_log { …, id, after, limit }` pages what the run printed. The stores are those `lk publish` knows but the macOS download (`workers::PUBLISH_STORES`), put in its order; `macos` signs with an identity in the keychain of the Mac that builds it, which would be the operator's or another tenant's, so the cloud doesn't publish it; none, an unknown one, or one named twice is `400 invalid_stores`. One publish per environment is queued or running at a time (`409 publish_in_flight`). The spend cap is checked as for a deploy. The archive's expiry is pushed past the latest the job could still run, so the sweeper can't delete it under a queued publish.

**Credentials.** A store's credentials are the environment's own secrets, named as `lk publish` reads them (`LEPTOSKIT_PUBLISH_CHROME_SERVICE_ACCOUNT`, `LEPTOSKIT_ANDROID_KEYSTORE_BASE64`, …): `workers::PUBLISH_CREDENTIALS` lists each store's, and a CLI test checks that list against `lk publish`'s `NEEDED`. These names are the one exception to the reserved `LEPTOSKIT_` prefix for `set_secret`, and no release is given them: `config::for_release` leaves them out, so a store key never reaches the app's pods. Variables that only hold a file's path are left out, since a path would name a file on the worker; a keystore goes as its `_BASE64` variable, which `lk publish` now accepts in place of the path. The credentials that may be a path or the contents (a service account's JSON, the App Store `.p8` key, the Solana keypair) must be the contents: the worker sets `LEPTOSKIT_PUBLISH_CONTENTS_ONLY=1`, and `lk publish` then refuses one that names a file. `publish` keeps only the names the environment has; at `claim` they are leased with `config::lease`, as a release's secrets are, to the one worker that claims the job, and recorded. A name that isn't in the list is never leased, by the control plane or by the worker. A credential removed before the claim fails the publish at the claim, with nothing leased.

**Workers.** A publish job is a build-role job that requires the `publish` capability, and `macos` too for `app_store`. Only a worker bound to the job's organisation takes one (`jobs::takes`), never the shared pool, since nothing isolates one job from the next on a worker and a publish carries store keys. A build worker offered publishes pairs with `--capability publish` and runs with `--publish-command`, a program the operator names; one paired with `publish` refuses to start without it, so it never claims credentials it can't use. The worker keeps the capabilities it paired with in `worker.json`. It is run as a build command is (`command::Launch`: cleared environment, its own process group, a time limit, two hours by default), in the unpacked source, with `LEPTOSKIT_PUBLISH_SOURCE`, `_INPUT` (the job without the archive's address), `_STORES`, `_SUBMIT` and `_OUTPUT`, a fresh `HOME` and `TMPDIR`, and the leased credentials as variables. The simplest program runs `lk publish $LEPTOSKIT_PUBLISH_STORES --json --yes` into `$LEPTOSKIT_PUBLISH_OUTPUT`. A zero exit with a report is `published`; anything else fails, and the log says why. Every log line, and every text in the report, has each credential's value hidden: the value whole (a password from four characters, anything else from eight), and any run of 16 or more of a key's characters that is part of one, so a value cut across the protocol's 4 KiB pieces is hidden too. `finish` holds the report to the stores asked for, 200 steps and 2,000 bytes a text, and a reason to 500 bytes, whatever the worker sent, then hides again every value leased to that attempt (`config::leased_values`, opened from the vault and never sent) and the control plane's own secrets. A publish's log is kept like a build's, counted against the same caps, under its job rather than a deployment.

**Never twice.** A publish may have reached a store before it stopped, so it is never run again: `max_attempts` is 1, a lease that lapses fails it (`may have uploaded to a store`), a worker that died with one in hand drops the marker rather than refusing to start, and one nobody claims within the unclaimed-build time fails. Its lease is held to `publish_deadline` (three hours from its claim), past the worker's own two-hour limit for the program and the fetch before it. Removing an environment fails its queued publishes; one that is running holds the removal off. A publish whose environment is gone by the claim fails there, without holding up the queue. Its minutes are metered as build minutes, macOS minutes when it required a Mac.

**Tests.** `support/publishing.rs`, on SQLite and Postgres: the stores checked and ordered; one in flight per environment; a build worker without `publish` never offered one; the claim carrying only the stores' credentials; the log and the report read back; no table holding a value; an Apple store waiting for a Mac; a lapsed publish failing and never offered again, its late outcome refused; a credential removed before the claim failing it. The worker's unit tests run a publish program: its variables and report, a failure and a missing report, a credential name that isn't a store's never reaching it, and redaction of a value cut across lines.

**Honest limits.**

- No publish program ships, and no build worker on a Mac exists: the tests' program is a shell script. No store has been published to from the cloud.
- The worker doesn't isolate the program, as for builds, and here it runs the organisation's own code with the organisation's store credentials in its environment. That is why only an organisation's own workers publish; the shared pool can once a sandbox exists.
- The control plane hides the leased values in a publish's report and reason, but not in its log lines: those are hidden only by the worker. A short value (an alias, a password under four characters) and an encoded form of a value (base64 of it, URL or JSON escapes) aren't hidden.
- The Solana dApp Store's release needs the publisher's wallet to sign; the wallet signing flow (`signing_request`, `submit_signature`) isn't built, so a cloud publish to `solana` needs the keypair as a credential, which the design says the cloud should never hold.
- `lk cloud publish` and the console's stores page aren't built (CLI 3, UI 3).

### Variables and secrets as built (Control 3, part 1)

`crates/leptoskit_cloud/src/config.rs` declares the six `config` operations; their bodies are in `src/server/config.rs` and the vault is `src/server/vault.rs`.

**Names and limits.** A name is an environment variable's: upper-case letters, digits and underscores, not starting with a digit. An environment has a name once, as a variable or as a secret (`name_is_secret`, `name_is_variable`). Names starting with `LEPTOSKIT_`, and `DATABASE_URL` and `PORT`, are the cloud's and can't be set. An environment has at most 200 variables and 200 secrets; a variable's value is at most 32 KiB and a secret's 64 KiB. Together an environment's variables take at most 256 KiB (names and values) and its secrets 512 KiB (names and sealed values), because a release carries every variable to every process and a cluster keeps a process's secrets in one object of at most 1 MiB (`variables_too_large`, `secrets_too_large`). A refused name is never repeated in its error, because it may be a value sent by mistake.

**Who.** `variables` and `secrets` need `view_projects`. The four that change anything need the new `manage_config` permission: owners, admins and developers, and tokens with the `manage` scope. Every change writes an audit row (`variable.set`, `variable.unset`, `secret.set`, `secret.unset`) naming the name and never a value.

**The vault.** Each organisation has a data key, 32 random bytes made when it first stores a secret and kept wrapped by the newest master key. A value is sealed with AES-256-GCM-SIV under its organisation's data key, bound to the organisation, project, environment, secret row, name and version it was stored as, so a row copied onto another secret, another environment, another organisation, an older version of itself, or a name that was removed and set again doesn't open. The master keys are `LEPTOSKIT_CLOUD_VAULT_KEYS`, newest first, and none of them may be one of the session keys, whatever its ID (`Keys::shares_key_with`). Two first writers race on the data key's unique organisation; the loser gets `vault_busy` (409) and tries again.

**Write-only.** `set_secret` is an `#[rpc::action]`, because a mutation's receipt keeps a hash of its arguments, and these hold the value. `secrets` returns names, versions and times. No operation returns a value, and the tables' sealed columns are `#[db(secret)]`. The value's argument is a `SecretValue`, whose `Debug` is redacted and which refuses anything but a string without repeating it, so a secret sent as a number doesn't come back in the error.

**Reaching a release.** A deployment's `ReleaseSpec` is made when its build finishes: the variables as they are then, written into each process's environment below the names the cloud sets, and the secrets by name only. The values leave the vault in one place: the answer to the cluster worker's `claim` of that release job (`Assignment::secrets`), with a `secret_leases` row per value (job, attempt, worker, secret and version) written in the same transaction, after every value has opened. A build worker never gets them. A rollback re-applies the recorded spec: its variables as they were, its secrets at their current values, and it is refused with `secret_missing` while a name it uses is unset. `unset_secret` is refused while a deployment of the environment is in flight. A release whose secrets can't be read (removed, or the vault can't open them) fails `rolling_out` with `secret_unavailable` instead of holding the cluster's queue.

**Tests** are in `tests/support/config.rs`, run on SQLite by `tests/deployments.rs` and on Postgres by `tests/postgres.rs`: the values reach the release and nothing else (no list, receipt, audit row, event or log); the name and size rules; another organisation's member, a viewer, a build worker and another cluster's worker get nothing; a copied row opens nowhere else; and concurrent first secrets end with one data key.

What this slice doesn't do yet:

- runtime log redaction doesn't know an environment's secret values, so a process that prints one is stored as printed;
- there is no operation that re-wraps data keys after the master key is rotated: old keys must stay listed;
- no worker applies a release yet (Worker 2), so the values have reached only the test worker;
- in `--dev` without `LEPTOSKIT_CLOUD_VAULT_KEYS` the master key is made for the run, and secrets stored before a restart no longer open;
- `set_variable` is a mutation, so with an `Idempotency-Key` its receipt keeps the variable it returned, value included, as long as receipts are kept;
- a secret's value is not wiped from memory after use: it is held in ordinary strings while a request or a claim runs.

### Domains as built (Control 3, part 2)

`crates/leptoskit_cloud/src/domains.rs` declares `domains`, `attach_domain`, `verify_domain` and `detach_domain`; their bodies are in `src/server/domains.rs` and the DNS lookup in `src/server/dns.rs`.

**Hostnames.** A custom domain is a hostname by the rules of §5, at most 232 characters so that its challenge record's name fits in DNS, and nothing at or under the cloud's own names: the reserved domains, the configured apps domain, and the host the control plane is reached at. An environment has at most 20.

**Who.** `domains` needs `view_projects`. The other three need `manage_config`, the permission variables and secrets use, so the `manage` token scope covers them as §6 says. Each change writes an audit row (`domain.attach`, `domain.verify`, `domain.detach`).

**Proof.** `attach_domain` makes the domain pending and answers with a TXT record to publish: `_leptoskit-challenge.<hostname>` holding `leptoskit-verify=<token>`, the token 16 random bytes made for that environment's row. `verify_domain` is an action: it checks the caller, reads the record through a DNS-over-HTTPS resolver outside any transaction, then marks the row in one. The resolver is `LEPTOSKIT_CLOUD_DNS_RESOLVER`, by default [Cloudflare's](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-json/); lookups take at most 5 seconds, follow no redirect, and read at most 64 KiB. A caller who may not change the environment's domains never causes a lookup.

**One holder.** Anyone may attach a hostname, each with a token of their own, and attaching says nothing about who else has. A verified row holds the hostname in a unique column, so of two verifications of one hostname only one commits; the other gets `domain_taken`. Someone else's record in DNS proves nothing for you.

**Reaching a release.** Like variables, domains apply at the next deployment. The spec made when a build finishes routes each verified domain to what the default hostname serves, with `tls: issued`, so the cluster's cert-manager issues its certificate. A domain is marked routed when a release that carries it is handed to the cluster, whether that release is then applied or fails part-way, and stays so until a release without it is applied. Detached while routed, it becomes `removing` and keeps its hold on the hostname until then; only after that can anyone else verify it. A deleted environment's routed domains keep their hostnames until the cluster's worker reports the environment removed, or an operator reconciles the removal. A rollback's recorded routes are cut down to the domains the environment holds now.

**Tests** are in `tests/support/domains.rs`, on SQLite and Postgres, with DNS replaced by a table the test fills: a pending domain routes nothing and a verified one reaches the release; the hostname rules, the limit, and who may do what; one holder per hostname, across organisations and across one project's environments; two verifications racing; a detached domain held until it stops serving, then left out of a rollback; and a hostname held after a release that failed part-way and after its environment was deleted, until the cluster is known to be without it.

What this slice doesn't do yet:

- no real DNS has been asked: the resolver client's parsing is unit-tested, and the scenarios use the test table;
- the domains in `leptoskit.toml` are not attached by a deployment; its sheet says they are served only once attached and verified;
- a verified domain is never checked again, so a domain that changes hands outside the cloud stays with its environment until it is detached;
- nothing checks that the domain points at the environment (the `CNAME` it is told to publish), and nothing reports a certificate's progress;
- custom domains are a Pro feature in §11. A plan's `custom_domains` limit in the catalogue enforces it since Control 4, part 4a;
- an environment that never has another applied release keeps a `removing` domain's hostname until it is deleted, and a removal that never finishes keeps it until an operator reconciles it;
- every verified domain asks the cluster's issuer for a certificate at each release, pointed at the cluster or not, so domains that aren't can use up the issuer account's rate limits for everyone on the cluster;
- the certificate's secret stays in the environment's namespace after its domain is detached, until the namespace goes;
- no cluster has issued a certificate for one.

### Managed Postgres as built (Control 3, part 3a)

`crates/leptoskit_cloud/src/databases.rs` declares `database`; its body and everything a release does with a database are in `src/server/databases.rs`. Backups and restore are part 3b, below.

**What an app gets.** An app whose `[db]` is Postgres gets one database per environment: a database and a login role of the same name on its cluster's shared Postgres server. The name is `env_` and the environment's ID in hex, 36 characters, so no two environments share one and a name is never used again. Only `size = "shared"` is planned: a dedicated instance is refused as `dedicated_database_unavailable`, and a service with `database = true` beside a Postgres app as `service_database_unavailable`.

**Where the server is.** A cluster's facts gain `postgres`: the namespace the server runs in, the host processes connect to, its port, and whether it takes TLS, which must be said. An operator sets them with `register_cluster` or the new `set_cluster_facts`, which checks them (a DNS label, a lower-case DNS name, a port), writes `cluster.set_facts` to the audit log with the facts as they are now and as they were, and refuses to drop `postgres` while an environment keeps a database there (`cluster_has_databases`). Without the fact, a Postgres app's `deploy` fails with `postgres_unavailable` and makes no deployment.

**The control plane never talks to Postgres.** `deploy` decides the name and makes the role's password, 24 random bytes in hex, in the caller's transaction. The cluster's worker makes the database and the role when the release reaches it: `ReleaseInput.database` names both, with the contract in `workers::DatabaseStep`: a role that logs in with the leased password and has no other privilege, a database made from `template0` that it owns and no other role can connect to, `CONNECT` revoked from `PUBLIC` on `template1` and `postgres`, identifiers quoted, and safe to repeat. `DestroyEnvironmentInput.database` names what to drop with the environment. No worker exists yet, so nothing has made a database on a real server.

**The password.** It is sealed with the organisation's data key, as a secret's value is, under a purpose of its own and bound to the organisation, the environment, the database's row and its version: a sealed password copied onto another row opens for nobody, and it never opens as a secret. No operation answers it. `database` answers the name, size, backups setting and whether a release that uses the database has been applied.

**`DATABASE_URL`.** The app's process gets it as a secret, never in the spec's plain environment: `secret_env` names it, and the value is put together when the cluster's worker claims the release, from the cluster's facts as they are then (`postgres://<name>:<password>@<host>:<port>/<name>?sslmode=require`, or `sslmode=disable` when the server takes no TLS; `require` encrypts and doesn't check the server's certificate). It is opened before any lease row is written, and a `secret_leases` row records that it went. When the row, the cluster's fact or the vault's key is missing, or the server has moved since the release was built so that its spec opens the network to somewhere else, the release fails as `secret_unavailable` before any worker is given it. The spec's policy carries the door: the server's namespace and port, which the runtime turns into the one egress rule to it.

**Rollback.** A rollback to a deployment that used the database is given `database` again, with the door and the address where the server is now. It is refused as `rollback_unavailable` when the cluster no longer says where its server is.

**Deleting.** The database's row goes with its environment's. The removal job carries the database's name, so the cluster's worker is told to drop it with the namespace, if it was ever made.

**Migrations and tests.** Each dialect gets a `databases` migration adding the one table. `tests/support/databases.rs` has six scenarios, run on SQLite and on a real Postgres: the first deployment and what it leaks nowhere, a copied password, a rollback and a queued release after the server moved, a failed release whose reason quotes the address, deleting an environment, and the checks on a cluster's facts. `release.rs` and `server/vault.rs` have unit tests for the plan, the spec and the password's sealing.

**Not built, and said so in each release's fine print:** backups on a schedule, whatever `[cloud.database] backups` says; part 3b takes one when asked. Also not built: rotating a role's password, dedicated instances, a service's own Postgres database, and moving a database between clusters.

### Backups and restore as built (Control 3, part 3b)

`src/databases.rs` declares `database_backups`, `create_backup` and `restore_backup`; their bodies are in `src/server/backups.rs`.

**What a backup is.** A row in `database_backups` and a `backup_database` job for the cluster's worker. The control plane never holds a dump's bytes and never talks to a Postgres server: the worker dumps the database with its own connection to its cluster's server, keeps the dump where only it reads, and answers a `location` in its own words and a size. The location is kept on the row and no operation answers it; it returns to that cluster's worker in a restore's input and goes nowhere else. It must be at most 512 printable characters and nothing a log line would redact, such as an address with a password in it, or the backup is recorded as failed and the location kept nowhere. No job of either kind is leased a secret.

**`create_backup`** needs `deploy`. It is refused without a database (`no_database`), before a release has made it (`database_not_ready`), while another backup or a restore of the environment hasn't settled (`backup_in_progress`), and at ten backups taken on request (`too_many_backups`). A restore is refused the same way at ten backups that restores took. A backup is kept for 30 days: the input carries `expires_at`, the worker deletes the dump then, and the sweeper deletes the row. A failed backup doesn't count against the ten. When the dump is reported, the row records the migrations the environment's placement holds, which is what the database held: a cluster's worker runs one job of an environment at a time.

**`restore_backup`** needs `delete_environment`, so owners and admins, and a token only with the `admin` scope: it replaces everything written since the backup. The caller types `<project>/<environment>` back as `confirm`. The backup must be this environment's (any other ID is `backup_not_found`), complete and unexpired (`backup_unavailable`). It is refused while a deployment is in flight (`deployment_in_flight`) or another backup or restore hasn't settled, and as `restore_unavailable` unless the live deployment's migrations start with the backup's, since a leptoskit server refuses a database with migrations it doesn't know and applies the ones it is missing as it starts. It is refused too while either side's migrations are uncertain. While a restore hasn't settled, `deploy` and `rollback` are refused as `database_restoring`.

**The worker's contract** is on `workers::RestoreDatabaseInput`: dump the database as it is, restore the backup into a new database beside the old one, stop the processes, swap the names, start the processes, and drop the old database only when every process is ready; otherwise swap back. So a restore that answers `failed` left the database as it was. The dump of what was replaced comes back as `before_restore` and becomes a backup of kind `before_restore`, kept 30 days, which can be restored in turn. No worker exists yet, so nothing has dumped or restored a real database.

**When a worker goes quiet.** A backup or a restore that no worker has taken for an hour is given up on, so a restore asked for while a cluster's worker is away never runs later, over what was written since. A backup whose lease runs out has failed, and another can be asked for; what its worker says later is refused. A restore whose lease runs out is unknown, as a release is: its environment takes no other job, and nothing deploys, until its worker reports after all or an operator's `reconcile` says which database the environment runs on. There is no restore row: `database_backups` answers the latest restore from its job (`pending`, `restored`, `failed` or `unknown`).

**Deleting.** Backups' rows go with their environment's. A backup or restore that no worker has taken is abandoned, and one a worker holds refuses the deletion. `DestroyEnvironmentInput.database` now also tells the worker to delete every dump it keeps of that database.

**Audit.** `database.backup` and `database.restore`, each with the environment and the backup's ID.

**Migrations and tests.** Each dialect gets a `backups` migration adding the table and the two job kinds. `tests/support/backups.rs` has four scenarios, run on SQLite and on a real Postgres: taking, listing, failing, the cap and expiry; restoring, with every refusal, a developer's and a stranger's attempts, and the backup a restore leaves; a quiet worker for each kind, with all three ways a restore settles; and deleting an environment. `server/backups.rs` has unit tests for the migrations rule, the location check and a failure's reason. The three operations are in the authorisation matrix.

**Not built:** backups on a schedule and point-in-time recovery (`[cloud.database] backups` is still only recorded), deleting a backup before it expires, downloading one, restoring into another environment. A dump's size is limited since Control 4, part 4c. It once waited for metering in Control 4.

### Metering, limits and the spend cap as built (Control 4, part 4a)

`src/billing.rs` declares `plans`, `usage` and `set_spend_cap`; their bodies, the cap and the limits are in `src/server/billing.rs`, and the counting in `src/server/metering.rs`. Nothing here charges anyone: `subscription`, `checkout` and `portal` wait for Stripe in part 4b, and `estimate` for a whole `[cloud]` table came in part 4c.

**What is counted.** The control plane counts from what it sees itself, into `usage_totals`: one row per organisation, project, calendar month (UTC) and meter, with no foreign key, so usage outlives the project it was for.

- Build minutes: when a build worker finishes an attempt, the time from its claim to its finish by the control plane's clock, rounded up to a whole minute, however the attempt ended. An attempt whose worker went quiet is counted when the sweeper takes it back, up to the end of the lease it last held, so a build that never ends is counted like one that does.
- Compute seconds: when a cluster's worker reports what an environment runs, each process's ready replicas times the whole seconds since its usage was last counted, at the size the live deployment planned. A first report counts nothing, a gap longer than five minutes counts as five, and a process the live deployment doesn't have counts nothing. A process is counted up to the release's `max`, however many times a report names it. The part of a second a report leaves over is carried to the next in `environment_statuses.metered_at`.

Each count is written in the transaction that records the finish or the report, so a retry isn't counted twice. Database and object storage, egress, dedicated database hours, macOS build minutes and custom hostnames aren't counted, because nothing reports them yet.

**What it costs.** `usage` prices a month's counts on the plan the organisation is on now, with the arithmetic `estimate` uses: allowances come off, each line rounds once, and the plan's included usage comes off the sum. It needs the new `view_billing` (owners, admins and billing members; a token with the `billing` scope), and answers each project's counts too. A control plane without a catalogue, or a plan the catalogue doesn't have, is unpriced: usage is counted and shown, and nothing is capped or limited. A control plane refuses to start with a catalogue that lacks `hobby`, the plan every organisation starts on, so a misspelt plan can't quietly uncap them all. A meter the catalogue has no price for costs nothing in the bill; `usage` names it in `unpriced`, and on a plan that costs nothing any such usage counts as the cap reached.

**The spend cap.** It is the most a month's usage may cost beyond what the plan includes. A plan's own cap is `spend_cap` in the catalogue, so it is the operator's data and not a constant. `set_spend_cap` sets an organisation's own, or goes back to the plan's, and needs the new `manage_billing`: owners and billing members, and never a token. On a plan whose monthly price is zero the cap is always zero and `set_spend_cap` above zero is `payment_required`. Once the month's usage has reached the cap, `deploy` answers `spend_cap_reached` and makes no deployment. The message doesn't say what the cap is, because a developer or a deploy token may deploy and may not see the bill. Rollbacks, and everything that runs, are left alone: nothing is slept, stopped or deleted yet.

**Limits.** A plan in the catalogue may carry `limits`: `organizations`, `projects` and `custom_domains`. `create_project` and `attach_domain` answer `quota_exceeded` at the limit; domains are counted over every environment the organisation has. `organizations` is read from `hobby` alone: it is how many organisations on that plan one person may have made, their own included, and `create_organization` answers `quota_exceeded` past it. Without it every allowance and limit could be had again by making another organisation. Other limits in §11's table (sizes, sleeping, members) aren't enforced.

**Migrations and tests.** Each dialect gets a `metering` migration adding `usage_totals` and `billing_accounts`, and a `metered_at` one for the column. `tests/support/billing.rs` has three scenarios with made-up prices, run on SQLite and on a real Postgres: counting builds and compute, pricing on a free and a paid plan, the cap refusing a deployment, who may see and set it, the limits, and a build whose lease ran out. `server/metering.rs` and `server/billing.rs` have unit tests for minutes, samples, months and the cap. The three operations are in the authorisation matrix.

**Honest limits.** The month is the calendar month in UTC, not a subscription's own; that comes with Stripe. A plan changed mid-month reprices the whole month on the new plan. Compute is what a cluster's worker reports, so it is as right as that worker; no worker exists yet. The cap is checked when a deployment is made: usage between deployments can pass it.

### Subscriptions and payment as built (Control 4, part 4b)

`src/billing.rs` declares `subscription`, `checkout` and `portal`; their bodies and the provider's events are in `src/server/subscriptions.rs`, and the provider itself in `src/server/payments.rs`. What is sold is a plan, as a [Stripe subscription](https://docs.stripe.com/billing/subscriptions/overview) started on [Stripe Checkout](https://docs.stripe.com/payments/checkout) and managed on Stripe's [customer portal](https://docs.stripe.com/customer-management). The control plane never sees a card. Usage beyond what a plan includes is counted and capped (part 4a) and still isn't invoiced.

**The provider.** `server::Payments` is five questions: a customer for an organisation (told nothing about it but its ID), a checkout page, a portal page, what a subscription is now, and whose a charge was. `server::Stripe` asks Stripe's HTTP API with a key, naming API version `2026-10-28.endive`, and never names payment method types, so the Stripe account's own settings choose them. Tests put a fake in its place. Configuration is `ControlConfig.payments`: the provider, the secret Stripe signs events with, and Stripe's price ID for each plan that is sold. The control plane refuses to start when a price is for a plan the catalogue doesn't sell for money, when a plan that is sold has no `monthly` price or no `spend_cap`, when two plans share a price, when the signing secret isn't `whsec_…` of 24 characters or more, or without a catalogue. `Stripe` sends its key only over `https`, or to this machine. The server binary reads it from `LEPTOSKIT_CLOUD_STRIPE_KEY`, `LEPTOSKIT_CLOUD_STRIPE_WEBHOOK_SECRET`, `LEPTOSKIT_CLOUD_STRIPE_PRICES` and `LEPTOSKIT_CLOUD_STRIPE_AUTOMATIC_TAX`: all of the first three or none. A test key is taken in `--dev`, and elsewhere only with `LEPTOSKIT_CLOUD_STRIPE_TEST_MODE=true`; an event from the other of Stripe's test and live modes is refused. The key and the signing secret are redacted from worker logs. Prices stay operator data: the code holds no price and no price ID.

**Operations.** `subscription` needs `view_billing` and answers the plan, whether this cloud takes payment, which plans are sold, and the subscription's status, period end and whether it ends then. `checkout` and `portal` need `manage_billing`, so owners and billing members and never a token, and answer a page's address at the provider. `checkout` makes the organisation's customer the first time, with the organisation's ID as the idempotency key so two first checkouts make one customer, and keeps it in `billing_accounts.customer`; it answers `already_subscribed` while a subscription runs, `plan_not_sold` for a plan without a price and `plan_not_found` for one the catalogue lacks. `portal` answers `no_customer` before any checkout. Both are actions: who is asking is checked and audited in a transaction, the provider is asked outside one, and a provider that can't be reached is `payments_unavailable`.

**How a plan changes.** In one place only: `subscriptions::apply`, from what the provider says a subscription is now. Leaving the checkout page changes nothing. Stripe posts events to `/webhooks/stripe`, a route that exists only when payment is configured. An event is taken only with a [signature](https://docs.stripe.com/webhooks#verify-events) of its exact bytes by the configured secret, made within five minutes, compared in constant time. An event is then only a reason to ask: the subscription's ID is read from it, the subscription is fetched from the provider, and the organisation is the one whose stored customer the fetched subscription belongs to. Nothing else in an event's body is believed, and metadata maps nothing. While the subscription is `trialing`, `active` or `past_due` the organisation is on the plan its price is for; once it is `canceled`, `unpaid`, `paused` or `incomplete_expired` the organisation is back on `hobby`. A price no plan has changes no plan and is audited as `billing.unknown_price`. Another subscription than the one followed takes its place only when it pays for a plan sold here and the one followed no longer keeps one; a second one beside a running one is audited as `billing.second_subscription` and changes nothing. A subscription ending puts the organisation back on `hobby` only from a plan that is sold, so a plan an operator set by agreement stays. Each event's ID is kept in `payment_events` in the transaction that applies it, so a repeated delivery does nothing; a provider that can't be asked about a subscription answers 503 without keeping the ID, so Stripe sends the event again.

**Late and lost events.** Two answers about one subscription can be written in either order, so after an event is written the provider is asked once more, and what it says then is written if it differs (`subscriptions::follow`, three rounds at most). The sweeper asks about every followed subscription whose paid time ended more than an hour ago while its stored status still keeps a plan, twenty a sweep and the longest unheard of first (`subscriptions::sweep`, `Swept.subscriptions`): a renewal or a cancellation whose event never arrived is caught up with then.

The events followed are `customer.subscription.created`, `.updated`, `.deleted`, `.paused` and `.resumed`, `checkout.session.completed` and `.async_payment_succeeded`, `invoice.paid` and `invoice.payment_failed`. `charge.refunded`, `charge.dispute.created` and `radar.early_fraud_warning.created` write an audit row (`billing.refund`, `billing.dispute`, `billing.fraud_warning`) against the organisation whose customer the provider says the charge was made to, and change nothing else; when the provider can't be asked the note is dropped, not asked for again. Every other kind is acknowledged and ignored.

**Migrations and tests.** Each dialect gets a `subscriptions` migration adding the customer, subscription, status and period columns to `billing_accounts`, and `payment_events`. `tests/support/subscriptions.rs` has three scenarios; the first two run on SQLite and on a real Postgres with a fake provider. One holds who may start a checkout, one customer however many checkouts, unsigned, wrongly signed and wrong-mode events refused, a plan following the provider through active, past due, cancelled and an unknown price, an event's body not being believed, an older subscription ending, the provider being away, a dispute and a refund, and the signing secret in no table. The other holds a second subscription beside a running one, a renewal and a cancellation the sweeper finds, an answer that was old when it was written being put right, and an operator's plan surviving a cancellation. `server/payments.rs` has unit tests for the signature, the two shapes Stripe has sent a subscription's period in, and the checkout request; `server/subscriptions.rs` for which IDs an event is read for. The three operations are in the authorisation matrix.

**Honest limits.**

- `server::Stripe` has never been run against Stripe, not even a sandbox: this session had no Stripe key. Its requests and its parsing follow Stripe's documentation and are tested only for their shape. It needs one run against a [sandbox](https://docs.stripe.com/sandboxes) before anyone is charged, with the Stripe CLI forwarding events.
- Nothing invoices usage. Stripe now points new usage-based integrations at [Metronome](https://docs.stripe.com/billing/usage-based) rather than Billing Meters; which of the two bills what part 4a counts is undecided.
- The usage month is still the calendar month in UTC, not the subscription's period.
- Tax: `automatic_tax` is off unless the operator turns it on, and [Stripe collects none](https://docs.stripe.com/billing/taxes/collect-taxes) until the account is registered where tax is owed. Products need a tax code and prices a tax behaviour, which are set in Stripe.
- A downgrade leaves what exists: an organisation back on `hobby` keeps its projects and domains beyond `hobby`'s limits, and only new ones are refused.
- `past_due` keeps the plan for as long as Stripe's own retry settings keep the subscription alive.
- While usage isn't invoiced, `set_spend_cap` refuses a cap above the plan's own (`cap_above_plan`): the cap is the most anyone can use without paying for it.
- The console has no billing page yet; the pages return to `/<organisation>/settings/billing`, which UI 2 will add.
- `payment_events` rows are never deleted.
- The portal's own configuration (which plans can be switched between, whether cancelling is immediate) is set in Stripe's dashboard.

### Rate limits, the estimate and a backup's size as built (Control 4, part 4c)

**Rate limits.** `src/server/throttle.rs`. Every operation, whether sent alone or over a live connection, is counted by `CloudIdentify` once the caller is known: a person by their account, so the console and the CLI share one count; an API token by its own ID and again with its organisation's other tokens; a worker by its own ID; and a request that is nobody's by the address it came from, which includes one carrying a credential that isn't anyone's, so guessing tokens is slowed too. An IPv6 address counts as its /64. A caller past their rate is answered `429` with `rate_limited` and how many seconds to wait; `leptoskit_rpc::Error` gained `TooMany` for it. The defaults are 600 a minute for a person and for a token, 3000 for an organisation's tokens together, 6000 for a worker and 120 for an address, in `ControlConfig.rate_limits`. `checkout` and `portal` are counted again per organisation, ten pages in ten minutes, after the caller is authorised and before anything is written or the provider is called, so a member who may not ask uses up none of them and a caller past the rate causes no call out.

A live connection is identified once, so `leptoskit_rpc`'s `Identify` gained `admit`, asked before each subscription, mutation, action and stream a connection sends; `CloudIdentify` counts there as it does for a request. A frame refused is answered `429` and the connection stays open.

The address is the connection's own unless `ControlConfig.client_ip_header` (`LEPTOSKIT_CLOUD_CLIENT_IP_HEADER`) names a header a proxy sets; then it is that header's value, which must be one address, with or without a port. A request the header is missing from, or whose header isn't one address, is counted by its connection. The server refuses `x-forwarded-for` and `forwarded` as the header: they are lists the client writes the start of. The same header now reaches `leptoskit_auth`, whose sign-in limits counted the proxy's address before, and which now also falls back to the connection's address.

The counters are fixed windows in the process's memory. Callers who are known and addresses are kept apart. Known callers are never refused for room: there are only as many as there are accounts, tokens and workers. At most 100,000 addresses are counted at once; past that, an address not yet counted shares one count, a hundred times one address's, with the others that found no room. Ended windows are forgotten at most once every ten seconds.

**`estimate`.** `billing::estimate` prices a whole `[cloud]` table, every environment it has, on the organisation's plan or on a named one, with the arithmetic and assumptions `preview_release` uses for one environment. It needs `view_projects`, so any member and any token. It answers `unpriced` without a catalogue, `plan_not_found`, and `invalid_config` for a table that doesn't resolve or is bigger than any real one: `release::resolve` and `release::resolve_all` refuse, before resolving, more than 50 environments, 50 services, 50 hostnames in an environment, and names longer than 100 characters (253 for a hostname). `deploy` and `preview_release` resolve through the same check.

**A backup's size.** `ShippingSettings.backup_cap`, 20 GiB by default. The worker is told it as `max_bytes` on a backup's and a restore's input, and its contract is to stop there, keep nothing and answer `failed`; for a restore, to restore nothing. A dump a worker says is larger is kept as a backup that failed, and a restore's safety dump that is larger is left out, as one with a location that can't be kept already was.

**Tests.** `tests/support/limits.rs` holds a person, a token and an address each running out on their own, and payment pages running out per organisation; `tests/support/billing.rs` holds `an_estimate_prices_a_table`; the backup scenario holds the size. All run on SQLite and Postgres. `server/throttle.rs` has unit tests for the windows, the bound on the addresses, the /64, and the header. The token scenario holds an organisation's tokens sharing a count; `leptoskit_rpc`'s `live_session` test holds `admit`; `release.rs` holds the bounds.

**Honest limits.**

- A control plane run as several processes allows each caller their rate in each process, and a restart forgets the counts. A shared counter (the database's, as sign-in uses, or Redis) is not built.
- Joining a channel and signalling over a live connection aren't counted; `leptoskit_rpc` bounds a connection's frames itself.
- The rates can't be set from the environment yet: the server binary uses the defaults.
- A request with a credential that is nobody's still costs the lookups that find that out before it is refused.
- Nobody outside a test has sent `max_bytes` to a worker: no worker takes a dump yet.

Known and not fixed:

- `sslmode=require` encrypts without checking the server's certificate. Checking it needs the cluster's CA as a fact;
- the door opens every process of the environment to every pod in the server's namespace on its port, a service with `trust = "isolated"` included. Only the password stands between such a service and the database;
- a cluster's `host` isn't tied to its `namespace`: an operator can name a host the door doesn't lead to;
- `set_cluster_facts` replaces every fact, so a call meant for Postgres can drop the runtime class. The audit row shows it;
- a tenant can list the shared server's database and role names, which are environments' IDs, and nothing here limits a database's size;
- a database's lease is recorded in `secret_leases` with the database's ID in `secret_id`;
- no rotation: a leaked address stays good until the environment is deleted. Passwords aren't zeroized in memory;
- log redaction knows the shape of an address, not an environment's own secret values.

## 8. `ReleaseSpec` and the runtime

`leptoskit_cloud_runtime::ReleaseSpec` is the whole desired state of one environment as data, with no reference to plans or prices:

- identity: the organisation, project and environment slugs and IDs, and the deployment number;
- processes: the app, any split roles, and one per service, each with an image digest (never a tag), command, port, health paths, environment variables, secret references, CPU and memory, scale and volumes;
- routes: hostnames and path prefixes to processes, including `/_leptoskit/services/<name>/` for public services and cookie stripping for isolated ones;
- database bindings: which secret holds each process's `DATABASE_URL`;
- policy: the runtime class, egress rules and quota.

`Runtime` is the boundary between the cloud and wherever it runs:

```rust
pub trait Runtime {
	async fn apply(&self, spec: &ReleaseSpec) -> Result<Applied, RuntimeError>;
	async fn status(&self, environment: &EnvironmentRef) -> Result<Observed, RuntimeError>;
	async fn logs(&self, environment: &EnvironmentRef, query: &LogQuery) -> Result<Vec<LogLine>, RuntimeError>;
	async fn destroy(&self, environment: &EnvironmentRef) -> Result<(), RuntimeError>;
}
```

The adapters are Kubernetes (server-side apply, then a watch until the rollout is ready or has failed), local processes for development and the end-to-end test, and a recording fake. Rollouts replace pods with `maxUnavailable: 0`, so a release that never becomes ready leaves the previous one serving.

## 9. The first deploy

```text
lk cloud login       # device code: opens the browser, or prints a URL and code
lk cloud launch      # in a project directory
```

`launch`:

1. reads `leptoskit.toml` and prints what it found: server, database dialect, services, platforms and stores;
2. asks for an `estimate` and prints the monthly cost and the spend cap;
3. creates the project and its production environment, idempotently, and writes `[cloud] project = "…"`;
4. packs the source archive and uploads it by digest, skipping the upload when the cloud already has it;
5. creates the deployment and follows its events: `Uploaded`, `Built`, `Migrated`, `Live`;
6. prints the address, the dashboard link, and what to do next (a custom domain, secrets it noticed in `.env`, stores).

On the web the same thing is: sign up, press **New project**, then **Deploy a starter** (the cloud scaffolds and deploys a template), **Import from GitHub**, or copy the two commands. Later deploys are `lk deploy`. `lk cloud` also has `status`, `logs`, `open`, `env`, `secret`, `domain`, `scale`, `rollback`, `db`, `publish`, `usage`, `token`, `project`, `org`, `whoami` and `logout`, and every command takes `--json`.

The CLI keeps its tokens in a private file under `$XDG_CONFIG_HOME/leptoskit/cloud/` with mode 0600, as the console client does, or reads `LEPTOSKIT_CLOUD_TOKEN` in CI.

## 10. Store publishing

`lk cloud publish [stores] [--submit]` asks the cloud to build each native target on a worker and run the same store clients `lk publish` uses, with credentials from the vault. The result is the same "What to do next" report, shown in the dashboard as a checklist of `agent` and `person` steps.

New stores land in `lk publish`, so they work locally too, in this order: the Solana dApp Store; Huawei AppGallery for Android and HarmonyOS; the Microsoft Store; the Samsung Galaxy Store; the Meta Horizon Store; itch.io and Steam for the game host; then the Amazon Appstore and the Snap Store. Each follows the existing shape: a `[publish.<store>]` table, a client over the `Http` or `Runner` seam, credentials in `NEEDED`, dry-run checks, steps, and tests against a fake server.

## 11. Pricing

Prices are data. The platform crate's catalogue holds each price with its cost basis, source and date, and a target margin; the control plane reads plans and meters from operator configuration and Stripe price IDs from the environment.

`leptoskit_cloud::pricing` holds the shape and the arithmetic, and no prices:

- A `Catalogue` has a currency, plans, and a unit price per `Meter`. It is validated on load: at least one plan, unique plan slugs, a name for every plan, and no allowance for a meter without a price.
- Meters are compute seconds per size, dedicated database hours per size, database and object storage in MB-months, egress in MB, Linux and macOS build minutes, and custom hostname months. Each has a stable code such as `compute_seconds_s`.
- Amounts are integers in the currency's minor unit. A `UnitPrice` is `minor` per `per` units, so a fraction of a cent per second needs no floats. Each line rounds half up once, after the plan's allowance comes off; the total is the plan price plus the usage beyond what the plan includes. Arithmetic saturates instead of overflowing.
- `EstimateInput::from_cloud` turns a resolved `[cloud]` table into a month of usage, and writes down every assumption it made in a sentence the dashboard and CLI can show. A month is 730 hours. A sleeping process is assumed awake 10% of the time, a database to hold 500 MB, and the project to keep 1000 MB in object storage, send 10,000 MB out and build for 100 Linux minutes. Every assumption is a field the caller can change.
- `estimate` prices that usage under one plan. A meter the catalogue doesn't price costs nothing, and the estimate says so; a plan priced by agreement shows usage alone.

Proposed plans, for the owner to decide:

| Plan  | Price                                              | Includes                                                                                                                       |
| ----- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Hobby | free                                               | one project, size `xs`, sleeps when idle, a shared database up to 500 MB, 100 Linux build minutes, default hostname, hard caps |
| Pro   | $20 a month plus usage, with $20 of usage included | teams, custom domains, autoscaling, always-on, continuous backups, store publishing                                            |
| Scale | by agreement                                       | dedicated nodes, or a customer's own cluster                                                                                   |

Suggested unit prices, from comparing [GitHub's runner prices](https://docs.github.com/en/billing/reference/actions-runner-pricing) and [Expo's](https://expo.dev/pricing): $0.005 a Linux build minute and $0.04 a macOS minute. An always-on `m` app with a 1 GB database comes to about $12–15 a month in all.

### Building and running the console

`crates/leptoskit_cloud_app` is both sides of the console. Built with `ssr`, `leptoskit-cloud-control` renders the console's pages beside the API, sign-in and the OAuth provider. The pages sit inside the same session and OAuth layers, so a page reads the same session an operation would. Built with `hydrate` for `wasm32-unknown-unknown`, the library is the client that hydrates those pages. The pages are builder-call components in file routes under `src/routes/`. The only script on a page is the leptos loader for the Wasm.

```sh
# The client: the hydrating Wasm and its loader, into <site>/pkg.
devenv shell -- cargo build -p leptoskit_cloud_app --lib --target wasm32-unknown-unknown --features hydrate --release
devenv shell wasm-bindgen --target web --out-dir target/site/pkg --out-name leptoskit_cloud_app \
  target/wasm32-unknown-unknown/release/leptoskit_cloud_app.wasm

# The server, rendering the pages and serving the client.
LEPTOSKIT_CLOUD_SITE=target/site devenv shell -- cargo run -p leptoskit_cloud_app --features ssr -- serve --dev
```

Without `LEPTOSKIT_CLOUD_SITE`, the pages render but don't hydrate. In `--dev`, the code for `/sign-in` is listed at `/_leptoskit/mail`. The fix for cloud-design.md §19 gap 15 (every render in the browser replaced the page's `<main>`, so a field lost focus after one keystroke) is in `leptoskit_native` as its own pull request against `main`; until that merges and this stack is rebased on it, the console still shows the fault.

A page rendered on the server calls its operations in process, through the one server `leptoskit_rpc` has installed for the process. The binary starts one control plane, so this holds there. `tests/console.rs` starts one per test, so its tests take turns (`one_server`); a second control plane in one process would render pages against the wrong database, and `leptoskit_rpc` has no per-request server yet.

- **Layers.** The OAuth provider answers discovery, tokens and the device flow from its layer, not from routes, so the binary builds every route it adds (the probes, and the pages with `ssr`) in full, applies `auth.layer()` and then `idp.layer()` last, and hangs that as the fallback of `Control::router()`, which `Control::start` has already layered the same way. Nothing is merged afterwards: in axum, merging a router whose fallback is the default swaps in its unlayered one, and the provider's endpoints answer 404. `tests/binary.rs` checks them on the real binary. Once `Control` hands out its routes unlayered, the binary can merge them all and layer once.
- **Routes.** `src/routes.rs` is generated. Run `lk plugin:router routes` in the crate after adding or moving a route file; `tests/routes.rs` fails while it's stale. Every first path word the console uses must be in `RESERVED_ORGANIZATION_SLUGS`, and the same test checks that too.
- **Operations that don't exist yet.** `src/data.rs` puts each one behind a trait, with `NotAvailableYet` as its only implementation, and the screens say "not available yet" rather than show a guess. Replace the implementation when the operation lands (cloud-design.md §20 #3 and #9).
- **Queries.** `Console::new` makes every query once, inside the page's `Suspense`, keyed by the route alone. The server numbers the answers it hands the browser in the order the queries start, and the browser starts each one as it's made, so a key that waits on another query's answer makes hydration read the wrong answers and fail. The server also may finish the page before such a query answers, so the page it sends and the browser's first render can differ. The one exception, the projects of the person's own organisation away from its pages (for the rail, `/welcome` and `/device`), waits on `whoami`: it's made last and asked only once the page is live, so `/welcome` shows its sheet and moves on in the browser if the account turns out to have projects. `tests/console.rs` checks the order on every page, and that only an organisation's own page hands over its projects.
- **Tests.** `tests/screens.rs` draws every screen headless from a filled query cache. `tests/console.rs` serves the console with the control plane on a real port. `cargo nextest run -p leptoskit_cloud_app --all-features` runs both.

## 13. Honest boundaries

What the code doesn't establish, and the docs mustn't claim until someone has done it for real:

- no cluster has been provisioned, no customer billed (the Stripe client has never called Stripe, sandbox included), and no store has received an upload from a cloud worker;
- [Apple's macOS licence](https://www.apple.com/legal/sla/docs/macOSSequoia.pdf) restricts running other people's builds on our own Macs, and needs legal review before a macOS pool is offered;
- isolation is designed around gVisor and single-tenant build sandboxes, and hasn't had a security review;
- the control plane has run only in tests and `--dev`. Its accounts, its deployments and its vault have each had one review, whose findings are fixed (§6, "Security review of Control 1"; §7, "Security review of Control 2", "Security review of Control 3, part 1", "part 2", "part 3a" and "part 3b"), but no external audit, and the operations' rate limit is kept in each process's memory, beyond sign-in's own;
- the default domains (`cloud.leptoskit.dev`, `*.leptoskit.app`) are configuration defaults, not registered infrastructure.
