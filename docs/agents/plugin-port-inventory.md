# Plugin port inventory

Maintainer ledger for porting system capabilities into leptoskit runtime plugins. The public, user-facing support matrix lives in [`docs/src/platforms/plugin-inventory.md`](../src/platforms/plugin-inventory.md); this file keeps the research snapshot, verification evidence, the upstream inventories, and the completion gates for each port.

Research snapshot: **20 October 2026**. This is a scope and acceptance ledger, not a platform-support announcement. The upstream inventories change; recheck their linked reference pages when beginning a port.

The API families below come from the [Expo SDK reference](https://docs.expo.dev/versions/latest/) and [Tauri official plugin catalog](https://v2.tauri.app/plugin/). The crate boundaries, priorities, and acceptance requirements are LeptosKit design proposals. They do not imply upstream compatibility. “Port” means providing the useful system capability through idiomatic Rust APIs and the LeptosKit host, without running a hidden React Native or Tauri application.

## Status vocabulary

| Status            | Meaning                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------- |
| Partial           | Source implements the explicitly named subset. Other methods and platforms remain open.                   |
| In progress       | Active implementation work; no release or platform coverage is asserted here.                             |
| Planned           | No completed runtime plugin is recorded in this inventory.                                                |
| Framework/tooling | Belongs to rendering, application lifecycle, or build tooling rather than an independent runtime service. |
| Migration only    | Document the replacement; avoid preserving a deprecated API indefinitely.                                 |

Each runtime plugin should remain its own crate. Platform implementations may live in that crate as Rust modules, a Swift package, and Kotlin sources. An internal shared codec or native helper does not turn unrelated plugins into a single omnibus dependency.

### Infrastructure and distribution

| Component                                   | Implemented subset                                                                                                                                          | Remaining scope                                                                                           |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `leptoskit_bridge` / `leptoskit_bridge_ffi` | Bounded binary transport, grants, cancellation, retained C/Swift/C++/JNI buffers, Rust worker execution and native job accounting through actual completion | Plugin-specific resource budgets, broader async guest resource protocols and end-to-end device benchmarks |
| `leptoskit_cli`                             | iOS/Android/macOS host generation/builds, editable host files and metadata-driven registration of selected direct dependencies                              | Windows/Linux scaffolds, richer release configuration, installers/signing/notarization/publication        |
| `leptoskit_codepush`                        | Signed Wasm manifests, verification, staging and delta machinery                                                                                            | Installed-host activation/recovery/rollback and native executable updates                                 |
| `leptoskit_plugin`                          | Build-time hooks                                                                                                                                            | Keep build plugins distinct from runtime capability crates                                                |

## Electron desktop baseline

Electron is useful here as an inventory of application responsibilities. Its Chromium/Node architecture does not need to be reproduced to supply those responsibilities.

| Electron reference                                                           | LeptosKit requirement                                                             | Current disposition                                                                                                          |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| [app](https://www.electronjs.org/docs/latest/api/app)                        | Activation/quit/relaunch, app paths, file/URL associations, second-launch handoff | Single-instance lock + argument mailbox; `deep_link` inbound queue/descriptors; quit/relaunch and association writers remain |
| [BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window)   | Create/close/focus windows, bounds, fullscreen and per-window lifecycle           | `window_state` supplies portable placement and owned macOS capture/restore; broader window lifecycle remains                 |
| [Menu](https://www.electronjs.org/docs/latest/api/menu)                      | Application/context menus, standard command roles, accelerators and enabled state | Partial `menu` crate: explicit macOS application-menu and Windows window-menu leases; roles and context menus remain         |
| [Tray](https://www.electronjs.org/docs/latest/api/tray)                      | Owned tray icon, menu/actions, click events and teardown                          | Partial `tray` crate: host-owned macOS/Windows/Linux KSNI icons, menus and bounded events                                    |
| [dialog](https://www.electronjs.org/docs/latest/api/dialog)                  | Open/save/message dialogs and cancellation                                        | Direct desktop `dialog` APIs; guest/window lifecycle integration remains                                                     |
| [Notification](https://www.electronjs.org/docs/latest/api/notification)      | Native notifications and interaction callbacks                                    | Partial immediate `notifications`; interaction callbacks and Windows delivery remain                                         |
| [globalShortcut](https://www.electronjs.org/docs/latest/api/global-shortcut) | Shortcuts while the app is unfocused                                              | Partial host-owned macOS/Windows/X11 `global_shortcut`; Wayland remains                                                      |
| [powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor)     | Suspend/resume, idle and power state events                                       | `power_monitor` host-pushed events + Windows idle queries; macOS/Linux observers remain                                      |
| [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)       | OS-protected secret storage with actual protection availability reported          | Partial `secure_store` credential entries; not a general encrypt/decrypt facade                                              |
| [autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater)       | Installed native application updates                                              | `updater` hooks + pluggable backends; no built-in feed; separate from guest bundle staging                                   |
| [utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process) | Owned child execution, cancellation and bounded results                           | Partial `shell` direct-child supervision with explicit scopes; no Node compatibility or process-tree contract                |

The `arguments` crate captures desktop process arguments and provides typed parsing without exiting the process. Guest disclosure is explicit; it does not provide second-launch activation or make `argv[0]` a trusted executable identity. Structured `logging` supplies a bounded local diagnostic sink, while crash reports, tracing and startup metrics remain separate work.

The broader [Electron API index](https://www.electronjs.org/docs/latest/api/app) also motivates display enumeration, system theme changes, sleep inhibition, desktop capture, printing, sharing, crash reporting, tracing, application purchasing, push registration and owned worker/utility processes. Track these as `display`, `theme`, `keep_awake`, `screen_capture`, `print`, `sharing`, `diagnostics`, `purchases`, `notifications` and process capabilities as their contracts are designed.

Chromium-specific `webContents`, browser sessions, preload scripts, DOM frames and Node integration are not required for a native renderer. Their underlying user needs—network requests, permissions, external content and isolated work—need explicit LeptosKit APIs instead. Touch Bar and other narrowly available UI integrations should have honest platform-specific contracts.

### Desktop application tooling

[Electron Forge's build lifecycle](https://www.electronforge.io/core-concepts/build-lifecycle) separates packaging, making distributables and publishing. Apply that separation to LeptosKit rather than hiding signing, network publication or installer mutation inside a runtime plugin.

| Work item            | Required result                                                                                           | Existing starting point                                                           |
| -------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Generate desktop app | Editable host, window lifecycle, assets and plugin registration for macOS/Windows/Linux                   | macOS AppKit host generated; Windows/Linux scaffolds remain                       |
| Compile native graph | Matching Rust/Swift/Kotlin/C++ target artifacts and bridge versions; deterministic registration           | iOS/Android/macOS metadata discovery and build pipeline                           |
| Package application  | Executable, guest bundle, native libraries, resources, icons and app identity in a runnable target layout | iOS/Android host assembly and runnable macOS `.app`; Windows/Linux layouts remain |
| Make distributables  | OS-specific installer/archive outputs from the packaged application                                       | No installer parity claimed                                                       |
| Sign and notarize    | Platform signing with explicit credentials/provisioning and verifiable output                             | Debug/unsigned mobile builds are not release distribution                         |
| Publish              | Upload already-built artifacts and signed update metadata                                                 | Keep separate from compilation and local plugin calls                             |
| Update               | Verify, stage, activate, recover and roll back with pinned trust                                          | Existing signed Wasm bundle machinery covers only part of this                    |
| Diagnose             | Versioned crash/symbol artifacts, traces and startup metrics                                              | Add platform symbol collection and host instrumentation                           |
| Verify installation  | Launch installed artifact, exercise plugin operation, upgrade and uninstall                               | Extend generated app UI tests into packaged-application tests                     |

[Electron's native module documentation](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules) illustrates the importance of matching native artifacts to their runtime. LeptosKit's equivalent is matching CPU/OS target, native SDK linkage and the C/guest ABI—not adding Node module rebuilding to this project.

## Background execution and headless guests

Flutter's [plus_plugins](https://github.com/fluttercommunity/plus_plugins) include packages whose whole point is running Dart code while the app is closed. On Android they boot a headless `FlutterEngine` from a receiver or service and invoke a callback handle the app registered earlier. LeptosKit's equivalent is running the app's Wasm guest without a window.

| plus_plugins package         | LeptosKit destination   | Status / acceptance scope                                                                                                                                                                                            |
| ---------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `android_alarm_manager_plus` | `android_alarm_manager` | Partial; one-shot/periodic alarms with every upstream flag, exact-alarm permission and fallback, durable scheduled/fired store, boot and permission-grant restore, guest wait/drain, headless launches. Android only |

### What runs today

`NativeHeadlessGuest` (`crates/leptoskit_bridge_ffi/mobile/NativeHeadlessGuest.kt`) is the Android host's windowless guest. It follows `LeptosKitView`'s lifecycle on the main looper: create the `App`, install the text measurer, activate services, register the generated plugins, enable timers, spawn the guest thread, and start it with the display's size. It drops render transactions and Rive frames, runs plugin requests through the ordinary `NativePluginJobs` budget, and leaves the frame clock disabled. `stop(outcome)` posts the same close sequence as `LeptosKitView.close`, then joins plugin jobs and the service owner before reporting `FINISHED`, `TIMED_OUT` or `FAILED`. `bundledWasm(context)` returns the store-shipped guest from `app.lkb`, or null when `codepush.json` enables updates.

The alarm plugin drives it from `AlarmReceiver`: the receiver records the fire in the store, and for a `headless` alarm with no live plugin instance in the process calls `goAsync()` and starts a headless guest whose plugins receive an `AlarmLaunchContext` (a `ContextWrapper` over the application carrying the fired record). The guest's `launch()` returns that record and `finish(sequence)` removes it and stops the run. The broadcast's pending result, and with it the alarm's wake lock, is held until the guest stops, at most `HEADLESS_BUDGET` (eight seconds) later. An unfinished alarm stays queued for the next `next()`/`drain()`, so delivery is at-least-once. The native plugin suite proves the path end to end: its guest finishes alarms carrying the fixture's params, and `AndroidAlarmManagerPluginTest` checks both a finished and a timed-out run.

### Gaps and the design for closing them

- **Code push.** A headless guest must run the code the app runs, but the update store (`NativeReleases`) is leased by the app's window and its launch selects candidates that only a first render can confirm. The plan: give `NativeUpdates` a read-only "confirmed release" query that does not take the directory lease or touch candidate state, and have `bundledWasm` fall back to it when updates are enabled. Until then, headless alarms in such apps stay queued.
- **Longer work.** `goAsync()` keeps the process for about ten seconds. Work that needs longer should hand off to a foreground service (`FOREGROUND_SERVICE_SHORT_SERVICE`, three minutes on Android 14+) or WorkManager; both can reuse `NativeHeadlessGuest` unchanged, with the receiver starting the service and the service owning the guest. That needs `android-services` metadata alongside `android-receivers`.
- **Choosing the handler.** Upstream stores a Dart callback handle per alarm. The guest has one entry point, so the alarm's ID and params select the handler; `handle_launch` runs before the app's other startup work. A dedicated guest export (`leptoskit_background(kind, payload)`) would let the host skip building the UI tree, but needs an interpreter entry point and generated-guest support.
- **Other background packages.** WorkManager, background fetch and push-message handlers fit the same shape: a manifest component from `android-receivers` (or a future `android-services`), a durable queue for at-least-once delivery, and an optional headless run. Apple platforms have no way to run app code at a chosen time; `BGTaskScheduler` runs at the system's discretion and would need its own plugin and an iOS headless guest built on `NativeGuestRuntime.swift`.

## Implementation order and completion gates

The current media additions provide these specific subsets:

| Crate               | Implemented subset                                                                                                        | Platforms                                                | Remaining scope                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `image_manipulator` | Bounded JPEG/PNG decoding, ordered crop/resize/rotate/flip, encoding and guest binary protocol                            | Automatic native Rust worker; direct Rust/browser engine | Other formats, retained image handles, streaming output and codec-private hard allocation guarantees        |
| `screen_capture`    | Android owned secure-window leases and screenshot callbacks; iOS scene capture-state and app-wide screenshot observations | Automatic Android/iOS registration                       | iOS prevention unavailable; desktop/browser unavailable; real recording and compositor verification pending |

This ordering is a proposal based on dependencies and common application needs, not an upstream ranking.

1. **Extend asynchronous integration:** verify generated HTTP/WebSocket and shell guest lifecycles across devices and add live-parent-window dialog presentation. Keep explicit destination scopes and bounded resource ownership; do not block the interpreter waiting for I/O.
2. **Verify and extend existing ports:** generated-app permission/lifecycle flows, physical haptics/sensors/brightness/speech, platform-specific credential failures, installed startup behavior and browser policy. Existing tests do not imply physical-device or release-package parity.
3. **Extend common services:** extend orientation observation and document import beyond their current bounded contracts; verify authentication policy on physical devices. Extend notifications with local scheduling/actions and remote-token registration as separately verified operations. Inbound links need launch routing and generated associations.
4. **Complete desktop application ownership:** Windows/Linux scaffolds, broader window/display APIs, menus, tray, shortcut event-loop integration, second-launch handoff and native updater. Build installers/signing/notarization alongside these so installed-app behavior can be tested.
5. **Expand acquisition and media:** remaining sensors (hinge), background location/geofencing, camera, barcode, audio/video, images, contacts CRM sync / browser picker, calendar reminders/recurrence, media library and NFC. Verify light/pedometer behavior on physical devices. Large data needs bounded streaming or owned resources; native views require renderer integration.
6. **Add background and extension integration:** task execution, notification/background launch, widgets, app intents, purchases, attestation and platform-specific identity features.

A port is complete only when its public operation list, target matrix and failure behavior are documented and backed by tests. For each operation record:

- Rust API and independent crate; explicit wire version and checked decoding.
- Real native/browser implementation, supported OS versions and hardware requirements.
- Required build contributions: permissions, usage strings, entitlements, URL schemes, extensions or dependencies.
- Permission denied, user cancellation, unavailable capability and native failure as distinct outcomes where the platform distinguishes them.
- App close, guest replacement, backgrounding, pending work cancellation and subscription cleanup.
- Bounded memory and work queues; blocking I/O off the UI thread; payload/FFI ownership tests.
- Device/browser evidence for user-facing behavior, with simulator limits stated.

Do not mark an entire upstream module complete after adding one method. Do not claim that a bridge microbenchmark proves an end-to-end advantage over Flutter or React Native. Measure warmed and cold calls, event throughput, allocations, large payloads, UI-thread time and platform-operation latency separately.
