# One leptos tree. Real native widgets.

leptoskit is a Rust toolkit for building an app's interface once, with leptos components and built-in Tailwind styles, and shipping it to the browser and as real native widgets on the desktop and on phones.

</Hero>

## What leptoskit is for

Most cross-platform toolkits make you pick: render to a web view everywhere, or write each platform twice—and then stitch together separate backend, auth, database, and deployment tools on your own. leptoskit brings the whole app into one Rust workspace.

<!-- {=leptoskitOverview} -->

leptoskit is a full-stack Rust toolkit for taking an app from a single codebase to every screen and to production:

- **One UI, real native widgets:** describe screens once as a tree of components (`View`, `Text`, `Button`, `TextInput`, `ScrollView`, …) styled with built-in Tailwind. On the web it renders to the DOM with SSR, CSR, or islands; on macOS, iOS, Android, Linux, Windows, the terminal, browser extensions, and experimental HarmonyOS it renders native controls with no web view and built-in signed WebAssembly over-the-air updates.
- **Full-stack by default:** typed server functions (`leptoskit_rpc`), file-based routing, cached queries, Rust-struct SQLite or Postgres schemas and migrations (`leptoskit_db`), passkey/OAuth sign-in and OIDC IdP (`leptoskit_auth`, `leptoskit_idp`), background jobs, real-time updates, and native device plugins live beside the UI in one workspace configured by `leptoskit.toml`.
- **Built for AI agents:** compiler-checked builder syntax by default (`[lint] markup = "builder"`), a built-in MCP server (`lk mcp`) for live DevTools inspection and cloud deploys, safe runtime generative UI (`leptoskit_agent_ui`), verifiable releases (`leptoskit verify`), a first-party skill, and `llms.txt` docs.
- **Two clear ways to ship:** deploy straight from `leptoskit.toml` to **LeptosKit Cloud** (`lk cloud launch` / `lk deploy`), or self-host on your own Linux VMs with **OpenTofu + Kamal** (`lk infra`).

## A screen in leptoskit

A screen is a function returning an `Element`. Tailwind classes style it on every platform:

```rust
use leptoskit::prelude::*;

#[component]
pub fn Welcome(name: &str, on_start: impl Fn() + Send + Sync + 'static) -> Element {
	view! {
		<View class="gap-4 rounded-2xl bg-white p-6 dark:bg-slate-900">
			<Text class="text-2xl font-bold">{format!("Hello, {name}")}</Text>
			<Text class="text-slate-500">"Your interface, everywhere."</Text>
			<Button class="rounded-lg bg-rose-500 px-4 py-2 text-white" on:press=on_start>
				"Start"
			</Button>
		</View>
	}
}
```

The same function renders as DOM elements in a browser, and through a platform backend as `NSView`s, `UIView`s, Android views, GTK widgets, Win32 controls, or ArkUI components. [The shared components guide](guide/07-shared-components.md) walks through it, and the [component catalog](reference/components.md) lists every component.

## Over the air updates

An installed native app is a small host that runs your interface as a WebAssembly bundle. Code push ships a new bundle over the air: signed, content-hashed releases, binary deltas, and a client that verifies every byte before it stages the update. A trial release replaces the working one only after it renders, so a release that fails to start is rejected and the app keeps running. The generated iOS and Android apps install these releases today; the generated macOS, Windows, and Linux apps don't check for updates yet. A release must match the installed host's interface contract and signing policy, and store rules still apply to what a download changes. [Code push](guide/05-code-push.md) covers keys, channels, publishing, and rollback.

## Where things stand

leptoskit is young, and these docs say plainly what works today.

Native filesystem, SQLite, and secure-store plugins enforce aggregate storage budgets in addition to operation limits. See [storage and networking](platforms/plugin-inventory.md#storage-and-networking) for defaults and upgrade behavior.

<Callout kind="note" title="Works now">

The web pipeline: cached builds, `wasm-opt`, server rendering, islands, and Axum serving. The layout engine and the renderer. Native backends for macOS, iOS, Android, Linux, Windows, and the terminal that draw every built-in component, checked in CI on a real Mac, an iOS simulator, an Android emulator, a Linux desktop, a Windows desktop, and headless terminal sessions. Generated apps for all of those platforms. The Wasm runtime and code push, from a signed release to a verified, staged update on iOS and Android, optionally gated on independent source approvals. File routes, server functions, queries, translations, and the testing tools.

</Callout>

<Callout kind="important" title="Known gaps">

- **Generated Apple and Android apps** draw the common controls, including `Switch`, `Checkbox`, `Radio`, `Slider`, `LinearProgressIndicator`, and `ActivityIndicator`. A custom widget is an empty container until a host registers one. Native controls expose their checked and range states, but other accessibility roles and states remain limited. File-route Stack, Tabs, and Drawer navigators, typed deep-link opening, and Android system Back through `leptoskit_system_back` are in the router; the Android activity asks the host view before finishing, and the native `guestSystemBack` symbol is soft-resolved until the guest-thread FFI lands.
- **iOS:** iOS has no native checkbox or radio button, so `Checkbox` and `Radio` are drawn with `UIButton`. VoiceOver gets fewer roles than macOS, and no expanded or collapsed state. [Live Activities](platforms/ios.md#live-activities-and-the-dynamic-island) wire ActivityKit start/update/end, Dynamic Island slots, stale dates/relevance, and iOS 17.2+ push-to-start tokens on iOS (plus Android 16+ Live Updates on Android); the iOS app still supplies `NSSupportsLiveActivities`, a Widget Extension for `LeptosKitLiveActivityAttributes`, and Push Notifications when using push tokens.
- **Android backend:** a `Custom` widget kind with no registered native implementation is an empty container, as on the other platforms. TalkBack gets a smaller set of roles than macOS. Fold posture, dual-pane, and tabletop layouts work through the `posture` plugin; per-hinge angles on multi-hinge devices and live foldable-emulator checks are still thin — see [Foldable phones](guide/21-foldable-phones.md). The [`device-policy`](platforms/plugin-inventory.md#device-management) plugin covers Device Admin lock, password rules, camera disable, and confirmed wipe on Android only; apps own the receiver and least-privilege policy XML, and Google Play still constrains distribution. Device Owner / Android Management enrollment is not included.
- **Overlays:** `Modal` and `Popover` are presented by every platform: a `<dialog>` and a `popover` element on the web, drawn over the screen in the terminal, a sheet and an `NSPopover` on macOS, a form sheet and a system popover on iOS, a dialog and a popup window on Android, a modal window and a GTK popover on Linux, and owned popup windows on Windows. Dimming, placement and what asks to dismiss differ by platform. See [Show a dialog or a menu above the screen](guide/07-shared-components.md#show-a-dialog-or-a-menu-above-the-screen).
- **Linux:** live regions update their text but are not announced, because announcements need GTK 4.14 and leptoskit supports GTK 4.6. A `TextArea` shows no placeholder, because GTK's text view has none.
- **Windows:** `Switch` is drawn as a checkbox. Rounded corners are cut with a window region, so their edges are not smoothed, and borders stay rectangular inside them. Accessibility has no expanded or collapsed state. A `Vector` with no background takes clicks only where it has ink. A `TextArea` shows no placeholder.
- **Desktop shell plugin:** invocation limits and cancellation clean up Unix process groups and Windows Job Objects. Unix commands that deliberately leave their group need additional host containment. Windows retains capacity when a member's termination cannot be confirmed; see the [plugin inventory](platforms/plugin-inventory.md).
- **Native menus:** builder APIs (`MenuBar`, `Submenu`, `Command`, `Check`) and macOS application-menu leases land in `leptoskit_plugin_menu`. Windows window-menu leases require the same root-submenu shape and host `translate_accelerator` wiring; Linux has no standalone menu bar (tray snapshots only). Duplicate accelerator chords are rejected at build time; `set_accelerator` updates a live row. Standard roles, radio groups, icons, context menus, and GTK 4 window menus are still out. The generated Swift macOS host still hardcodes a small Edit menu; generated Windows and Linux runners do not host the API yet. See [macOS application menus](platforms/macos.md#application-menus).
- **Home-screen widgets:** the [`home-widgets`](platforms/plugin-inventory.md) plugin publishes snapshots, multi-entry timelines, iOS 18+ Control Center control states/reloads, and Android Quick Settings tile states across iOS, Android, and macOS, with `LeptosKitWidgetStore` (Swift) and `HomeWidgetsPlugin.readSnapshot` / `readQuickTile` (Kotlin) helpers. It does not scaffold Widget Extensions, `AppWidgetProvider`s, or `TileService`s, draw widget UI, or support Windows/Linux/browser backends yet.
- **Electron-shaped desktop lifecycle:** hosts can construct `power_monitor`, `deep_link`, `updater`, and second-launch handoff on `single_instance`. Idle-time queries are Windows-first; association writers, shipping update feeds, and desktop screenshot capture remain. See [Electron concepts](platforms/electron.md).
- **Background alarms:** the [`android_alarm_manager`](platforms/plugin-inventory.md#background-alarms) plugin schedules Android alarms that fire while the app is closed, and can start the app's guest without a window to handle one for up to eight seconds. Apps that take over-the-air updates keep those alarms queued for the next launch instead. iOS, macOS, Windows, Linux, and the browser have no equivalent and return `Unavailable`.
- **Rive:** [shared Rive elements](guide/20-rive.md) render on the web, macOS, iOS, Android, Linux, Windows, and experimental HarmonyOS. Native playback supports vector scenes and rejects images, fonts, text, layout, scripts, audio, view models, and unsupported draw features. View-model data binding is not exposed. HarmonyOS playback still needs validation on the target device.
- **Game host:** [`leptoskit game`](guide/39-game-engine.md) runs Rust gameplay behind leptoskit menus. The world is drawn with wgpu (or on the CPU when the machine has no adapter) and the menu is the same component tree as every other platform, for `View`, `Text`, and `Button`. It is a desktop binary on Linux, macOS, and Windows. It does not package an iOS, Android, or browser app, and it does not open a window: it writes the last frame as a PNG. Other widget kinds commit and take a frame, but only background colour and text are drawn.
- **3D scenes:** [`Scene3d`](guide/33-3d-scenes.md) draws glTF models with skins, morph targets, and animation on the GPU on the web (WebGPU, or WebGL2), iOS and macOS (Metal), and Android (OpenGL ES, or Vulkan by choice). Windows and Linux leave an empty space, the terminal draws a placeholder, HarmonyOS stops with an error, and the watch surfaces refuse it. One directional light, a soft disc shadow, no stereo multiview yet, and only PNG and JPEG textures. Android, iOS and macOS scene views send primary-pointer input through `Scene::next_pointer`, separately from model events. Native drawing has not yet been checked on a device or simulator in CI.
- **Canvas text editor (experimental):** `CanvistEditor(id)` marks where a [canvist](https://github.com/canvist/canvist) text editor shows, and takes a label, a placeholder, `read_only`, and `focused` like a `TextArea`. On the web the editor comes from the `leptoskit_canvist` crate, which is not on crates.io yet, so an app adds it as a git dependency: create a `CanvistState`, give the element its `id()`, and the editor appears in the element, on server-rendered pages too once they hydrate. It edits plain paragraphs and copies and pastes plain text. With the crate's `ink` feature a page also holds drawings between its paragraphs: `insert_drawing()` puts a sheet at the caret, and a mouse, a pen, or a finger draws on it in the pen `set_pen` chose, each stroke one step of undo. The [sketchnote example](examples.md#sketchnote) is a notebook built that way. Formatting and a first paint from the server are not there yet, only Chrome has been tested, and drawing with a real pen or finger has not been tried on a device. macOS, iOS, Android, Linux, and Windows show an empty view, the terminal a dim block, HarmonyOS stops with an error, and the watch surfaces refuse it. Use `TextArea` for several lines of plain text in a released version.
- **Motion:** [`motion`](guide/32-motion.md) animates elements on the web only. macOS, iOS, Android, Windows, Linux, the terminal, and HarmonyOS show every element at its resting pose, and scroll-driven motion needs a browser with CSS scroll timelines; others show the resting pose too.
- **Sound:** the [`audio`](guide/34-audio.md) plugin plays looping music and effects with fades, volume ramps and gliding filters through one Rust engine on iOS, Android, macOS, and Linux, and through Web Audio in the browser. Only macOS output has been heard on real hardware so far. Android does not report losing audio focus, recording is not supported, and HarmonyOS has no output.
- **Video:** the [`video`](platforms/plugin-inventory.md) plugin creates host-owned URL players (play/pause/seek, muted/loop/rate, status) and a `Video(player_id)` surface on iOS/macOS (`AVPlayer`), Android (Media3), and the browser (`<video>`). Tracks, caching, AirPlay, fullscreen controls, iOS PiP enter against an attached player, audio focus, and Windows/Linux/HarmonyOS playback are not covered yet.
- **Camera:** the [`camera`](platforms/plugin-inventory.md) plugin creates host-owned sessions (back/front), torch when supported, bounded still capture, status, and a `Camera(session_id)` surface on iOS/macOS (`AVCaptureSession`), Android (CameraX), and the browser (`getUserMedia`). Video recording and Windows/Linux/HarmonyOS remain out of scope.
- **Runtime plugins on Windows, Linux, and the terminal:** the generated Linux app registers plugins written in Rust, but not app-owned services. The generated Windows and terminal apps don't register runtime plugins yet. Plugins they can't run are left out with a warning, and calls to them fail with `Unavailable`. See [plugins a platform can't run](platforms/host-projects.md#plugins-a-platform-cant-run).
- **Android intents:** the [`android_intent`](platforms/android.md#android-intents) plugin launches, broadcasts, and resolves arbitrary intents on Android only; every other platform returns `Unavailable`. It does not return activity results or share files with per-URI grants.
- **Picture-in-picture:** Android can enter activity PiP (with `android:supportsPictureInPicture` on the activity) and hold a system overlay after a settings grant for `SYSTEM_ALERT_WINDOW`. iOS reports PiP support but does not yet enter it without an attached video player, and has no draw-over-apps overlay. Desktop and the browser return `Unavailable`. See [runtime plugins](platforms/plugins.md).
- **Notifications:** the [notifications service](guide/notifications/readme.md) stores one durable, idempotent notification per recipient in its own database and serves each person their own live inbox — with audiences partitioned by topics, by conditions over topics, the app-set person attributes (segments), and the enrolled devices' platform, locale, time zone, and app version — judged per device, so a push reaches only the devices a condition matches — and "everyone" over the person registry, subscribed and set by the app's server in batches or by the person where the operator opened the topic, fanned out durably in batches with status and a dry run — scheduled visibility with cancel-before-due (mid-fanout included), sends translated per person and delivered at a wall-clock time in each person's own time zone, expiry, per-person read and dismissed state shared across their devices, and category opt-outs enforced at send and at visibility — on the web, iOS, Android, macOS, and Linux, with the terminal and Windows screens reading it like any other service call. A tap the app reports is recorded as an open, once per person, and marks the notification read on every device; a per-send report then counts how many of the send's notifications are stored, read, opened, dismissed, and cancelled. Server-side push is built: with a transport configured (APNs by `.p8` key, FCM by service account, or Web Push by VAPID pair), a send also reaches the endpoints its recipients enrolled — durable per-endpoint deliveries attempted by a background job, retried with the provider's `Retry-After` honored, ended with sanitized reason codes, and reported to the app as per-endpoint status where `accepted` is provider acceptance, deliberately not a receipt. Each send can be shaped — silent data messages, priority, image, sound, a per-recipient unread badge, a click link, and per-platform `android`/`apple`/`web` overrides, degraded in a documented order when a payload is over its limit — and `send_test` probes one person's devices with a spec, once each, writing nothing. The client half of enrollment is here on the web, iOS, Android, and macOS — the browser push handler, and native token acquisition that enrolls an APNs device token on iOS and macOS and an FCM registration token on Android — while Windows, Linux, HarmonyOS, and the watch surfaces have no enrollment story. The app's server can also list the sends it made, read what an audience is made of before sending to it, preview the request each provider would get, and keep campaigns as drafts that are tested, launched once, and cancelled; there is no screen for composing them yet, rows are deleted after operator-set retention periods, and the chapter's [Coming from Firebase](guide/notifications/coming-from-firebase.md) page lists what Firebase Cloud Messaging has that this does not. Composing a banner with the local-notifications plugin works on iOS, macOS, Android 26+, the browser, and Linux; Windows answers `Unavailable`.
- **App shortcuts, badges, and NFC:** [app shortcuts](platforms/plugin-inventory.md#launcher-presence-and-near-field-reads) publish static launcher items on iOS and Android and a macOS dock menu through the generated host, index `CoreSpotlight` items and publish `NSUserActivity` Handoff on Apple, and deliver incoming `ACTION_SEND` (Android) or Share Extension (iOS) payloads; [badge](platforms/plugin-inventory.md#launcher-presence-and-near-field-reads) sets icon counts on Apple and Android, with a Linux D-Bus client for custom hosts and the browser Badging API where the page is an installed app; [NFC](platforms/plugin-inventory.md#launcher-presence-and-near-field-reads) reads one NDEF text or URI record on iOS and Android. Windows jump lists, Siri App Intents registration, Android `AppSearch`, and NFC tag writes remain open.
- **Unwired mobile OS frameworks:** StoreKit 2 / Google Play Billing in-app purchases, Apple Pay / Google Pay and Wallet passes, CallKit / `ConnectionService` VoIP, VisionKit / ML Kit barcode & document scanners, speech-to-text (`SFSpeechRecognizer` / `SpeechRecognizer`), Lock Screen Now Playing / `MediaSession` controls, on-device AI (Foundation Models / Gemini Nano), App Clips, SharePlay, CloudKit, Play In-App Updates, and live App Attest / Play Integrity (`app-integrity` is currently an `Unavailable` stub) require host-supplied native plugins today; see [iOS](platforms/ios.md#complete-ios-and-ipados-capability-map) and [Android](platforms/android.md#complete-android-capability-map).
- **HarmonyOS (experimental):** eight components (not including `Vector`), synchronous Rust plugins and ArkTS plugins (`posture`, `health`, `wearable`, `watch-sync`, `ble`, `battery`, `thermal`, `pedometer`), wearable (`Huawei Watch`) `deviceTypes` configuration via `[native.harmonyos]`, italic text and per-edge borders through ArkUI, and no code push, dark mode, right-to-left layout, `active:` pressed styles, or CI run on a device. See [HarmonyOS](platforms/harmonyos.md).
- **Augmented and virtual reality (experimental):** the [`xr` plugin](guide/34-augmented-reality.md) tracks the world through ARKit on iOS, ARCore on Android, WebXR in the browser, and OpenXR on headsets, with a rotation-sensor fallback and recorded playback. On iOS and Android a `Scene3d` with the camera backdrop draws over the session's camera picture, hidden behind real things where the phone measures depth, and Android phones without ARCore show the back camera through Camera2. Recorded playback, the frame stream, and drawing over a camera picture are tested; the ARKit, ARCore, Camera2, WebXR, and OpenXR backends build but haven't run on a device. The camera picture reaches the GPU as a CPU copy rather than shared on the GPU. [Meta Quest](platforms/quest.md) apps build from the Android project, publish signed APKs through `leptoskit publish quest` (wrapping `ovr-platform-util`), and draw the app's 3D scene into the headset from a panel app through an immersive activity, but haven't been installed on a headset or uploaded with live Meta credentials, and immersive mode shows only what the app draws in 3D. The experimental [Meta Horizon extension](platforms/horizon.md) scaffolds TypeScript `horizon/ui` Custom UI host templates (not yet run in the Horizon Worlds Desktop Editor) and validates/packages offline MHCP web zips (`leptoskit native platform package horizon`). Apple Vision Pro, image tracking, room meshes, and shared anchors are not covered. Phones without platform depth (the Solana Seeker, ARCore phones without the Depth API, iPhones without LiDAR) get depth estimated from the camera picture by the `leptoskit_depth` model when the app ships it and sets `depth-model`; it is tested on photographs and through the plugin's runtime, but has not run on a phone.
- **Wear OS, watchOS, and HarmonyOS wearables (experimental):** watch apps use the sensor-first [`WearableApp`](platforms/watch.md) and [`leptoskit::watch`](platforms/watch.md) surfaces — pages, tiles, glances, and complications with layout budgets — paired with the `wearable`, `health`, `watch-sync`, and `ble` plugins. App-owned Wear OS (including Samsung Galaxy Watch) and watchOS hosts prepare and build through `leptoskit native`, and HarmonyOS supports `[native.harmonyos]` `wearable` device types; live watch hardware CI, signed store packaging, and always-on ambient updates remain open. See [Wear OS](platforms/wearos.md), [watchOS](platforms/watchos.md), and [HarmonyOS](platforms/harmonyos.md).
- **Terminal:** the terminal's font is the user's, so font sizes and weights draw as attributes and colors rather than different metrics, `Image` and `Vector` draw a placeholder texture, `Rive` playback is unsupported, and right-to-left text is not reordered. See [Terminal](platforms/tui.md).
- **Browser extensions:** [extensions](platforms/extension.md) build and package for Chromium, Firefox, and Safari, whose extension goes inside the macOS and iOS apps. Surfaces talk to the background worker with one-shot messages or long-lived ports; storage and optional permissions cover clear/keys/quota and grant/revoke listeners. `leptoskit dev` and `leptoskit test extension` run them in Chrome for Testing or Firefox (`--browser firefox`). [`leptoskit publish`](guide/24-publishing.md) uploads extensions to the Chrome Web Store, Edge Add-ons, and addons.mozilla.org, and apps to App Store Connect, Google Play, the Solana dApp Store, and the Meta Horizon Store. iOS apps carry their Safari extension; Mac App Store submission still needs a sandboxed host.
- **Service workers:** the web page can [register a service worker](platforms/web.md#service-workers), exchange messages, describe caching strategies, open Cache Storage, and manage Web Push subscriptions through `leptoskit`'s `service-worker` feature. You still ship the worker script yourself; native apps, the terminal, and extension backgrounds report the APIs unavailable.
- **DevTools:** under `leptoskit dev`, the web page and the generated macOS, iOS, and Android apps report to [DevTools](guide/26-devtools.md#where-it-stands). The native apps outline the selected element and pick whatever you tap, but don't name each element's component yet. Windows, Linux, the terminal, and HarmonyOS don't report yet.
- **Scrolling from code:** [`scroll_offset`](guide/17-virtualized-lists.md#programmatic-scrolling) scrolls a list to a number and a [`Reveal`](guide/07-shared-components.md#scroll-an-element-into-view) scrolls one element into view, on the web and in the generated macOS, iOS, Android, Windows, and Linux apps. Windows and Linux jump where the others animate, and neither has scrolled on a Windows machine yet outside CI. HarmonyOS and the terminal don't scroll from code yet.
- **Sign-in on Windows and the terminal:** the generated Windows and terminal runners can't host plugins yet. They build without the ones `leptoskit.toml` grants, and say so, so [sign-in](guide/23-sign-in.md) there answers that it isn't set up: its client needs the `http`, `secure-store`, `passkeys`, and `web-auth` plugins. The generated Linux app signs in with everything but passkeys.
- **Timers:** generated macOS, iOS, Android, Windows, Linux, terminal, and experimental HarmonyOS apps give the query cache a real, cancellable timer, so retry backoff, debounce, and cache expiry wait rather than firing at once. Hosts built before the timer plugin existed answer `Unavailable`; `has_timer` reports `false` there. See [timers in a native guest](guide/11-fetching-data.md#native-and-embedded-hosts).
- **Sign-in:** email codes, authenticator apps (TOTP), recovery codes, step-up, required two-step verification, passkeys, opt-in passwords, the twenty built-in providers (Google, Apple, Microsoft, GitHub, Facebook, X, Discord, LinkedIn, GitLab, Slack, Twitch, Spotify, Reddit, Amazon, Dropbox, Bitbucket, Notion, Zoom, TikTok, and Yahoo), and any OpenID Connect provider work on the web and in the generated iOS, Android, and macOS apps. The apps use the system's own passkey sheet, Sign in with Apple's own sheet on Apple devices, and the system browser for other providers. In the apps, passkeys aren't offered in a text field's suggestions; Android signs in with providers only when its default browser has Auth Tab (Chrome 137 or later); and Apple devices need the app's associated domain, which the generated Xcode projects don't add yet. The generated Linux app signs in too, with providers in the default browser and the session in the desktop's Secret Service keyring. Windows and Linux have no native passkeys, so passkey calls answer `unsupported` there; a Windows host that registers plugins itself gets provider sign-in in the default browser. HarmonyOS has neither. Solana wallets link and sign in through the Wallet Standard on the web only; native apps list, rename, and unlink linked wallets, and answer `unsupported` for asking a wallet to sign until a native wallet adapter exists. Wallet proofs are message signatures, so program-derived addresses, multisigs, and wallets that can't sign messages can't be linked yet. `leptoskit generate auth` includes masked `PasswordInput` fields when password sign-in is enabled. Merging accounts can bring the other account's data along once every table that holds it declares an `on_account_merge` strategy, which `leptoskit db check` enforces.
- **Animations:** [transforms, transitions, keyframes, and entering and exiting animations](guide/32-animations.md) run on the platform's compositor on the web and in the generated iOS, Android, and macOS apps. The web doesn't run `exiting` or `layout_transition` yet. Windows, Linux, the terminal, HarmonyOS, and the native backend crates ignore them, so values jump.
- **Toasts:** [Ding-inspired toast pills](guide/33-toasts.md) morph in place from ordinary `View` / `Text` / `Button` / `Vector` builders. Enter, morph, and stack springs match Ding's tunings where animations already run; elsewhere the resting phase still shows.
- **Gestures:** [tap, long press, pan, pinch, rotation, and fling](guide/38-gestures.md) run in one arena on the Android widget backend and on Linux. A winning drag claims the pointer so a button does not also click. The web, iOS, macOS, Windows, the terminal, HarmonyOS, and the generated Swift and Kotlin renderers still deliver presses and clicks only.
- **Styled text, key handlers, and controlled focus** work on the web and in the terminal. The native widget backends still draw a `Text`'s styled runs in its own single style, deliver no `on_key` presses, and do not move focus for `focused(true)`. To move focus once, a [`FocusRequest`](guide/15-accessibility.md#move-focus-once) works on every backend; it has been run on the web, in the terminal and on GTK, and is untested on macOS, iOS, Android and Windows. **Italic and per-edge borders** (`border-l-2`, `border-t`, …) paint on Linux (GTK), Android, and experimental HarmonyOS (ArkUI); AppKit, UIKit, and Win32 still draw italic upright and leave a per-edge border undrawn.
- **LeptosKit Cloud:** `lk cloud launch`, `lk deploy`, `lk cloud status`, `lk cloud logs`, `lk cloud estimate`, secrets, domains, usage, and the `lk mcp` cloud tools are wired end to end against the control plane, workers, and platform generator; live cluster acceptance runs, dedicated database tiers (`s`/`m`/`l`), cluster-worker Postgres dump/restore, and automatic bucket provisioning for `[cloud.storage.buckets.<name>]` remain open. See [LeptosKit Cloud](guide/41-leptoskit-cloud.md).

On every native platform, `Image` loads the pictures your app bundles with [`asset://`](guide/36-assets.md) and local files, not URLs. Code push updates reach the iOS and Android apps; the generated desktop apps don't check for them yet. CSS shadows, gradients, filters, and custom fonts aren't supported anywhere yet: the [CSS coverage reference](reference/css-coverage.md) lists what is. Color and length `var(--name)` utilities work on the web and, through `Theme`, on native — including one nested fallback, `/opacity` on color vars, and `[theme]` tokens in `leptoskit.toml`. Deeper nesting and Tailwind `@theme` / `tailwind.config` files still don't. Rive's internal vector paints and transforms are separate from those CSS properties. [Platforms](platforms/readme.md) has the full picture.
